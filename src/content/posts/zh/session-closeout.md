一次 AI 对话结束后，代码可能已经合并，解释可能写得很完整，关键经验却仍散在几十轮消息和工具输出里。几周后换一个工具继续工作，又要重新寻找：最后采用了哪个方案，哪些检查真的做过，还有什么没有完成？

我把整理这一切的过程叫作 **session closeout，会话收尾**。它核对一次工作的事实，为结果、证据和遗留事项找到持久的去处，再挑出值得进入长期知识的内容。在 [Yaaa 导读](/posts/yaaa/)里，模型和工具可以更换；这里要解决的，就是换工具以后，工作还能否接得上。

## 一次发布，几种不同的“完成”

这次博客建设就遇到过一个例子：文章已经合并，CI 和自动发布通过，线上三语文章也能阅读，但复验发现一个已经删除的旧页面仍返回 200。源站已经没有它，正式域名却还命中旧缓存。问题后来进入了[网关与发布方式的修复](https://github.com/Jarvie8176/blog-tech/pull/13)。

当时，文章修改、内容合并和部署各自有成功证据；删除路径的对外行为仍有缺口。收尾记录需要同时保留这些事实，并把后续排查交给明确的任务。把整次工作压成一个“完成”，会丢掉最有价值的部分。

完成还取决于当次请求。用户只要求准备审阅稿，交付一个可审阅 PR 就可能满足要求；用户要求合并上线，待审 PR 就仍是剩余项。收尾可以在业务任务尚有遗留时完成交接，但交接材料已经准备好，也不能证明接收者已经接手。

## 用五步把结果留下来

我目前复用一份五步 SOP。这里的 SOP 指一份固定的操作说明，各个 AI 工具都按同一份内容执行。

1. **回顾发生了什么。** 重查相关 PR、任务和验证结果，标明能看到的对话范围。只拿到压缩摘要时，就记录覆盖缺口。
2. **更新任务进度。** 检查相关 issue 和上级项目的正文是否仍准确，进度评论只补充本次增量。满足验收条件后再关闭任务。
3. **决定材料的去向。** 脚本、配置、失败记录和验证方法，分别判断应进入仓库、保留为过程记录，还是按规则清理。
4. **交接剩余工作。** 写清当前状态、证据入口、已试过的路线、限制、下一步与验收条件。能放进已有任务，就不用再新建一个交接 issue。
5. **检查是否形成了可复用方法。** 优先修订已有 SOP 或 procedure；确有重复需求时，再提取新的流程。

每一步要能找到产物或“不适用”的理由。产物可以是更新后的任务正文、一份工作记录、一个脚本 PR，也可以是自包含的交接说明。是否另写 journal 文件、是否新建 PR，取决于实际材料和用户要求。

## 证据要能支撑结论

在一次既有收尾记录评估中，扫描了 92 条讨论记录，并深读 10 组目的抽样案例。评论不等于独立会话，这组样本也不能用来计算成功率；评估没有重新执行那些生产任务。它的价值是找出反复出现的错误推断。

例如，原始比较报告已经丢失，只剩用户转述的数字，保留下来的代码 hash 不能把这些数字变成独立验证结果。CI 全绿但仍有已知未修复问题，也不能写成全部验收通过。文件 hash 一致、用户短时抽检和完整场景验收，各自回答不同的问题。

我希望每项重要结论都能回答三组问题：

| 要核对什么               | 需要留下的信息                                             |
| ------------------------ | ---------------------------------------------------------- |
| 谁观察到了什么？         | 程序直接观察、用户报告、另一个 agent 转述，还是推断        |
| 证据还能拿到吗？         | 可读取、没有权限、已经丢失，或当时没有采集                 |
| 覆盖多大范围、哪个时刻？ | 检查时间、对象、通过与跳过的数量，以及历史结果还是当前状态 |

“没有权限”不能记成“已丢失”；“上次成功”不能自动写成“现在正常”。程序可以检查字段、引用、内容摘要和相互矛盾的声明。数据库恢复是否完整、设备体验是否可接受，仍需要对应领域的验证方法。

## 从工作记录到长期知识

收尾先保留一次工作的上下文。长期知识还需要选择：它是否会再次有用，有什么证据，在哪些条件下成立，应该由谁维护？在个人系统中，维护者通常就是用户本人；agent 提出候选，维护者决定是否接受、修订或撤销。

![从对话到知识：核对事实并收尾，保留工作记录与交接；可复用经验经过审阅，进入记忆、SOP 或测试，再在下次工作中检查适用性](/images/closeout/lifecycle-zh.png)

_工作记录可以保留未完成事项；进入长期知识的内容需要另行审阅。图示表达目标流程，不表示自动沉淀链已经上线。_

| 材料                                   | 合适的去处                               |
| -------------------------------------- | ---------------------------------------- |
| 与这次问题有关的过程、失败和更正       | 工作记录与受控归档                       |
| 有证据、范围清楚、会影响未来判断的事实 | 长期记忆候选                             |
| 稳定的检查顺序与操作方法               | SOP；确定性步骤可继续成为 procedure 候选 |
| 能复现的失败或错误判断                 | 测试、反例与故障案例                     |
| 未完成工作                             | 已有任务或自包含交接                     |

博客缓存问题值得留下的，是一条带条件的方法：站点通过网关发布、且允许删除内容时，发布验收要检查被删除的原始 URL，并核对正式页面对应的提交。它在[发布脚本、文档和回归检查](https://github.com/Jarvie8176/blog-tech/pull/13/files)里获得了具体落点。这个案例可以追到方法落地，还不能据此声称已经证明了跨工具独立接手的效果。

一张足够小的沉淀卡，可以只保留：**结论、证据、适用范围、失效条件、维护位置、下次使用入口**。后来发现结论不成立，应能修订或撤销它。摘要、脱敏文本和检索索引仍可能含有私密信息；原始对话与长期知识要分别管理访问、保留和删除。

## 一套跨工具的实现

我把收尾拆成三个部分：共享 SOP 说明要做什么；当前 agent 整理可见材料、补查事实并提出修改；程序负责可以确定性检查的部分。Codex 和 Claude Code 的入口可以不同，收尾语义和证据要求保持一致。

一次收尾可能回顾多个源会话，也可能在后来补交接。输入需要分别标明源会话、这次收尾运行，以及修订关系。相同输入重跑应避免重复写入，新发现和新交接则要保留为增量修订。

执行机制的设计是先整理证据包与计划，再在授权范围内写入，最后回读结果。对话摘要只是输入之一；程序不能因为模型写了“完成”就签发完成状态，也不应为了验证收尾而自行重演生产故障。

### 先做一张可解释的状态表

目前的离线原型只显示每个会话的两个量：**closeout state** 和 **staleness**。前者表示有没有明确收尾记录、记录是否覆盖最新活动；后者表示距离最后一次已保存活动过去多久。

下面是原型读取的实验性收尾记录，不是已发布的通用 schema：

```json
{
  "provider": "codex",
  "session_id": "resumed-after-closeout",
  "state": "closed",
  "covers_through": "2026-10-24T20:00:00Z"
}
```

原型用主机、工具和原生 session ID 区分身份，再将 `covers_through` 与最新活动时间比较。上面的记录虽然写着 `closed`，如果会话后来继续活动，显示结果就会变成 `needs_closeout`。没有明确记录时显示 `unknown`，不会从“闲置很久”推断为已经收尾。

以固定时间运行六条合成会话，CLI 实际输出如下；`local` 是样本的默认主机标识：

```text
SESSION                                  CLOSEOUT        STALENESS
local/claude/open-old                    open            2d 0h · stale
local/claude/legacy-no-closeout-record   unknown         1d 2h · stale
local/claude/closing                     closing         2h 0m · fresh
local/codex/closed-recent                closed          30m · fresh
local/codex/resumed-after-closeout       needs_closeout  5m · fresh
local/codex/archived-source-unavailable  unknown         unknown
```

收尾状态与闲置时间是独立的。刚恢复的会话可能需要重新收尾，已经收尾的会话也可以很久没有活动。来源不可读、时间无效或记录尾部不完整时，原型保留未知值。它信任输入的时间和回执，因此只是状态显示器，不能证明收尾内容充分，更不能证明业务任务完成。

## 当前做到哪里，下一次验证什么

截至 2026 年 10 月 25 日，五步 SOP 已有手工使用记录，历史样本评估已完成；只读状态原型可以输出 CLI 表格、JSON 和静态 HTML，本次重新运行的 11 项测试全部通过，输入包含合成会话和原生格式的合成记录。

完整自动收尾还没有跑通：真实收尾流程尚未自动发布回执，原型尚未接入真实历史扫描，没有部署常驻界面，也没有接上长期知识的自动接收链。中立执行机制和合并授权约束已有方向，完整实现与验收仍是后续工作。收尾请求本身也不自动授予合并或部署权限。

下一步先用受控的真实样本验证状态与证据覆盖，再比较加入离线检查器后，是否真的减少错误结论和交接缺项。还需要让一个没有参与原对话的新会话，只凭留下的任务、SOP 和证据完成接手，才能评价知识是否真正变得可复用。目前没有可靠的耗时、token 或接手成功率基线，不写节省比例。

我希望下一次遇到同类问题时，agent 能找到适用的方法、读到它的依据，知道什么时候该重新验证。Session closeout 为这件事留下入口，知识能否在下一次工作中发挥作用，还要由下一次使用来检验。
