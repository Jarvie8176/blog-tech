_把 AI 当作流体，用需求、约束和验收塑造实现。_

把 Homelab 的配置、脚本和维护工作交给 AI，变化很快就会体现在 GitHub 上：要检查的实现、要确认的设计、要处理的 PR，一起增加了。

AI 可以同时推进几个任务，人却仍然需要判断它们做得对不对。如果每一份改动都等着我逐行阅读，编码节省下来的时间，很容易又花在审阅上。原本想减少维护负担，结果自己成了整个系统的审阅队列。

当实现能力越来越充足，人应该在哪里投入判断，项目又应该在哪些地方停下来？

我更愿意把 AI 看成一种**流体般的智能体**。给它一个大致方向，它能探索、补全、连接，并把许多实现细节填起来。我需要做的，是逐步打造一副“模具”：明确需求、设计意图、接口、不能破坏的约束，以及怎样判断成品合格。然后让 AI 在其中自行填充、“注塑”，再通过审计和使用打磨边角。

这里的模具也需要迭代。实现出来的东西可能暴露原先没有想到的需求，验收可能证明一个设计方向不合适。管理这套流程，就包括决定什么时候继续打磨，什么时候应该重新开模。AI 也很容易把空白补成更多功能、抽象和流程，所以我还需要判断：这副模具是否正在变得比实际需求更复杂。

## 先把模具做成可以工作的约束

在 Homelab Ops 中，模具分散在几个彼此连接的地方。

Issue 说明需要解决的问题和完成条件，epic 组织相关任务，设计文档说明系统如何拆分，接口约定组件怎样交换信息。PR 固定一组具体改动，CI 检查能够机械判断的要求，运行记录和验收结果说明它最终做了什么。

这些材料需要互相对得上。一个需求如果只留在聊天里，下一轮实现就可能丢掉它；一个接口如果文档写着一种含义、代码接受另一种含义，后续组件就会沿着不同的理解继续生长。

模具也需要分清哪些地方可以自由发挥。用户界面的文案和布局，可以通过原型讨论；数据应该写到哪里、一个动作可以影响哪些对象、失败后如何恢复，则需要更明确的边界。能写成程序检查的约束，就让程序检查。需要语义理解和取舍的部分，再让 AI 或人判断。

我希望得到的产物，是一套别人能够继续使用的工作条件：知道目标、输入、允许的变化和验收方式，就可以接着推进。

## 这和“向 AI 许愿”有什么区别

一句“审计 PR #xxx”可以很短，因为 PR 已经指向改动、关联需求、设计说明和检查结果。模型还可以自己查上下文、选择方法、补充测试。简短的是这次委托，不代表整个工作过程没有需求和约束，也不要求人提前把所有细节写成完美规格。

我所说的“向 AI 许愿”，是提出一个期待之后，只凭它回答“已经完成”就接受结果。这里的工作则会留下可检查的东西：PR 固定改动，复现和测试检验行为，多轮对抗审计寻找遗漏，实际使用继续提供反馈。如果证据不足，就继续调查；如果发现需求理解错了，就修改需求或重新设计。模型的完成报告也是需要检验的主张。

“模具”也不是人先独力造好，再交给 AI 执行。AI 可以帮助发现需求、比较方案、形成约束，并把问题推进到能够作决定的程度。我需要理解的是：现在究竟在决定什么，哪些需求已经确认，接受这项取舍会改变什么。无法确认的需求要继续发现，不能靠更多实现把不确定性盖过去。

所以，用 token 和电费交换的是分析、实现与反复检查的劳动；目标和效果仍然通过决策与使用反馈不断校正。这个过程允许起点模糊，但需要让模糊逐步变成能够确认的需求和能够检验的结果。

## 多 agent 对抗审计，先让 AI 找 AI 的问题

实现可以并行，审计也可以。对于值得深入检查的改动，我会让多个 agent 从不同角度寻找反例：并发、资源消耗、权限与数据暴露、错误恢复，或者接口的生产者与消费者。

实际使用时，我不需要把这些角度逐项写成指令，通常只说一句：**“审计 PR #xxx。”** 选择审计视角、拆分任务、阅读源码、寻找触发条件、运行复现，再汇总和裁决，都是可以交给模型处理的脑力劳动。需要具体的是它带回来的问题和证据，任务入口可以很简短。

我愿意这样做，是因为上游云端大模型已经吸收了足够多的最佳实践、设计模式和踩坑经验，迭代速度和推理能力也已经足够胜任我的这些任务。在自己的实践中，它们能够满足需求，所以我选择把复杂度交给模型，用 token 和电费交换脑力劳动。这里的依据是当前用途中的实际效果；仍然要用审计结果和使用反馈判断它有没有做好。

目标是让模型通过多轮对抗审计逐步填补缺口，再把使用过程中遇到的问题反馈到下一轮。人把精力放在**理解决策点和确认需求**上：为什么需要这个变化，哪些取舍值得接受，实际结果是否符合用途。

不同 agent 的结论还需要汇总、去重和裁决。一次照片缓存审计中，一个审计者认为并发损坏已经被排除，另一个却认为问题存在。主线程实际运行复现，确认写入时存在文件被截断的窗口。决定结果的是触发过程与观察到的行为。

发现的问题可以按 P0 到 P3 排出修复优先级。下面是审阅时采用的工作口径，具体级别仍要结合影响范围和发生条件判断。

| 级别 | 重点判断                                       | 处理方式                       |
| ---- | ---------------------------------------------- | ------------------------------ |
| P0   | 是否会造成严重、难以恢复的损坏，或突破关键边界 | 停止相关推进，先限制影响并修复 |
| P1   | 是否阻断核心功能，或让重要的运行与恢复承诺失效 | 在相关阶段放行前解决           |
| P2   | 是否在具体条件下出错，影响可靠性、兼容性或维护 | 结合本次验收决定修复或明确跟踪 |
| P3   | 可读性、呈现和局部维护上的改进                 | 避免淹没关键问题，按价值安排   |

这不是让审计者凑齐四种级别。每个 finding 都应该带着证据来；无法复现的担忧可以保留为待核实项，不必包装成已经确认的缺陷。

修复以后也要复审。修改可能只覆盖了一个触发条件，也可能引入另一种错误。与此同时，检查工具本身也会出错：检查了旧版本、连错预览服务、没有收集到新样本，都可能给出错误结论。因此，审计者需要证明自己检查的是哪个版本、哪些对象，以及测试确实能够发现目标错误。

多人同意，能够提供线索；独立的反例和运行证据，才让结论更容易判断。目前这些方法已经在多个任务中使用，统一的审计 SOP 和工具化仍在继续整理。

## 给 AI 自动增长的复杂度设限

AI 降低了生成代码和文档的成本，也让系统更容易长出额外结构。一次局部修改，可能带出通用接口、配置层、插件机制、迁移工具和一套新的管理流程。每一项都能解释用途，组合起来却可能超出这个 Homelab 真正需要承担的事情。

把分析的复杂度交给云端模型，并不意味着要把它全部固化成系统里的框架、配置和审批步骤。一次审计中的探索，可以消耗 token 后结束；留下来的组件和流程，却会继续产生维护成本。

这些复杂度需要持续维护。新增一个组件，就要考虑部署、升级、故障定位和恢复；新增一个配置项，就多了一种需要理解和验证的行为；新增一个审批步骤，也会占用人的注意力。AI 能帮忙维护它们，但理解、接手和更换工具的成本仍然留在系统里。

因此，审阅一份设计时，我还会问几个问题：

- 新增的结构解决了哪个已经出现、或有明确依据即将出现的问题？
- 现有组件和更简单的实现能否满足这次需求？
- 为此增加了哪些运行依赖、维护步骤和需要人理解的概念？
- 如果暂缓或删除这一层，会失去什么实际能力？

共用操作基座的设计就做过这样的取舍：复用已有分发设施，并明确拒绝另造一套跨工具的配置转换和代码生成框架。所需的是让不同工具找到并调用共用操作，没有必要把潜在的扩展能力全部提前建出来。

多 agent 审计同样需要控制范围。审计者可以不断提出可能的边界条件和更精细的实现，但每个建议都要回到实际影响、发生条件和本次目标。数据完整性、权限、恢复和核心行为值得深入；局部命名、尚无使用者的扩展位、纯偏好的实现替换，可以按维护价值安排，避免把交付变成无限打磨。

我会为当前阶段约定审阅的结束条件：阻塞问题已处理，约定的验收满足，剩余风险和后续事项有明确去处。出现新的重要证据时再继续检查。这样既能保留必要的细节，也能防止审阅在低价值问题上反复展开。

模具本身也有成本。我希望持续减少的是不必要的依赖、分支和人工协调，让新增的复杂度有具体用途，并允许那些已经失去用途的部分被简化或移除。

## 让项目推进到决策点

有了明确目标和允许范围，AI 应该能够连续完成一段工作：查现状、补资料、提出方案、实现、测试、修复，再把可审阅结果留下来。每完成一条命令就回来问“是否继续”，会把项目切成大量没有价值的等待。

我希望人接到的是需要取舍的问题。例如，下一步是否会扩大数据暴露范围，是否需要改变已经接受的接口，是否要增加长期运行成本，或者是否准备执行会影响现有服务的变更。

为了做到这一点，项目需要把工作状态说清楚。哪些需求已经确认，哪些步骤只是实现细节，哪些任务被别的工作阻塞，哪些动作必须等一次决定，都应该能从 tracker 找到。一个后续任务可以先建好并标明阻塞条件，依赖没有满足时保留在队列中。

到达决策点时，AI 应该带回足够让我选择的材料：观察到了什么，有哪些可行方案，推荐哪一个，代价是什么，接受后会解锁哪些工作。如果发现的是实现缺陷，而且修复仍在原来的目标与授权范围内，就应继续解决。

这是我希望提高的项目推进能力。不同工具的持续执行、授权和任务恢复能力并不一致，具体推进范围仍要在当次任务中落实。需要先做完能够独立完成的准备工作，把人的注意力留给真正需要改变方向的地方。

## 需求发现，决定要不要重新开模

一份描述清楚的任务，也可能建立在错误理解上。AI 能很快把这个理解实现出来，速度越快，越值得尽早拿出东西确认。

Homelab 的监控页面就发生过这样的偏差。“glance”既可能指一个独立门户，也可能指 Grafana 里的一个看板。一次任务先改了门户，后来明确的需求却是：在 Grafana 的告警概览里，动态汇总其他看板中需要关注的内容。随后需要撤回无关修改，并围绕实际页面重新组织实现。

这个问题在写代码之前就已经存在。需要先确定：用户从哪个入口进入，想完成什么判断，目前缺少什么信息，以及什么结果算有帮助。名字相同、实现容易，都不足以说明任务已经被理解。

还有一些问题，要到使用之后才会暴露。摘要推送系统曾遇到流入量超过消息窗口排空能力的情况。继续增加消息数量，可以缓解局部积压，却会让阅读负担继续增长。后来的设计把通知面、完整数据和下钻阅读分开，重新讨论摘要怎样组织、哪些内容必须显式出现、反馈应该指向什么对象。

这就是 requirement discovery，需求发现。用户反馈、原型和运行数据，不断补充最初的任务描述。发现方向不合适时，需要回到需求和设计，接受已经做过的一部分实现可能要被替换。

## 用 spike 和最小贯通实验决定是否正式推进

重新设计不需要立刻投入完整实现。关键假设不确定时，可以先做 spike：用很小的实验，回答一个会改变后续路线的问题。

在为 GitHub 写操作增加会话来源标记时，早期实验需要确认：现有 CLI 的各种正文输入方式能不能被正确处理，重复编辑会不会产生多份标记，没有显式正文的命令会不会被改变含义。

只在替身程序上测试还不够。接到真实 CLI 后，实验发现了一种危险行为：清理旧尾注的逻辑，可能把尾注之后的有效正文一起吞掉。这个缺陷涉及实际内容的保存，远比“标记是否成功出现”更值得先解决。

因此，我会把推进过程拆开来看：

1. **Spike**：固定关键疑问，用最小实现寻找可行或不可行的证据。
2. **最小 E2E**：让一个有代表性的输入经过真正的入口，走到实际输出，并从接收侧回读。
3. **正式推进**：根据结果接受、调整或放弃路线，再安排完整实现、部署、监控与业务验收。

实验的结论也要保持范围。成功调用一次 API，可以证明这条调用路径可行；它还没有回答持续运行、升级、恢复和多人使用的问题。反过来，一个足以否定关键假设的实验，也值得让项目停下来。

我希望先得到能帮助决策的结果，再决定模具是否值得继续完善。

## Gated decisions，让阶段之间有明确的门

让 AI 自动推进，需要知道它在哪里必须停下。Gated decision，就是把后续动作与明确的决定或验证条件关联起来。

这些门可以有不同作用：设计门确定方向与取舍，接口冻结门确认组件之间的约定足够稳定，发布门决定哪组改动可以进入运行环境，验收门判断运行结果是否达到当初的要求。

人的决定与程序检查可以配合，但各有职责。一个 CI 通过的接口，仍可能遗漏调用方需要的字段。一次设计审阅接受了方案，也还没有替节点完成部署，更没有替用户确认使用效果。

Homelab 的接口冻结讨论就遇到过这种情况：测试始终通过，但对抗审计继续发现字段含义、必填条件和文档之间的偏差。需要从真实实现中抽取输入输出，逐项核对生产者和消费者，再决定何时让其他组件固定依赖它。

一扇有用的门，需要说明它保护什么、用什么证据放行、由谁作决定，以及放行后能够做什么。只写一句“需要批准”，却不绑定当前版本、目标和具体动作，很容易让不同参与者批准不同的东西。

授权工具也需要接受这类检查。已有 token 或确认框，并不能单独证明批准来自正确的人、覆盖正确的参数，或者能在恢复任务后继续正确使用。这些能力应当按实际交付程度描述，不能用一个“有 gate”概括全部。

门设置在有意义的边界上，才能同时减少无谓打断和未经判断的推进。

## 我不默认逐行读源码，重点审设计和编码意图

如果实现检查已经有 AI 审计和自动测试，人还应该看什么？

对我来说，重点是理解决策点、确认需求，再据此审视设计和编码意图：为什么需要这次变化，为什么采用这条路径，哪些旧行为准备保留，哪些行为会改变，为什么这些验证足以支持结论。

意图需要落到行为上。“增加缓存”只是实现名称；“多人同时请求时，读取者只会看到完整结果，资源消耗有明确限制”，才让审阅者知道应该检查什么。“增加重试”也需要继续解释：重试哪些失败，会不会重复写入，什么时候停止，失败最终怎样被看到。

我不把逐行通读源码作为每份 PR 的默认工作，而是要求 AI 把这组关系讲清楚：**需求 → 设计选择 → 实现位置 → 观察到的结果**。需要核实时，仍然能够沿着证据回到实现、测试和运行状态；影响很大的变更，也可以增加专门的代码或领域审阅。

一份适合我审阅的 PR，应当让我看懂：

- 它解决哪个实际问题，采用了什么方案，为什么接受这些取舍。
- 它新增的复杂度是否值得，有没有能满足同一需求的更简单做法。
- 它会改变什么、影响哪些对象，哪里存在恢复或兼容性成本。
- AI 审计发现了什么，怎样处理，哪些判断还没有收敛。
- 验收检查了哪些输入和行为，还有什么需要由我实际使用后确认。

源码仍然是实现检查的重要对象。变化在于，我把更多精力用来判断模具和产出的关系，同时让能够阅读源码的工具承担实现层的检查。解释很顺、测试很多，都需要回到具体行为上接受检验。

## 验收和反馈，让打磨能够进入下一轮

PR 合并之后，还需要检查它有没有真正进入运行环境，以及用户最终拿到了什么。

照片流程的一次 E2E 工作留下过一个教训：任务完成了有限的传输检查，也如实记录了尚未完成的部分，但在用户检查最终落盘结果之前，把实际传入的测试副本清理了。结果，后续验收和交接失去了原本需要保留的对象。

问题在于没有把整条请求绑定到清楚的终点：选定的资产应该经过哪些阶段，最终保存在哪里，谁还需要检查，什么时候才允许清理。

因此，验收需要从实际用途写起。通知应该从预期的触发器出发，到正确的接收端留下可读消息；照片应该到达约定的位置，能够被后续工具继续使用；一次服务更新需要确认新版本在运行，并且原有数据和功能仍然可用。每一步都要说明检查了什么，以及哪些状态还未知。

反馈也应该有去处。一次实现错误，可以变成回归测试；一个经常被误解的需求，可以补进任务模板或设计说明；不合适的默认行为，可以调整为可配置策略；发现接口本身不适用，则重新打开设计讨论。反复出现的问题，要考虑修改约束和机制，而不只是继续追加提醒。

这也是“打磨边角”的意义。把一次偏差修好以后，下一轮应该更容易得到合适的结果。值得保留的经验，再通过[会话收尾](https://blog.fnpg.me/tech/posts/session-closeout/)进入能够被后续任务找到的记录、方法和验证工具中。

## 让审阅回到需要判断的地方

这套做法不会让 PR 自动消失。设计、实现、部署和后续修订，仍然需要留下可以检查的改动记录。

我更关心的，是系统是否在解决实际问题的同时不断增加维护负担，自己是否还要反复判断同一种低层问题，以及每次需要我决定时，材料是否已经准备充分。需求不清，就先发现需求；关键假设未验证，就先做实验；实现有偏差，就由审计和测试尽早暴露；出现新的取舍，再把项目推进到人的决策点。

人的精力应当集中在理解决策点和确认需求上。模型负责通过多轮对抗审计填补实现中的缺口，实际使用再提供下一轮反馈；我需要判断的是方向、取舍和效果是否符合自己的需要。

把 AI 当作流体般的智能体，意味着我可以给它足够的空间完成工作，也要持续检查模具是否合适。它能够填补实现细节、帮助找错，也能够协助重新设计模具。人需要保留对目标、约束、验收和行动边界的理解，并能在产出偏离用途时介入。

我希望 Homelab Ops 最终形成的是这样的节奏：把需要的形状讲清楚，让 AI 连续推进，用证据检查成品，再把反馈带回下一轮。PR review 太多时，值得重新设计的，可能正是这套让实现汇集到人面前的流程。

## 下篇：秘密泄露怎么办

把实现和运维交给云端 AI，还会带来一个具体问题：服务需要凭据，模型和工具究竟需要看到多少？配置、命令参数、日志和任务上下文，都可能成为秘密流出的路径。审阅再认真，也需要在操作方式上减少不必要的暴露。

下一篇《秘密泄露怎么办》会介绍 Homelab 自用的 `envctl`、提供公钥加密能力的 [age](https://github.com/FiloSottile/age)，以及管理加密配置文件的 [SOPS](https://getsops.io/docs/)，说明它们如何分工，让凭据以密文保存、在需要时供进程使用。文件加密并不意味着运行中的程序或输出无法泄露秘密；接下来也会讨论如何确定影响范围和凭据使用方，以及撤销、轮换与恢复服务时需要作出的决定。
