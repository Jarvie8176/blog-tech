_把运维交给 AI 以后，凭据如何保存、进入进程、出现在输出里，以及泄露后怎样撤销和恢复，都需要有明确的责任与验证方式。_

在[上一篇](/posts/pr-review-too-many/)里，我讨论了 implementation 不再稀缺时，怎样重新分配人类判断、机器执行、工程验证和项目决策之间的责任。凭据管理让这个问题变得很具体：AI 可以帮我部署服务、排查认证错误，背后却可能接触能够操作整套环境的 token。

我希望服务能够使用需要的凭据，正常操作尽量不把值复制进对话和日志。发生暴露以后，还要知道它能做什么、谁在使用，以及怎样让旧凭据失效并恢复服务。保存一份加密文件，只完成了其中一段。

## 一次排障为什么变成了多处轮换

2026 年 6 月的一次排障中，`docker inspect` 的环境变量输出把部署控制器使用的共享 GitHub PAT 带进了对话记录。PAT 是 personal access token，持有者可以在它的权限范围内访问 GitHub；当多个节点共用一份 PAT 时，撤销也会同时影响这些节点。

随后，轮换脚本又引入了故障：它覆盖了一份还包含其他参数的配置文件，把部分节点的 token 写到了错误的变量名下，并因为没有匹配到几种预设错误而给出了成功判断。服务恢复需要分别修复这些问题，后来相关脚本修复也合入了仓库。

这段经历把几件工作连在了一起：减少排障输出中的秘密、找全共享凭据的消费者、保护配置里的其他字段，以及证明新值确实在工作。一次轮换会改变系统状态，它本身也需要设计和验收。

这里记录的是历史暴露与恢复过程。凭据进入对话记录已经构成需要处置的暴露，是否被第三方滥用则需要另外的证据；当时恢复成功，也不能说明今天所有后续硬化都已完成。

## 服务需要凭据 模型需要什么

一次操作至少涉及几个不同位置：模型收到的上下文、agent 发出的工具调用、本地执行的进程、凭据存储，以及目标服务。

模型可以围绕“哪个服务、哪个凭据引用、允许执行什么、怎样检查结果”组织工作。真正的值由获准的本地工具读取，交给需要它的进程。工具返回给模型的，可以只是动作结果和必要的错误分类。

这个分工需要落实到执行和输出上。如果读取命令把 token 打到终端，工具结果仍然会带着它返回；如果业务命令把认证头展开成命令参数，值又进入了另一个可观察的位置。把输入文件加密，并不能约束这些后续行为。

还要区分流程约定和权限隔离。agent 如果拥有同一用户下的任意 shell、解密权限或 Docker 管理权限，就可能绕过正常流程读取秘密。1Password 的环境注入文档也明确提醒，应当假设同用户运行的进程能够访问彼此的环境。更强的隔离需要单独的账户、受限执行入口和权限检查来落实。[1Password 环境注入说明](https://www.1password.dev/cli/secrets-environment-variables)

## 这套凭据栈解决什么 为什么这样选

最初的问题是凭据散落在各处：一份在节点配置里，一份在脚本环境中，另一个消费者又记住了旧值。需要轮换时，很难确认该改哪里。

我已经使用 1Password，因此沿用它维护凭据的权威记录，再把值投影到具体消费者需要的位置。这里的“投影”是按用途生成的派生副本；修改来源以后，还需要更新副本，并确认服务真正使用了新值。在 1Password 编辑一个字段，也不会替目标服务签发或撤销 token。

另一项需求是让配置能够进入 Git 和 PR。SOPS 管理加密配置，支持 ENV、YAML 等格式；age 提供其中一种公钥加密后端。recipient 是允许解密这份文件的接收者配置，对应私钥则由需要解密的节点或操作者持有。这个组合适合已有的文件与 Git 工作流，同时需要维护密钥、接收者和恢复入口。变量名及部分元数据仍可能可见。[SOPS 文档](https://getsops.io/docs/) · [age](https://github.com/FiloSottile/age)

几种路径各有适用条件。直接维护节点上的明文 `.env` 很容易接入现有程序，但副本与更新责任会散开。`op run` 可以在运行时从 1Password 取值，适合能够接受这项依赖的操作。对于需要使用已保存凭据的常驻任务和部分故障处理，我希望减少每次执行都实时访问 1Password 的要求，因此保留本地加密载体。

| 需求                     | 采用的组件        | 留下的工作                               |
| ------------------------ | ----------------- | ---------------------------------------- |
| 集中维护凭据记录         | 1Password         | 管理权限、有效期、消费者和服务端签发状态 |
| 配置加密并进入版本管理   | SOPS + age        | 维护 recipient、私钥、恢复办法和历史副本 |
| 编辑、备份和注入本地载体 | envctl + bakctl   | 保持命令兼容，检查读写、恢复和输出行为   |
| 为部署生成服务级配置     | envsync + doco-cd | 更新 carrier、交付、部署并验证实际生效   |

我把这种加密配置副本称为 carrier，也就是供消费者使用的载体。`envsync` 从 1Password 生成服务级 SOPS carrier，doco-cd 在部署时解密并完成 Compose 插值。这个环节消费已经交付的文件，减少了实时读取 1Password 的依赖；Git、镜像和网络等其他依赖仍要分别管理。载体也可能过期，所以更新来源、生成配置、部署和业务验证需要逐步确认。

部署控制器自己的启动凭据还有 bootstrap 问题：它先要取得 Git 访问能力，才能拉取后续部署输入。现有路径为此保留了单独生成、限制文件权限的主机本地明文配置。这一例外也属于需要管理的系统现状。

## envctl 怎样把组件接起来

`envctl` 最初是这套 Homelab 的自用 dotenv 工具，现在已有独立的[公开仓库](https://github.com/Jarvie8176/envctl)和 [v0.1.0 发布](https://github.com/Jarvie8176/envctl/releases/tag/v0.1.0)。它把编辑、SOPS 调用、备份和进程执行连接起来，与文件快照工具 `bakctl` 配对分发。1Password 接入和节点分发由外部工具承担，原有节点迁移到公开版本也需要分别验收。

![凭据栈与 envctl 逻辑组件：1Password 和 envsync 提供服务级载体；envctl 连接配置、键值编辑、存储、SOPS、bakctl 与进程执行](/images/secrets/components-zh.png)

_逻辑职责示意。envctl 的相关实现目前集中在一个脚本中；图中的分组不代表已经拆成独立模块或服务。_

| 逻辑组件                | 负责什么                                           |
| ----------------------- | -------------------------------------------------- |
| CLI 与配置              | 选择命令、目标文件、SOPS 程序和密钥配置            |
| Document                | 查找与修改键值，保留其他行，处理重复写入           |
| Storage 与 SOPS adapter | 读取、加密、解密和替换文件；明文通过子进程管道传递 |
| Backup adapter          | 调用 bakctl 保存快照、查看历史与恢复文件           |
| Runner 与 Output        | 将变量注入进程，或按命令输出键名、值               |

当前默认目标仍是 `~/cc/.env`，只有文件名以 `.enc` 结尾才自动走加密路径。示例会显式指定 `service.env.enc`。服务级部署 carrier 常采用另一种命名，由 SOPS 和 doco-cd 消费，不能只看到文件名里含有 `enc` 就假定 envctl 会解密它。

`exec` 会继承父进程环境，并注入所选文件的全部变量。按用途拆分载体，可以减少交给一次业务操作的内容；它还没有逐命令变量白名单。`get` 和 `export` 会主动输出值，`list` 只输出键名。运行涉及秘密的任务时，通常应让业务进程直接消费，而不先把值取回来交给模型。

加密写入的临时文件保存的是密文，bakctl 对加密目标保存的也是密文快照。这减少了这条工具路径主动生成的明文副本；子进程、日志和其他程序是否写出秘密，仍要分别控制。

## 从空条目到一次带凭据的执行

下面用一个假想服务 `demo-service` 说明我希望固定下来的工作方式。工具已有的能力包括条目创建、引用读取、envctl 的 stdin 写入和 `exec`。导入前校验、失败保护与输出筛选还需要封装成受控入口，并用合成数据完成贯通验收。

![创建和注入凭据的五步流程：agent 准备基础环境并建立空条目，人在 1Password 填写，受控本地工具校验后写入密文，再通过 envctl 执行业务命令](/images/secrets/use-case-zh.png)

_目标流程。值由本地工具处理，模型获得引用与结果；这条正常路径本身不建立同权限 agent 的隔离边界。_

### Agent 准备基础环境

在获准节点上准备 `op`、SOPS、age 工具和配对的 envctl/bakctl，核对实际执行路径与版本。在本机生成或复用 age identity，配置 recipient 和文件权限，再用合成值检查加密与解密。

首次访问 1Password 也需要已有认证。服务账号或其他引导凭据沿授权的控制面准备，私钥和 token 都不作为检查输出返回。`age-keygen` 用于建立密钥身份；envctl 的加密读写实际调用 SOPS，由 SOPS 使用 age 后端。

### Agent 建立条目 stub

Agent 在指定 vault 创建空条目，填写服务名称、用途、消费者和需要用户填写的字段。秘密字段保持为空，返回给人的只是条目链接与字段说明。1Password CLI 提供类别模板和条目创建接口，可以据此完成准备工作。[条目创建说明](https://www.1password.dev/cli/reference/management-commands/item)

例如，这次任务约定一个 `credential` 字段，后续引用写成 `op://demo-vault/demo-service/credential`。这是示意引用，不对应真实条目。stub 存在只说明准备工作完成，不能推断凭据已经填写或可用。

### Human 在 1Password 填写凭据

用户在服务端取得适当权限的凭据，直接填入 1Password，并确认用途、权限范围和有效期。对话中只需要通知“已填写”。需要调整权限或申请更大范围的 token 时，把这个选择留在人的决策点。

### Agent 触发本地校验与加密导入

调用参数只包含引用、目标 key 和载体路径，例如把上述引用映射到 `DEMO_API_TOKEN`。受控导入进程读取值，确认读取成功、字段存在、非空且符合约定格式，才经 stdin 交给 envctl 写入 `service.env.enc`。值不需要进入命令参数、shell 展开或工具返回。

这里需要有明确的失败顺序。直接把 `op read` 接到 `envctl set`，上游失败时，下游仍可能先把空输入写进去；`pipefail` 只能让整条管道报告失败，不能撤回已经发生的写入。导入器应在读取与校验成功后才调用写入。公开版 v0.1.0 已会对候选密文做解密回读检查，再原子替换目标；这项保护与上游非空检查分别负责一段，不能互相替代。[公开版安全边界](https://github.com/Jarvie8176/envctl/blob/v0.1.0/docs/security-model.md)

这个封装还应关闭命令跟踪，只返回 key、状态和必要的错误分类，不原样回传响应、异常或秘密哈希。重复导入相同值也不应产生无意义的更新。

### Agent 通过 envctl 执行业务命令

调用形式如下，`service_check.py` 表示需要另行准备的业务检查脚本：

```bash
envctl --file ./service.env.enc exec -- python3 service_check.py
```

业务脚本在进程内读取 `DEMO_API_TOKEN`，组成认证请求，并只返回约定的状态字段。若又把环境值展开成 `curl` 的认证参数，或者开启完整请求日志，前面减少的暴露就会从另一个出口回来。

机械化的验收可以用合成 canary，也就是一段只用于测试的可识别字符串。检查正常、读取失败、空字段、错误 key 和业务失败时，stdout、stderr、参数与产物是否带出样本值，同时确认旧载体在失败后保持不变。这样的测试检查指定路径，完整隔离仍需要另外的权限边界。

## 怀疑泄露时先确认对象与范围

面对暴露，首先限制继续输出和复制，再确认泄露的对象、权限、时间与可能持有副本的位置。几种秘密需要不同的处置。

| 暴露对象          | 需要处理什么                                                               |
| ----------------- | -------------------------------------------------------------------------- |
| 业务 token 或密码 | 在签发服务撤销、重新签发或改密，更新消费者，检查旧访问是否失效             |
| age 解密私钥      | 识别它能够解密的载体与历史副本，替换解密身份，再处理其中可能暴露的业务凭据 |
| SOPS 文件数据密钥 | 确认关联文件，更新数据密钥和访问配置，并评估文件里的秘密                   |
| 已输出的私密内容  | 处理保留、访问和删除范围；轮换凭据无法收回已经获知的内容                   |

SOPS 的 `updatekeys` 调整接收者，`rotate` 更新文件数据密钥，两者都不会撤销业务 token。移除受损身份并更新数据密钥后，再保存新的业务秘密；旧密文与已知明文仍无法收回。[SOPS 密钥管理](https://getsops.io/docs/usage/key-management/)

若暴露发生在 Git 中，删除最新版本里的字符串也不会撤销凭据。需要先在服务端处置访问，再按敏感内容和传播范围安排历史、克隆、缓存及其他副本的清理。[GitHub 敏感数据处理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

## 撤销 轮换与恢复需要怎样的证据

处置顺序取决于紧迫性。如果发现正在被利用，或者暴露的是高权限访问，应优先限制访问并接受必要中断。能够受控切换、且服务支持新旧凭据短暂并存时，可以先部署新值、验证消费者，再撤销旧值；需要给重叠期设定明确边界。

消费者清单包括仓库引用，也包括运行中的容器、定时任务、外部节点和人工维护的位置。按变量名搜索可以给出线索，搜索无结果不能证明没有使用方。还要保留轮换所依赖的管理与恢复入口，避免把自己唯一的访问身份一起撤掉。

验收需要同时回答几个问题：新凭据是否能执行所需动作，权限是否符合预期；旧凭据是否按服务语义失效；所有已知消费者是否恢复了实际功能；原有配置是否完整；排障输出是否继续暴露秘密。已有会话、派生 token 与缓存授权也应按服务的撤销语义分别核对。

一次 HTTP 成功不能覆盖这些结论。容器健康不等于能够拉取代码，文件写入成功不等于进程加载了新值，某条请求失败也可能是目标或网络有误。需要保留检查的版本、对象和动作结果，同时避免为了证明成功而再次输出秘密。

## 当前实现与下一步

截至 2026 年 10 月 26 日，envctl/bakctl 已用于这套环境，envsync 和服务级 SOPS carrier 也已有实现。公开 v0.1.0 增加了候选密文回读、写入互斥与输入检查，并以临时 identity 和合成值覆盖加密路径。工具仍保留明文默认值、整份选中文件的环境注入和 get/export 的值输出；部署引导还存在受权限控制的明文配置。

通用的 1Password 到 envctl 安全导入入口、五步 use case 的贯通验收、运行时凭据隔离和部分轮换后续仍需补齐。公开首版的发布元数据清理、原有安装迁移与实际节点验证也仍在跟进。已经有公开工具包，不意味着旧节点已经升级，也不能替代业务凭据的生效与失效检查。

我希望沉淀下来的，是能够检查的责任链：人确认用途、权限和中断取舍；agent 在授权范围内准备和推进；本地工具处理值与执行；验证检查真实生效和失效；[会话收尾](/posts/session-closeout/)留下脱敏的结果、遗留与方法。这样，下一次需要凭据时，可以复用已经检查过的路径，也能够知道哪一段还需要继续改进。
