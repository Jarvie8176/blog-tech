_设计从凭据可能被读取、复制和传播出发：尽量减少暴露，并让不可避免的轮换范围和恢复成本可控。_

2026 年 6 月的一次排障中，`docker inspect` 的环境变量输出把部署控制器的共享 GitHub PAT 带进了对话。后续轮换又覆盖了其他配置、写错了部分变量名，并误报成功。它同时暴露了读取、凭据共用和变更验收三个问题。

这篇保留事故与修复取舍。工具的选型、组件和目标流程移到[下一篇 envctl 的设计与边界](/posts/envctl-design/)。

## 按每份凭据都会暴露来设计

这里对秘密保存采取 zero trust 的设计前提：先假设每份凭据都会暴露，不能把“值会一直留在保险箱里”当作可靠性承诺。加密仍然重要，但程序要使用凭据，就会出现可被读取的时刻。对话、日志、配置副本和知识沉淀还会扩大传播范围。

因此，需要一起优化四件事：**暴露机会、单份凭据的权限与寿命、传播范围、轮换成本**。禁止所有探索性读取，会损失排障能力；每次普通检查都轮换全部凭据，也会制造中断和新的变更风险。应让常规检查尽量不接触值，让高权限例外有边界，并能找全需要撤销与更新的对象。

共享 PAT 正好放大了成本：撤销一个值，会同时打断多个节点。清单只能帮助找全消费者，按节点或服务拆分、限定仓库和只读权限，才能缩小一次撤销的范围。单仓库可以评估独立 deploy key，HTTPS 可以评估细粒度 PAT，多仓库长期集成可以评估 GitHub App；分别承担密钥管理、用户绑定或短期 token 签发的成本。[GitHub 认证选项](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys)

截至 2026 年 10 月 26 日，现有轮换路径仍围绕共享 PAT，不能宣称按节点拆分完成。验收应实际撤销一个节点的凭据，确认其他节点仍能拉取；只看新配置已写入是不够的。

## 先减少最容易发生的无意暴露

完整隔离需要时间，也可以先加便宜的保护。下列措施是下一轮落实与验收的方向，不能读作已部署完成。

**执行前拦截。** 在 agent 工具入口拒绝裸用 `docker inspect`、`env`、`printenv`、读取 `.env` 的命令，以及 `envctl get/export` 等常见值输出操作，提示改走受限检查。组合命令、脚本、别名或其他 API 都可能绕过它，因此它用于减少误操作；仍值得用合成秘密测试“这次这种命令”是否会在执行前被挡住，不能因为不构成强制隔离就跳过。

**减少环境变量中的秘密。** Compose 的 `secrets:` 可按服务授予文件，挂到 `/run/secrets/...`，让应用直接读取文件，不再把值放进容器环境。这样常规 inspect 的环境字段就不会包含该值。`_FILE` 是应用约定，需要确认目标版本支持；把文件重新读进环境再启动应用，会重新引入环境泄露路径。[Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

doco-cd 的文档提供 `GIT_ACCESS_TOKEN_FILE`，与直接的 token 设置互斥。迁移时应核对运行版本，移除原环境值，确认实际拉取成功，并用合成数据验证 inspect 不含样本值。现有部署声明里，其他秘密已用文件挂载，Git token 仍走环境变量；本次文章重构没有改变这些部署。[doco-cd Git 设置](https://doco.cd/latest/Git-Settings/)

普通 Compose 的文件型 secret 是文件挂载，并不自动加密宿主机源文件。bootstrap 的本地明文仍要管理权限和生命周期，主机 root 或 Docker 管理者也仍可读取。这项改动针对无意转储，不能独自提供秘密隔离。[Compose secrets 参考](https://docs.docker.com/reference/compose-file/secrets/)

**限制返回内容。** 常用 procedure 在本地选必要字段，只返回状态、计数或错误分类；未知输出先保留在受控执行端。返回通道再做检测与脱敏，覆盖 stdout、stderr、异常和产物。检测不能保证识别任意编码或分片后的值，但能够补漏；在内容进入模型后再过滤，已经无法撤回暴露。

## 探索性排障需要升级通道

AI 的价值包括临时看日志、配置和没有预想到的状态。procedure 无法预先覆盖所有故障。独立账户与严格输出契约会缩小探索范围，也会增加等待、封装和人工判断的成本，这项代价需要正面接受。

我希望采用分级路径：常规检查走只返回必要字段的入口；覆盖不足时，先让有权限的人在本地调查并提供去敏结果，或者为这次任务扩展一个受控检查。确实需要 agent 扩大读取能力时，才进入显式批准的临时升级。

批准前需要列明目标、动作、时限、可能读到哪些凭据、输出去向，以及结束后预计要轮换哪些对象。权限由执行端授予并到期回收，入口代码不能由 agent 修改；能保持字段筛选时继续保持。广泛 shell 或 Docker 权限下，若无法证明哪些秘密未被接触，应把授权范围内可读的凭据列入潜在暴露清单，安排重新签发、切换、撤销和验证。轮换成本过高时，也可以决定由人继续调查。

这不是授予一次权限后继续相信值不会外流。对普通 rootful Docker Engine，`docker` 组具有 root 级权限；结束 shell 或恢复账户权限，也不会撤销已经复制的 token。临时升级需要把后续处置和中断预算一起批准，已经发生的高权限暴露则不能为了平滑切换拖延撤销。[Docker 权限说明](https://docs.docker.com/engine/install/linux-postinstall/)

## 对话沉淀也是传播路径

PAT 已经进入对话，这是确定的暴露。它是否进一步进入 closeout、journal、`agent-manifest`、知识候选或检索索引，**尚没有覆盖整条派生链的核对结论**。不能从“记录脱敏了”推断所有副本都安全，也不能从撤销 token 推断私密内容已经消失。

[Yaaa 的规则](/posts/yaaa/)在这里应当落实：派生内容的敏感度至少继承所有实际来源的最高级。摘要、改写和嵌入不会自行降密。[Session closeout](/posts/session-closeout/)应先检查可见会话与工具输出是否出现秘密；检出或无法排除时，将记录及相关派生内容按高敏感隔离，暂停普通归档、云端再处理和长期知识晋升。检测结果要注明覆盖范围，不能把扫描通过当成没有秘密的证明。

复核范围包括原始记录、收尾摘要、journal、知识候选、agent-manifest、索引、同步副本与备份；还要核对当时使用的云端产品、账号策略和可用删除渠道。本地删除不等于提供方保留副本已经删除。核对在可信本地环境内完成，不把旧秘密送入另一个云端扫描器，也不在工单里复写值。

最后保留不含秘密的传播与处置记录：哪些来源和派生对象已检查，哪些受限，哪些删除或等待到期，哪些仍未知。经独立去敏审阅后，只晋升必要的方法和事实。历史 PAT 的这项传播核对、自动敏感标记和晋升阻断，都不能在本文中视为已完成。

## 轮换本身也会制造事故

同年 6 月的 SSH 轮换曾把同类公钥共有的前缀当作旧 key 标识，锁死五台主机；恢复中又因版本切换失败运行旧脚本而复发。它与 PAT 轮换共有的模式是：对象识别不准，实际执行版本和成功判断不可靠。

所以轮换至少要绑定精确的消费者与目标、经验证的脚本版本、dry-run 和受保护的写前备份；先试一个消费者，保留独立恢复入口，再验证新值能完成实际业务、其他配置未损坏，最后按签发端语义确认旧访问失效。缺少成功证据应失败或标为未验证，不能只凭“没有匹配到错误”报成功。已撤销的旧值也不能当作回滚方案。

当前 PAT 脚本已有部分修复，但仍缺完整的统一验收，部分未观察到成功日志的路径仍可能成功退出。更新密文、替换 age 身份或 SOPS 数据密钥，也都不会替业务系统撤销 token。减少每次轮换的消费者数量、让更新可重复且失败不破坏原值，才会降低持续处置的成本。

## 工具交付和风险优先级并未一致

6 月事故之后，10 月完成的是把已有 dotenv 编辑与备份工具整理为独立的 envctl/bakctl 包。这段交付可以在不变更生产权限的情况下，用合成数据检查读写和恢复；它没有修复临时排障读取。实际交付顺序确实与这里提出的风险优先级不一致，开源完成不能作为事故整改完成的依据。

目前没有已确认的生产验收日期。我提出的下一轮验收门槛，是在后续开展广泛的 agent 排障前，先验证执行前拦截、文件型 token、返回筛选与知识传播处置，再演练临时升级的到期回收和轮换。完整隔离、按节点拆分及统一轮换 procedure 仍需单独交付；此前保留受限检查或人工调查路径。

评估进展时，应看一条泄露路径是否减少、一次暴露要轮换多少对象、传播清单是否可追踪、恢复是否可验证。[下一篇](/posts/envctl-design/)说明 envctl 在其中能承担的有限职责。
