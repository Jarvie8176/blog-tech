_把运维交给 AI 以后，凭据如何保存、进入进程、出现在输出里，以及泄露后怎样撤销和恢复，都需要有明确的责任与验证方式。_

在[上一篇](/posts/pr-review-too-many/)里，我讨论了 implementation 不再稀缺时，怎样重新分配人类判断、机器执行、工程验证和项目决策之间的责任。凭据管理让这个问题变得很具体：AI 可以帮我部署服务、排查认证错误，背后却可能接触能够操作整套环境的 token。

这次事故暴露了三个相连的问题：排障输出把秘密带进对话，共享凭据扩大了撤销影响，轮换脚本又破坏了配置。加密文件和安全导入可以改善日常使用，但要防止重演，还需要约束临时排障的读取权限与输出，并把轮换变成可验证的变更。

## 一次排障为什么变成了多处轮换

2026 年 6 月的一次排障中，`docker inspect` 的环境变量输出把部署控制器使用的共享 GitHub PAT 带进了对话记录。PAT 是 personal access token，持有者可以在它的权限范围内访问 GitHub；当多个节点共用一份 PAT 时，撤销也会同时影响这些节点。

随后，轮换脚本又引入了故障：它覆盖了一份还包含其他参数的配置文件，把部分节点的 token 写到了错误的变量名下，并因为没有匹配到几种预设错误而给出了成功判断。服务恢复需要分别修复这些问题，后来相关脚本修复也合入了仓库。

这段经历把几件工作连在了一起：减少排障输出中的秘密、找全共享凭据的消费者、保护配置里的其他字段，以及证明新值确实在工作。一次轮换会改变系统状态，它本身也需要设计和验收。

这里记录的是历史暴露与恢复过程。凭据进入对话记录已经构成需要处置的暴露，是否被第三方滥用则需要另外的证据；当时恢复成功，也不能说明今天所有后续硬化都已完成。

## 先约束排障时能读什么 能返回什么

事故发生在临时读取路径上。即使导入、加密和 `exec` 都正确，下一次 `docker inspect`、`env`、`cat .env` 或 `envctl get` 仍可能把值送进上下文。后文的五步流程改善计划内操作，不能作为这次事故已经得到预防的证据。

要针对事故原因，需要分别处理三个位置：

- **排障入口**：把常用检查封装成 procedure，只接收允许的目标和动作，在本地选取必要字段。例如查看容器是否运行、重启次数，可以只返回布尔值和计数；完整环境、标签、日志和错误文本都不能默认回传。未知输出先停止回传，再由受控入口处理。
- **工具返回**：在 stdout、stderr、异常和产物进入 agent 通道之前，按字段白名单生成结果，再做秘密检测或脱敏。检测能够补漏，但无法保证识别任意格式、编码或拆分后的秘密；过滤已经进入模型的文本也来不及撤回暴露。
- **执行权限**：如果要建立隔离，agent 应使用没有 Docker 管理权限、任意 sudo、业务解密私钥和凭据文件访问权的独立账户，通过受限入口请求操作。入口本身的代码、配置和允许的程序也不能由该账户改写，否则仍可绕过约束。

这里的 Docker 管理权限尤其重要：对常规 rootful Docker Engine，Docker 官方明确说明 `docker` 组授予 root 级权限。只删除某条命令或改成 token 文件，并不能阻止拥有 daemon 管理权的账户读取容器或挂载的秘密。[Docker 权限说明](https://docs.docker.com/engine/install/linux-postinstall/)

模型需要的是服务、凭据引用、允许的动作和验证结果；值由可信执行端交给业务进程。1Password 也提醒，应假设同用户进程能够访问彼此的环境。[环境注入说明](https://www.1password.dev/cli/secrets-environment-variables)

这套环境尚未完成上述排障入口、通道过滤和独立权限边界的整链验收。现阶段仍存在再次输出秘密的路径；它们应优先于通用导入器的完善来处理。

## 共享凭据扩大了影响范围

多个节点共用 PAT，使一次撤销变成多处同步切换。消费者清单能帮助找全更新位置，却不能缩小一份凭据本来的权限和影响范围。现有轮换路径仍按共享 PAT 组织，不能把它描述成已经完成按节点拆分。

对于只拉取单个仓库的消费者，可以评估每个节点、每个仓库使用独立的只读 deploy key；HTTPS 消费者可以评估限定仓库与必要权限的细粒度 token。多仓库、长期集成还可以评估 GitHub App 的短期 installation token。选择要服从部署控制器的认证支持，并逐个验证拉取；deploy key 默认只读但没有自动到期，细粒度 PAT 仍绑定签发用户，GitHub App 则增加签发与续期的维护成本。[GitHub deploy key 与 App](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys) · [细粒度 PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

拆分的验收点是：撤销一个节点的凭据，其他节点仍能完成各自的拉取。凭据数量可能增加，单次泄露与撤销的范围应当缩小；同一特权账户仍能读取所有节点秘密时，拆分也不能提供完整隔离。

部署控制器的 bootstrap 明文配置也没有因此消失。它仍是一个需要限制账户访问、记录消费者和轮换责任的例外。改用 token 文件可减少环境转储中的值输出，但主机 root 或 Docker 管理者仍可能读取它，不能宣称这个例外已经解决。

## 这套凭据栈解决什么 为什么这样选

最初的问题是凭据散落在各处：一份在节点配置里，一份在脚本环境中，另一个消费者又记住了旧值。需要轮换时，很难确认该改哪里。

我已经使用 1Password，因此沿用它维护凭据的权威记录，再把值投影到具体消费者需要的位置。这里的“投影”是按用途生成的派生副本；修改来源以后，还需要更新副本，并确认服务真正使用了新值。在 1Password 编辑一个字段，也不会替目标服务签发或撤销 token。

另一项需求是让配置能够进入 Git 和 PR。SOPS 管理加密配置，支持 ENV、YAML 等格式；age 提供其中一种公钥加密后端。recipient 是允许解密这份文件的接收者配置，对应私钥则由需要解密的节点或操作者持有。这个组合适合已有的文件与 Git 工作流，同时需要维护密钥、接收者和恢复入口。变量名及部分元数据仍可能可见。[SOPS 文档](https://getsops.io/docs/) · [age](https://github.com/FiloSottile/age)

几种路径各有适用条件。直接维护节点上的明文 `.env` 很容易接入现有程序，但副本与更新责任会散开。`op run` 可以在运行时从 1Password 取值，适合能够接受这项依赖的操作。对于需要使用已保存凭据的常驻任务和部分故障处理，我希望减少每次执行都实时访问 1Password 的要求，因此保留本地加密载体。

| 需求                     | 采用的组件        | 留下的工作                               |
| ------------------------ | ----------------- | ---------------------------------------- |
| 集中维护凭据记录         | 1Password         | 管理权限、有效期、消费者和服务端签发状态 |
| 配置加密并进入版本管理   | SOPS + age        | 维护 recipient、私钥、恢复办法和历史副本 |
| 编辑、备份和注入本地载体 | envctl + bakctl   | 保持命令兼容，检查读写、恢复和输出行为   |
| 为部署生成服务级配置     | envsync + doco-cd | 更新 carrier、交付、部署并验证实际生效   |

我把这种加密配置副本称为 carrier，也就是供消费者使用的载体。`envsync` 从 1Password 生成服务级 SOPS carrier，doco-cd 在部署时解密并完成 Compose 插值。这个环节消费已经交付的文件，减少了实时读取 1Password 的依赖；Git、镜像和网络等其他依赖仍要分别管理。载体也可能过期，所以更新来源、生成配置、部署和业务验证需要逐步确认。

部署控制器自己的启动凭据还有 bootstrap 问题：它先要取得 Git 访问能力，才能拉取后续部署输入。现有路径为此保留了单独生成、限制文件权限的主机本地明文配置。这一例外也属于需要管理的系统现状。

### 用复杂度四问检验这套栈

这套设计把散落的副本变成了有来源关系的副本，并没有自动减少副本。一个凭据可能同时存在于 1Password、服务级 SOPS carrier、本地 envctl 文件和 bootstrap 配置中；并非每个服务都需要全部四层。沿用[上一篇的四问](/posts/pr-review-too-many/)，我需要给每一层一个保留或删除的理由。

1. **解决了什么已出现的问题？** 1Password 集中维护记录；SOPS 让配置进入 Git；本地载体支持不实时访问 1Password 的操作；bootstrap 处理控制器首次拉取。它们没有直接解决排障读取与共享权限的问题。
2. **更简单的办法能否满足？** 能接受实时依赖的任务可直接用 `op run`；已有 SOPS 文件、只需要执行的任务可用 `sops exec-env`。没有本地编辑需求时，可以省去 envctl 副本；同一消费者不应仅为“统一栈”再复制一层。
3. **增加了哪些维护责任？** 每个派生副本都要记录来源引用、消费者、生成或部署版本、更新时间、权限和负责更新的入口。核对版本与实际认证动作，不把秘密哈希当作对外证明；来源更新不会自动使运行进程刷新。
4. **删除一层会失去什么？** 删除本地缓存会恢复实时凭据源依赖；删除 envctl 会失去其编辑与快照约定，但 SOPS 仍可注入；删除服务 carrier 会改变部署交付方式。只有确实需要这些能力的消费者才承担相应副本。

目前保留本地载体是对可用性与维护成本的取舍。全量副本清单与过期检查尚未统一，因而不能把“来源关系明确”写成“轮换已经闭环”。后续应逐个消费者合并重复载体，并让更新失败、未部署或仍使用旧值成为可见状态。

## envctl 怎样把组件接起来

`envctl` 最初是这套 Homelab 的自用 dotenv 工具，现在已有独立公开仓库 [Jarvie8176/envctl](https://github.com/Jarvie8176/envctl)和 [v0.1.0 发布](https://github.com/Jarvie8176/envctl/releases/tag/v0.1.0)。它把编辑、SOPS 调用、备份和进程执行连接起来，与文件快照工具 `bakctl` 配对分发。1Password 接入和节点分发由外部工具承担，原有节点迁移到公开版本也需要分别验收。

读者可从仓库的[固定版本安装说明](https://github.com/Jarvie8176/envctl#install-a-fixed-release)取得配对工具，按 [Releases](https://github.com/Jarvie8176/envctl/releases) 核对版本、产物和校验摘要。本文讨论 v0.1.0 的行为；后续版本与安装步骤以公开仓库为准。

已有安装可以按[集成与迁移约定](https://github.com/Jarvie8176/envctl/blob/main/docs/integrations.md)先在独立安装前缀验证，再切换消费者。envctl 与 bakctl 应保持同一发布版本，并核对实际执行文件；更新一个源码 checkout 不会自动更新其他节点上的复制版本。

![凭据栈与 envctl 逻辑组件：1Password 和 envsync 提供服务级载体；envctl 连接配置、键值编辑、存储、SOPS、bakctl 与进程执行](/images/secrets/components-zh.png)

_逻辑职责示意。envctl 的相关实现目前集中在一个脚本中；图中的分组不代表已经拆成独立模块或服务。_

| 逻辑组件                | 负责什么                                           |
| ----------------------- | -------------------------------------------------- |
| CLI 与配置              | 选择命令、目标文件、SOPS 程序和密钥配置            |
| Document                | 查找与修改键值，保留其他行，处理重复写入           |
| Storage 与 SOPS adapter | 读取、加密、解密和替换文件；明文通过子进程管道传递 |
| Backup adapter          | 调用 bakctl 保存快照、查看历史与恢复文件           |
| Runner 与 Output        | 将变量注入进程，或按命令输出键名、值               |

`exec` 并非 envctl 独有的能力。SOPS 原生的 `exec-env` 已能把解密结果交给子进程环境，`exec-file` 可为接受文件的程序提供载体。若需求只有“解密后运行一次”，优先考虑原生能力。envctl 的主要差异在编辑阶段：按 key 从 stdin 写入、保留其他行、候选密文回读、互斥与原子替换，以及配对的备份和恢复约定；它为已有 dotenv 操作提供统一接口，不增加运行时隔离。[SOPS 进程执行说明](https://getsops.io/docs/usage/advanced/#passing-secrets-to-other-processes)

当前默认目标仍是 `~/cc/.env`，只有文件名以 `.enc` 结尾才自动走加密路径。示例会显式指定 `service.env.enc`。服务级部署 carrier 常采用另一种命名，由 SOPS 和 doco-cd 消费，不能只看到文件名里含有 `enc` 就假定 envctl 会解密它。

`exec` 会继承父进程环境，并注入所选文件的全部变量。按用途拆分载体，可以减少交给一次业务操作的内容；它还没有逐命令变量白名单。`get` 和 `export` 会主动输出值，`list` 只输出键名。运行涉及秘密的任务时，通常应让业务进程直接消费，而不先把值取回来交给模型。

加密写入的临时文件保存的是密文，bakctl 对加密目标保存的也是密文快照。这减少了这条工具路径主动生成的明文副本；子进程、日志和其他程序是否写出秘密，仍要分别控制。

这些默认值来自面向人的工具习惯，对 agent 并不保守。v0.1.0 的回读、锁和原子替换加强了**写入完整性**，本次泄露需要补的是**读取与输出约束**。

可评估的 agent 模式应要求显式选择加密文件，拒绝 `get`/`export`，并让 `exec` 只注入声明的变量，同时筛选继承的父环境，避免旧秘密从父环境混入。它还需要限定可执行动作和返回字段；仅给任意程序一份更小的环境，仍不能阻止程序打印值或访问其他秘密。**这些是待实现的接口约束，v0.1.0 没有 agent 模式**；即使实现，强制边界仍依赖独立权限和受控执行端。

## 从空条目到一次带凭据的执行

下面用一个假想服务 `demo-service` 说明我希望固定下来的工作方式。工具已有的能力包括条目创建、引用读取、envctl 的 stdin 写入和 `exec`。导入前校验、失败保护与输出筛选还需要封装成受控入口，并用合成数据完成贯通验收。

![创建和注入凭据的五步流程：agent 准备基础环境并建立空条目，人在 1Password 填写，受控本地工具校验后写入密文，再通过 envctl 执行业务命令](/images/secrets/use-case-zh.png)

_目标流程。值由本地工具处理，模型获得引用与结果；这条正常路径本身不建立同权限 agent 的隔离边界。_

### Agent 准备基础环境

在获准节点上准备 `op`、SOPS、age 工具和配对的 envctl/bakctl，核对实际执行路径与版本。在本机生成或复用 age identity，配置 recipient 和文件权限，再用合成值检查加密与解密。

首次访问 1Password 也需要已有认证。服务账号或其他引导凭据沿授权的控制面准备，私钥和 token 都不作为检查输出返回。`age-keygen` 用于建立密钥身份；envctl 的加密读写实际调用 SOPS，由 SOPS 使用 age 后端。

### Agent 建立条目 stub

Agent 在指定 vault 创建空条目，填写服务名称、用途、消费者和需要用户填写的字段。秘密字段保持为空，返回给人的只是条目链接与字段说明。1Password CLI 提供类别模板和条目创建接口，可以据此完成准备工作。[条目创建说明](https://www.1password.dev/cli/reference/management-commands/item)

例如，这次任务约定一个 `credential` 字段，后续引用写成 `op://demo-vault/demo-service/credential`。这是示意引用，不对应真实条目。stub 存在只说明准备工作完成，不能推断凭据已经填写或可用。

### Human 在 1Password 填写凭据

用户在服务端取得适当权限的凭据，直接填入 1Password，并确认用途、权限范围和有效期。对话中只需要通知“已填写”。需要调整权限或申请更大范围的 token 时，把这个选择留在人的决策点。

### Agent 触发本地校验与加密导入

调用参数只包含引用、目标 key 和载体路径，例如把上述引用映射到 `DEMO_API_TOKEN`。受控导入进程读取值，确认读取成功、字段存在、非空且符合约定格式，才经 stdin 交给 envctl 写入 `service.env.enc`。值不需要进入命令参数、shell 展开或工具返回。

这里需要有明确的失败顺序。直接把 `op read` 接到 `envctl set`，上游失败时，下游仍可能先把空输入写进去；`pipefail` 只能让整条管道报告失败，不能撤回已经发生的写入。导入器应在读取与校验成功后才调用写入。公开版 v0.1.0 已会对候选密文做解密回读检查，再原子替换目标；这项保护与上游非空检查分别负责一段，不能互相替代。[公开版安全边界](https://github.com/Jarvie8176/envctl/blob/v0.1.0/docs/security-model.md)

这个封装还应关闭命令跟踪，只返回 key、状态和必要的错误分类，不原样回传响应、异常或秘密哈希。重复导入相同值也不应产生无意义的更新。

### Agent 通过 envctl 执行业务命令

调用形式如下，`service_check.py` 表示需要另行准备的业务检查脚本：

```bash
envctl --file ./service.env.enc exec -- python3 service_check.py
```

业务脚本在进程内读取 `DEMO_API_TOKEN`，组成认证请求，并只返回约定的状态字段。若又把环境值展开成 `curl` 的认证参数，或者开启完整请求日志，前面减少的暴露就会从另一个出口回来。

机械化的验收可以用合成 canary，也就是一段只用于测试的可识别字符串。检查正常、读取失败、空字段、错误 key 和业务失败时，stdout、stderr、参数与产物是否带出样本值，同时确认旧载体在失败后保持不变。这样的测试检查指定路径，完整隔离仍需要另外的权限边界。

## 怀疑泄露时先确认对象与范围

面对暴露，首先限制继续输出和复制，再确认泄露的对象、权限、时间与可能持有副本的位置。几种秘密需要不同的处置。

| 暴露对象          | 需要处理什么                                                               |
| ----------------- | -------------------------------------------------------------------------- |
| 业务 token 或密码 | 在签发服务撤销、重新签发或改密，更新消费者，检查旧访问是否失效             |
| age 解密私钥      | 识别它能够解密的载体与历史副本，替换解密身份，再处理其中可能暴露的业务凭据 |
| SOPS 文件数据密钥 | 确认关联文件，更新数据密钥和访问配置，并评估文件里的秘密                   |
| 已输出的私密内容  | 处理保留、访问和删除范围；轮换凭据无法收回已经获知的内容                   |

SOPS 的 `updatekeys` 调整接收者，`rotate` 更新文件数据密钥，两者都不会撤销业务 token。移除受损身份并更新数据密钥后，再保存新的业务秘密；旧密文与已知明文仍无法收回。[SOPS 密钥管理](https://getsops.io/docs/usage/key-management/)

若暴露发生在 Git 中，删除最新版本里的字符串也不会撤销凭据。需要先在服务端处置访问，再按敏感内容和传播范围安排历史、克隆、缓存及其他副本的清理。[GitHub 敏感数据处理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

## 把轮换当作受控变更

2026 年 6 月的 SSH 密钥轮换也出现过相似问题：脚本把所有同类公钥共有的前缀当作旧 key 标识，锁死五台主机；恢复中又因切换版本失败而运行了旧脚本，再次锁死。PAT 轮换中的错误变量、配置覆盖和误报成功，与它共享一个模式：变更对象识别不准，执行版本与成功判断又不可靠。修复一条匹配规则，不足以防止下一种轮换事故。

现有 PAT 脚本已增加保留其他配置、选择目标和检查成功日志的处理，但仍不是下面这套完整 procedure：它没有统一的 dry-run、写前备份与自动旧值失效验证；部分“尚未看到成功日志”的路径只提示复查，最终退出状态仍可能为成功。通用轮换规范与后续硬化尚未完成，当前不能宣称轮换已经受到完整控制。

我希望固定下来的最小流程是：

1. **计划与 dry-run**：列出凭据、消费者、精确目标 key、权限、变更差异及实际执行脚本版本。用合成配置验证多 key、同类 key、空输入和错误目标；计划输出不含秘密。
2. **保留恢复入口**：写前保存受保护的配置备份，验证恢复方式；先选一个消费者试切换，保留不受本次轮换影响的管理身份。获取或切换指定版本失败就停止。
3. **更新并核对配置**：通过受控进程读取新值，精确更新目标，失败保留原值，并核对其他字段没有变化。备份本身也按秘密管理。
4. **验证新值与消费者**：确认消费者加载了目标版本，再执行真实的拉取、登录或业务动作；日志无错误、容器健康、文件写入成功均不足以替代。缺少成功证据应返回失败或明确的待验证状态。
5. **撤销并验证旧值**：在签发端撤销，检查同一目标上的旧访问已失效；把网络失败、目标错误和权限拒绝分开。会话、派生 token 与缓存按服务语义另查。agent 只接收脱敏结果。
6. **保留收据**：记录版本、对象、消费者结果、撤销状态、回滚条件和未完成项。已经撤销的旧凭据不能当作回滚方案，需要另有恢复身份或重新签发能力。

顺序仍取决于紧迫性：正在被利用或高权限暴露时，应先限制访问并接受中断；服务支持受控重叠时，才可先验证新值，再在明确期限内撤销旧值。流程需要支持两种处置，而不能为了完成平滑切换延误撤销。

## 当前实现与优先顺序

截至 2026 年 10 月 26 日，已交付的是 envctl/bakctl、服务级载体和部分轮换脚本修复；公开 v0.1.0 的写入保护有合成加密路径测试。它们没有证明临时排障不再泄密，也没有证明共享 PAT 已拆分、所有旧值已失效或完整轮换 procedure 已验收。

接下来优先补排障入口、工具返回与权限边界，再验证凭据拆分和受控轮换，随后完善五步导入流程。agent 模式与副本过期检查也需要各自的实现和验收。公开工具版本由 [envctl 仓库](https://github.com/Jarvie8176/envctl)维护，节点采用情况与实际业务结果分别核对。

[会话收尾](/posts/session-closeout/)应留下这些具体状态：阻止了哪条泄露路径，哪些消费者完成切换，旧访问是否失效，还有哪些入口依然开放。这样才能判断本次事故的原因是否真正被处理，而不只是确认新工具能够工作。
