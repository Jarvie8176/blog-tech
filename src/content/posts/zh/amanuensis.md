[Amanuensis](https://portfolio.fnpg.me/projects/amanuensis/) 是 [Yaaa](/posts/yaaa/) 中负责信息采集、分诊与提醒的子系统。它把来自不同来源的信息整理成记录，判断哪些值得看，再按受众、敏感度和提醒时机送达。首个应用是 digest：把持续流入的邮件整理成较少、较有用的提醒与摘要。

我需要它，是因为“收到信息”和“知道现在应该关注什么”之间，还有不少工作。邮箱、订阅、笔记和任务工具各自有收件箱，每一处都要求主动查看。逐条生成摘要可以缩短文本，却未必减少切换和打断。

本文从总体结构讲到组件组织，再讨论信息如何整合。**邮件采集、分诊和 digest 投递已有运行记录；任务、笔记等来源的完整接入，以及跨源事件聚合，仍需分别实现与验收。** 架构图说明职责与接口，不表示图中所有可能来源均已上线。文中的活动改期场景完全虚构，不使用私人邮件。

## 一封邮件需要经过哪些步骤

设想我订阅了一个社区活动。一封邮件说活动改到周六，另一份公开简报仍刊着旧时间。系统至少需要完成几件不同的事：取回新邮件、保留来源与时间、判断改期是否重要、决定何时提醒，以及在投递失败后继续处理。

如果进一步要求它识别“两份材料说的是同一活动”，还要处理实体对应、时间先后与证据冲突。把两条内容放进同一个数据库，只完成了采集上的汇合。

Amanuensis 因此把主路径拆成三段：**gather / judge / deliver，即采集、判断和投递。** 每段有自己的输入、结果与状态，应用层负责接线。

## 三个 kit 怎样组织

平台代码按可独立安装、测试的 Python package 组织：

```text
packages/
  ingest-kit/    # 来源适配、规范化、游标、同源去重、记录存储
  triage-kit/    # 分诊输入、策略接口、模型路由、结构化判断
  push-kit/      # 渠道选择、投递检查、摘要队列、投递账本
```

triage-kit 不 import ingest-kit，push-kit 也不 import 前两者。消费这些库的应用把采集记录转换为分诊输入，再把有效判断与原始记录关联，构造投递输入。这样可以单独更换适配器、推理端点或渠道实现，代价是应用必须认真维护字段映射和版本兼容。

| 组件         | 输入与输出                           | 它维护的状态                           |
| ------------ | ------------------------------------ | -------------------------------------- |
| `ingest-kit` | 来源适配器 → 规范化 Item             | 来源游标、内容哈希、采集记录与运行审计 |
| `triage-kit` | 分诊输入 + 策略 → structured verdict | 判断结果、模型版本、重试与异常状态     |
| `push-kit`   | 投递输入 + 渠道目录 → 发送或保留决定 | 队列、投递尝试、拒送与显式反馈状态     |
| digest 应用  | 查询、字段转换、关联与调度           | 部署配置、私有策略、各阶段的接线       |

### ingest-kit：保留来源差异，统一下游形状

适配器负责理解邮件协议或其他来源接口。核心记录包含 `source_id`、`external_id`、标题、作者、时间、正文和必要元数据。来源自己的标识保留下来，下游可用 `(source_id, external_id)` 找回同一条信息。

每个适配器还拥有自己的续取游标。核心只保存和交回这个 opaque cursor，不假定它是递增整数。邮件 UID、同步 token 或时间游标因此可以使用同一种存取接口；真正接入新来源，仍要实现适配器、验证权限和处理删除、更新等来源语义。

当前内容哈希用于**同一来源内、按指定字段计算的重复抑制**。它不能证明两个来源描述同一事件，也不等于对完整正文作语义去重。digest 使用采集与分诊分离的方式运行，采集阶段无需调用模型。

### triage-kit：把解释变成可以检查的判断

单条分诊用一次模型调用生成 `priority`、`audience`、`summary`、`key_entities` 和 `action_required`。这份 structured verdict 是后续策略的输入。例如，改期邮件可能被判断为值得留意，受众仍是个人；出现活动、日期等实体，并不自动证明它已经和另一条记录合并。

策略接口提供重要性准则、受众规则和模型选择扩展点。当前基础实现支持通过配置替换规则文本；按实时日历、在场状态或当前计划动态判断，需要额外的上下文接线和实现。不能仅凭存在插件接口，就声称系统已经持续理解我的计划。

敏感度在模型调用前决定允许的端点。高敏感内容只进入受信任的 local-only 路径；端点不可达时进入 `deferred`，等待之后再试，不因可用性问题改送云端。输出中的 priority 缺失或非法时，结果进入 `degraded`，超出重试上限后进入 `dead`，不填一个看似正常的等级。模型请求名称与实际服务模型也应分别记录，无法确认的来源保持未知。

### push-kit：把重要性变成合适的打扰

priority 使用五级：`must`、`should`、`fyi`、`ambient`、`drop`。它们表达紧迫程度与信息价值。**实际发送时机由投递策略决定**：当前 bundled default 是 digest-first，立即发送需要明确配置；不能把模型输出 `must` 当作必定即时通知的开关。

策略可以选择 immediate、下一个 digest 窗口或安静保留。`drop` 不投递、只保留记录；`ambient` 可以保留供回看。它们也不授予执行动作的权限，`action_required: true` 只表示可能需要用户关注。

真正发送前，引擎独立检查两项条件：渠道受众必须匹配条目受众；高敏感条目只能进入被配置为非云的渠道。这两项检查也覆盖摘要 flush，并使用投递账本持久化的条目属性。未知受众按 personal、未知敏感度按 high 处理；渠道的可信配置和底层隔离仍需正确维护。

因此，本地完成推理不代表可以把摘要发到云端。没有合适的非云渠道时，高敏感内容应保留而不投递。可用的 `--dry-run` 能预演路由和检查，不实际外发或写入投递状态。

## 机制、默认规则与私人策略放在哪里

复用平台时，最容易混在一起的是“怎样执行判断”和“我的家庭、账户与渠道到底是什么”。Amanuensis 用三层 policy 区分它们：

| 层                | 放置内容                                   | 维护位置                 |
| ----------------- | ------------------------------------------ | ------------------------ |
| T0 engine         | 存储、重试、接口、模型路由与投递检查机制   | 平台 package             |
| T1 defaults       | 通用重要性准则、默认提示与默认路由方式     | 平台 bundled defaults    |
| T2 private policy | 真实成员、受众分类、渠道映射与个人修正规则 | 消费应用的私有配置或插件 |

这里的分层说的是代码和配置的组织。引擎源码不嵌入私人身份和路由，运行时仍然会处理私人数据，插件也会以宿主进程的权限执行。它没有因此自动获得进程隔离或日志脱敏。

把敏感策略排除在平台源码之外，可以减少复用和未来发布时的清理成本。目前这是一项结构设计，不能据此推导平台已经开源，或所有运行数据都适合公开。

### 采集整合：记录可以一起查询

不同来源进入同一种记录形状，但各自保留原始身份。source 标识防止两个系统碰巧使用相同 ID 时被误当成一条记录；时间、出处与运行记录帮助解释信息何时取得、来自哪里。

虚构场景中的改期邮件和旧简报在这里仍是两条记录。它们可以被统一查询和送入分诊，不必先抹平来源差异。

### 判断整合：来源与上下文共同形成解释

当前成熟路径主要是逐条分诊：规则与单条材料产生结构化结果。若要进一步得出“周六是新安排，简报中的周五已过期”，系统需要识别同一活动，比较发布时间与来源权威性，保留冲突，再给出带依据的解释。

这也是扩展方向：结合当前计划、跨源关联和人工修正，提高判断的个人相关性。现有实体字段、策略接口和记录身份提供了接线位置，但并未单独交付完整的事件聚类、冲突消解或长期记忆。

整合后的内容还要继承来源约束。包含高敏感材料的组合摘要应保留相应敏感度，不能因为字数变少就自动降密。这是扩展跨源组合时的要求，需要落实并验证每个转换环节；当前单条投递门不能替代完整的派生链控制。

### 呈现整合：把多次到达变成一次阅读

即使还没有跨源语义合并，按窗口收集、排序并汇总投递，也能减少打断。push-kit 用队列和投递账本把“信息已取得”“判断已产生”“是否发送”分开记录。

同一个窗口里的多条信息，不一定属于同一个主题；可选的自然语言概述也不能取代机械生成的条目索引。概述失败时，基础索引仍可投递，让语言生成质量不必决定整个窗口是否可用。

账本按来源、条目与渠道关联投递，支持重试抑制和诊断。不过，数据库状态与外部渠道发送之间仍可能出现结果未知，需要按渠道能力核对；有 ledger 不等于所有渠道都实现了严格 exactly-once。`sent`、`read`、`acked` 也分别表示送达记录、显式阅读信号与显式确认，不能推导现实任务已经完成。

## 反馈怎样改变下一次判断

分诊错误需要一种低成本修正方式：review card 提供“同意”“应该更高”“应该更低”“不再推这一类”等信号，进入 feedback ledger。重复信号可以整理成候选 override rules，经人工审阅后用于后续分诊。模型负责解释信息，修改长期策略仍有独立的审阅步骤。[作品集技术说明](https://portfolio.fnpg.me/projects/amanuensis/technical/)

这个闭环描述的是分诊修正。打分面、信号捕获、候选生成和批准后应用，是需要分别检查的环节；不能把展示出的闭环当作每一步生产接线都已完成的证明。它也没有自动变成 Yaaa 的通用 SOP 学习或跨工具记忆系统。

## 当前边界与下一步

已有记录确认邮件采集、分诊和 digest 投递在 2026 年 7 月形成可运行路径。本文写于 2026 年 10 月 28 日，主要解释已记录的机制；写作日期不构成一次新的运行验收。作品集的[示例流程](https://portfolio.fnpg.me/projects/amanuensis/walkthrough/)使用线上取样并为展示重建的材料，可以帮助理解一条记录的变化，不能替代逐项验收。

| 范围                             | 本文采用的口径                                  |
| -------------------------------- | ----------------------------------------------- |
| 三个 kit 与 digest 接线          | 已有实现与邮件链路运行记录                      |
| 其他邮件之外的来源               | 接口支持扩展，具体 adapter 和生产接线需逐项确认 |
| 结合实时计划的判断、跨源事件合并 | 需要继续实现与验证                              |
| 分诊反馈回路                     | 有设计与展示，实际接线各环节分别核验            |
| 通用对话、长期记忆、批准后执行   | 属于更广的 Yaaa 整合范围，有独立交付边界        |

后续扩展最有价值的检验，是回到活动改期这个场景：能否找出相关记录，指出新旧信息与冲突，解释为什么值得提醒，并把提醒送到允许的地方。若还要修改日历，就进入 Yaaa 的操作路径，另行核对批准与执行结果。
