在[《如何管理 Homelab》](/posts/managing-homelab-with-ai/)里，我写过这套环境怎样从家居自动化扩展到文件、照片、媒体和个人事务。服务增加以后，日常维护也开始涉及更多关系：照片应用依赖存储，媒体服务需要找到正确的文件，监控负责发现问题，通知服务再把需要处理的事情送到人面前。

2026 年 10 月 26 日，Glance 展示的服务清单中有 64 个条目，其中 56 个标记为已部署，另有 3 个规划中、3 个已退役、2 个已替代。这个数量包含应用、基础设施和管理组件，也包含开发环境；“已部署”是清单中的生命周期状态，实际健康情况还需要检查。

其中一些服务直接参与日常使用，另一些则帮助我管理它们。

| 用途           | Glance 中的代表服务                     | 维护时需要关心什么             |
| -------------- | --------------------------------------- | ------------------------------ |
| 家居自动化     | Home Assistant、Zigbee2MQTT             | 设备通信、自动化规则和执行结果 |
| 文件与照片     | Samba、Syncthing、Immich                | 数据位置、读写权限、同步和恢复 |
| 媒体与阅读     | Jellyfin、Music Assistant、Calibre-Web  | 媒体路径、资料库和客户端访问   |
| 个人资料与事务 | Linkwarden、Memos、Vikunja、Firefly III | 保存的数据、账户和应用升级     |
| 监控与通知     | Prometheus、Grafana、Uptime Kuma、ntfy  | 检查覆盖、告警条件和通知送达   |
| AI 与任务执行  | Hermes、LiteLLM、Cronicle               | 调用入口、权限、依赖和任务结果 |

这张表按用途归纳服务，最后一列是相应的维护关注点。它们把“管理几十个服务”变成了具体问题：这个服务由谁部署，数据放在哪里，旧主机是否已经退役，升级之后应该检查哪个接口，上次迁移留下的脚本还能不能执行。每个问题单独看都不复杂，积累起来，却足以让一次普通维护变成考古。

AI 能帮我读代码、查日志、修改配置，也能执行命令。于是，问题进一步变成：当 AI 可以直接操作系统时，我怎样保留对系统的理解？同一项任务交给另一个会话，怎样复用已经验证过的流程？它说“完成了”以后，我又凭什么确认结果？

我希望建立的运维方式，需要同时满足这些条件：人能够理解系统，AI 能够接手任务，已知操作可以重复执行，执行结果能够独立验证。Runbook 是我用来连接这些要求的核心机制。这篇文章讨论它怎样组织日常操作，以及怎样让同一项工作交给另一个 AI 会话时，仍然有清楚的执行依据。

通常，runbook 指实现特定结果的操作流程。它可以从一份简单清单开始，逐步包含工具、权限、错误处理和升级路径。这也是 [AWS 对 runbook 的基本定义](https://docs.aws.amazon.com/wellarchitected/latest/framework/ops_ready_to_support_use_runbooks.html)。在我的 Homelab 中，一个服务的 runbook 还会连接当前说明、部署配置、执行脚本和验证方法，让人和 AI 都能从同一个入口开始工作。

## 把当前状态和历史分开

这件事首先要求我们知道：今天的系统究竟是什么样。

随着服务迁移和部署方式变化，文档很容易不断追加内容。最早是一份安装步骤，后来加入新主机的配置，再后来补上某次事故的临时修复命令。每段内容在写下时都可能正确，但它们共存在一个操作入口里，就会出现多个看起来都能执行的版本。

2026 年 10 月，我的 runbook 收敛工作集中处理了这类问题：互相冲突的当前状态、已经退役却仍留在目录中的可执行文件，以及夹在部署步骤中的迁移记录。对于接手的人和 AI，这些材料都增加了同一种负担——先判断哪些内容仍然有效，再开始处理任务。

因此，我开始把当前入口和详细历史分开。当前 README 解释服务现在由谁管理、数据和配置在哪里、有哪些约束、怎样操作、如何验证，以及支持什么恢复路径。详细迁移过程、失败尝试和旧拓扑进入 `history.md`，并明确标注不能据此部署。

一个服务目录可以组织成这样：

```text
runbooks/example/
├── README.md          当前状态、约束、操作入口与验证方法
├── history.md         迁移和事故经过，明确标记为历史
├── deploy.sh          需要脚本化时的执行入口
├── verify.sh          适合自动检查时的验证入口
├── compose.yaml       仍在使用的部署配置
└── recovery.md        仅在存在受支持的恢复流程时保留
```

这是职责划分的示意，文件应按服务实际需要设置。已经由部署控制器管理的服务，不必再复制一套手动部署流程；没有受支持恢复方案的服务，也不应该为了凑齐目录放一个空的恢复文档。

## 人和 AI 怎样接入服务

把人、AI 和服务放在一起，可以看到这份文档怎样参与操作。人通过仓库或编辑器阅读 runbook，AI 则按任务读取同一份当前说明，再选择其中指定的操作入口。

![人和 AI 读取共享 Runbook，通过终端、已登记的 MCP procedure 或配置 PR 接入服务，再独立核对执行结果](/images/runbook/architecture-zh.png)

[查看矢量图](/images/runbook/architecture-zh.svg) · [Mermaid 源文件](/images/runbook/architecture-zh.mmd)

_图 1：人和 AI 通过共享 runbook 找到执行入口。虚线表示文档引用，实线表示读取、调用或结果传递。图中展示可用的接入方式，不表示所有服务都已经登记为 procedure。_

直接操作有两种常见入口。人和 agent 都可以通过终端调用独立脚本；已经登记的 procedure，则可以通过本地 procedure CLI 或 MCP 调用。MCP 在这里是 agent 连接工具的协议：先用 `list_procedures` 查到参数、适用范围和 SOP，再用 `run_procedure` 调用。两种 procedure 入口复用同一个 dispatcher，也就是负责选择操作并实施调用检查的组件。

这几种入口的检查边界需要分清。直接执行脚本，依赖脚本自身的前置检查和执行身份的权限；经过 dispatcher 的已登记操作，还要满足它的参数、作用域与 gate 检查。文档里的说明帮助人和 AI 理解规则，是否真正阻止了不符合条件的操作，要看对应入口的实现。

Runbook 接入服务也有不同方式。操作脚本可以通过 SSH、命令行工具或服务 API 查询和修改目标；采用配置驱动部署的服务，则通过 PR 更新配置，经检查与授权合并后，由 doco-cd 等部署控制器拉取并应用。比如当前 Caddy 的常规路由变更走后一路径，随后还要检查目标域名实际返回的应用。Runbook 指定应该采用哪条路径，避免维护同一服务的多个相互冲突的入口。

## Calibre-Web 的 Runbook 示例

[Calibre](https://calibre-ebook.com/about) 是一款免费开源的电子书管理软件，可以整理书名、作者、封面等信息，转换电子书格式，并把书传到阅读器。[Calibre-Web](https://github.com/janeczku/calibre-web) 是使用 Calibre 书库数据库的独立 Web 应用，让人通过浏览器浏览、阅读和下载书籍。本文维护的是 Calibre-Web 服务，升级时需要同时保护书库记录和实际的电子书文件。

在我的 Homelab 中，Calibre-Web 由 doco-cd 管理，应用配置、书库元数据和电子书文件分别挂载到 `/config`、`/library` 和 `/storage`。它还有两个初始化服务：`calibre-library-init` 处理初始书库，`calibre-config-init` 处理应用配置，然后才启动 `calibre-web`。旧主机、迁移过程和修复经过已经移入 `history.md`。

假设这次任务是“升级 Calibre-Web，保留原来的书库”。下面是一份面向这项任务的 README 示例：部署关系和数据约束来自现有 runbook，操作与验收部分是为本文补全的示例流程；主机和宿主机路径通过清单查找，不在这里复制。

```markdown
# Calibre-Web 常规升级

## 当前状态与入口

- 部署方式：配置 PR 合并后，由 doco-cd 应用。
- 配置入口：runbooks/calibre-web/docker-compose.tp.yml。
- 目标主机与访问地址：查服务清单中的 calibre-web。
- 数据：/config 保存应用配置与用户；/library 保存书库元数据；
  /storage 保存电子书文件。宿主机路径以当前 Compose 为准。

## 适用范围与前提

- 本流程只处理应用镜像更新，不迁移书库、不修改挂载、不重置账户。
- 确认目标版本、当前运行镜像及更新说明中的数据库兼容性。
- 确认覆盖应用配置、书库元数据和电子书文件的恢复点与恢复方法。
- 记录升级前可访问的一本书，作为升级后的对照样本。
- 缺少恢复依据、存在数据迁移或现状与文档不符时，先停止升级。

## 必须保持的约束

- 已有书库不能按新安装处理。
- library-init 会在 metadata.db 缺失或为空时初始化空库；
  升级前发现这两种情况，应调查挂载或数据丢失，不能直接继续部署。
- config-init 与主服务都引用应用镜像，变更时必须核对两处。
- 凭据沿用现有注入路径，不复制到 README、PR 或执行回执。

## 操作

1. 读取当前配置，核对运行镜像、挂载和升级前的书库访问结果。
2. 在配置 PR 中写明目标镜像版本或摘要，同时核对初始化服务。
   检查 diff，确认没有混入路径、账户或初始化逻辑的变更。
3. 检查通过并在已有授权内合并，等待 doco-cd 应用对应提交。
4. 核对初始化服务的退出结果、主服务实际镜像和挂载，再做应用验收。

## 验收

- 实际运行镜像与本次变更的目标一致，原有挂载仍然存在。
- 访问服务地址，确认到达 Calibre-Web，登录后看到原有书库。
- 找到升级前记录的书，打开详情并验证其文件可读取。
- 回执记录提交、目标、时间、各项结果和未验证的能力。

## 失败处理

- 未通过验收时，不宣布升级完成；保留日志和观测结果。
- 书库为空时，先核对挂载和原始数据，不能用重新初始化来修复。
- 只有确认数据格式兼容且恢复路径受支持，才考虑回退镜像；
  数据库已变化时，不能把 Git revert 当作数据恢复。
```

这份示例让人可以先审查任务的边界，再把执行交给 agent。给 AI 的任务也可以具体到：“按这份 runbook 准备升级 PR，完成变更前检查；本次授权到提交 PR 为止。”已有流程并不会扩大这次授权，合并和实际部署要等到相应授权成立。

其中“核对运行镜像和挂载”还可以落成一个独立的 `inspect.sh`。下面是本文示例中的只读入口，`BOOK_HOST` 由操作者从服务清单确认后传入；人通过终端调用，拥有相同权限的 agent 也调用这份文件。

```bash
#!/usr/bin/env bash
set -euo pipefail
: "${BOOK_HOST:?请先从当前服务清单确认 SSH 目标}"

ssh -o BatchMode=yes -o ConnectTimeout=10 "$BOOK_HOST" \
  'docker inspect --format "{{.Config.Image}} {{.Image}}" calibre-web'
ssh -o BatchMode=yes -o ConnectTimeout=10 "$BOOK_HOST" \
  'docker inspect --format "{{json .Mounts}}" calibre-web'
```

这个脚本只提供主服务的镜像和挂载证据，结果还要与配置及目标版本比较。它没有证明初始化成功，也没有证明用户能读到书。对于这个例子，实际变更仍然通过配置 PR 和 doco-cd 完成，不需要另造一份手动部署脚本。如果以后把检查登记为 procedure，MCP 入口也应调用同一份实现。

这里的数据边界会直接影响操作选择：Git 保存部署配置、数据位置和初始化规则，书籍文件与可变数据库属于运行数据。仓库能够重新部署应用，并不能据此推导出书库也能够恢复。因此，“书库为空”应当触发调查，而不能让 AI 把旧服务重新初始化成一个看似健康的新服务。

当前入口也不需要复制所有信息。主机与服务清单有自己的权威来源，负责按配置更新服务的部署控制器有自己的管理配置，密钥有自己的存储和注入机制。README 的职责是把它们连接起来，并解释重要约束。把同一份配置抄到多个地方，会让下一次修改更难保持一致。

## 让执行过程可以重复检查

当上下文有了明确入口，下一步才是约束执行。

如果每次部署都要让 AI 从自然语言重新组织命令，那么同一个任务仍然包含大量临时选择：先创建哪个目录，使用哪个用户，是否拉取最新代码，遇到错误是否继续。能够重复执行的部分，应逐步进入版本化脚本或部署控制器。Runbook 说明前提、影响和验证方法，AI 找到适用的入口后，调用已有实现。

我在项目中采用的代码抽离约定，要求新增或变更的 runbook 将可执行代码放进独立文件。这样，人可以审查实际实现，工具可以检查语法和行为，其他流程也可以直接调用它。对于重复任务，之前做过的判断能够保留下来，下一个会话不必重新生成一套实现。

这也延续了[《PR review 太多了！》](/posts/pr-review-too-many/)里关于分工的讨论。人需要理解目标、约束和验收条件，AI 可以继续承担代码阅读、实现和检查。Runbook 让这些要求有稳定的入口，脚本则让具体行为能够被反复检查。

不过，有了脚本，只完成了这项工作的第一步。

我检查过的一份部署脚本，已经有工具依赖检查和 `.env` 检查，也启用了 shell 的严格模式。但它更新源码时仍使用 `pull --ff-only || true`，也就是允许更新失败后继续，结束时主要打印容器状态和日志。拉取失败后继续运行，可能意味着部署沿用旧代码；打印日志则只是提供观察材料，还没有证明应用功能正常。

这类细节说明，“确定性执行”需要具体定义。我的目标是让已知操作在明确的输入、版本和前置状态下，遵循可检查的执行规则：参数缺失时停止，目标不符时拒绝执行，关键步骤失败时返回明确结果。网络和外部服务仍会变化，但系统应该有规定好的方式处理这些变化。

可重复执行、幂等和可恢复，也分别对应不同问题：换个会话能否调用同一流程；重复执行是否产生额外副作用；执行到一半失败后，是否有办法继续或撤回。给文件命名为 `deploy.sh`，或者加一行“幂等”的注释，都不能代替这些检查。

因此，适合交给执行层的规则，需要真正进入执行层。例如，目标主机或运行用户必须匹配，必要参数必须齐全，一次性初始化必须识别已经存在的数据。重要约束应由脚本、权限或部署策略执行，AI 读到的说明则帮助它理解这些规则为什么存在。

凭据也是这个分工的一部分。Runbook 可以说明需要哪个凭据引用、允许完成什么操作，实际值由获准的工具交给需要它的进程。这里沿用[《envctl 的设计与边界》](/posts/envctl-design/)中的正常使用路径，说明文件和操作回执都应避免复制秘密值。输出过滤和执行权限仍需另行落实，相关边界见[《秘密泄露怎么办》](/posts/secrets-and-credentials/)。

不同 AI 工具也应尽量调用同一份实现。项目把可调用的操作称为 procedure，把固定的操作说明称为 SOP。它们保存在独立于具体 AI 工具的基座里，通过操作目录按需发现，再经统一入口调用。各工具的适配层负责连接，部署逻辑留在一处，换一个 agent 入口时，仍然可以审查相同的操作代码。

AI 在其中承担的工作依然很多：阅读现状、调查差异、判断已有流程是否适用，以及在遇到新问题时提出修改。但经过验证的常规操作，应尽量通过明确的入口完成。这样，人可以把注意力放在新变化和例外上。

## 一次操作的执行与验收流程

一次操作从目标走到验收，可以整理成下面的流程。图中的执行者可以是人，也可以是 AI agent；“适用且可执行”包括流程与任务匹配、当前状态满足前提，以及已有授权和实际权限足够。

[查看矢量图](/images/runbook/flow-zh.svg) · [Mermaid 源文件](/images/runbook/flow-zh.mmd)

_图 2：一次 runbook 操作的执行与验收流程。已有授权可以复用；只有出现新的取舍或超出授权范围时，才需要补充人的决定。_

发现条件不满足时，先停止对应变更，保留观察结果，再补齐参数、调查状态差异或提出流程修订。条件解决后重新检查，不能把第一次失败当成自动扩大权限的理由。两条执行路径最终都要核对服务结果：脚本退出成功、PR 合并或控制器报告完成，各自只证明流程中的一段。

验收失败时，执行者在已有授权内排障；需要恢复时，只使用当前仍受支持且适用的恢复流程。回执应保留执行版本、目标、观测时间、结果和未覆盖范围。这个流程表达的是希望每次操作都满足的要求，各服务已有入口对它的覆盖仍要分别验证。

## 用证据确认任务完成

接下来是整个流程里最容易被忽略的一步：怎样证明任务完成。

Portainer 的退役记录提供了一个很直观的例子。旧服务域名的根路径返回 HTTP 200，看起来仍然“健康”；实际响应来自反向代理的通配目录页，目标应用的 `/api/status` 返回 404。请求成功抵达了一个页面，却没有抵达预期应用。

如果 runbook 的验证步骤只写“确认返回 200”，人和 AI 都可能给出错误结论。更有意义的检查，需要确认响应属于哪个应用、版本或内容是否符合预期、认证行为是否正确，以及关键数据路径是否可用。检查深度由任务决定，但成功条件应该在执行前就写清楚。

类似地，容器处于运行状态，只能证明进程层面的某种状态；配置合并进 Git，只能证明源文件发生了变化；部署控制器报告成功，也不能自动覆盖所有业务功能。每一层证据都有自己的范围。

我希望 AI 的执行报告能够回答四件事：用了哪个版本的流程，操作了哪个目标，观察到了什么结果，还有什么没有验证。人可以沿着这些证据检查结论，而不必重新读完整段终端输出，也不必把一句“已完成”当成验收。

回到 Calibre-Web 的升级例子，假设容器已经换成目标镜像，页面也能打开，但登录后没有看到原来的书库，回执就应该表达这个失败，而不是把前两个信号合并成“升级成功”。下面是这种情况下的示例记录，尖括号中的内容应由实际执行证据填写：

```text
任务：升级 Calibre-Web，保留原书库
执行依据：runbook 提交 <commit>；变更 PR <PR>；部署提交 <commit>
目标与时间：<清单中的目标>；<带时区的观测时间>
运行镜像：<实际镜像 ID>，已与目标版本对应
应用检查：Calibre-Web 页面可访问，登录成功
数据检查：原书库未出现，对照书目不可见
结论：验收失败，不能标记完成
后续：保留初始化日志，在授权内核对挂载和原数据库
未执行：重新初始化书库、恢复备份、再次部署
未验证：原电子书文件是否完整；上传等其他功能
```

人看到这份回执，就知道书库验收尚未通过，需要继续调查挂载、应用配置与数据状态。它也给下一个 AI 会话留下了起点：哪些事实已确认、哪些动作尚未发生，以及为什么不能直接重复部署。

## 区分历史与恢复路径

恢复流程同样需要这样的明确性。

旧部署脚本曾经运行成功，并不足以证明它适合今天的环境。主机、数据格式、权限和依赖可能已经变化。我的 runbook 约定因此把历史和恢复分开：历史文件解释过去发生过什么；受支持的恢复流程需要说明触发条件、权限、前提、验证方式和退出条件。

确认为退役、又不承担当前恢复职责的可执行文件，可以在留下提交或 PR 指针后从当前目录移除。这样既能追溯，也能减少误用。不过，删除仓库文件和清理主机残留是两项工作。Portainer 的记录就明确保留了这一边界：旧控制面已被替代，停止的容器仍保留数据，全范围退役检查尚未完成。

## 持续维护 Runbook

这些约定需要持续维护。服务改变之后，如果只修改代码而不更新入口，下一次操作仍会从过期信息开始。因此，一次变更需要同时考虑：执行实现是否改变，当前说明是否仍然准确，验证条件是否需要更新，以及旧路径现在属于历史还是受支持的恢复方案。

对于能够机械判断的部分，我把它们交给模板、脚手架和 CI。目前的结构检查会对声明采用新契约的 README 检查必要章节，也会检查历史文件的警告与返回当前入口的链接、未替换的模板占位符，以及相关文档中的相对链接。

这种检查能减少结构遗漏，但它不会登录主机核对拓扑，也无法判断某个恢复方案今天是否仍然有效。脚本测试同样需要明确范围。项目中的测试标准要求：能在干净环境复现、后置状态可检查且耗时足够短的行为，应提供自动测试；涉及生产写入或无法模拟的操作，则需要记录人工验证方式和原因。

当 AI 遇到已有流程没有覆盖的问题时，这套机制也需要允许调查和修正。它可以先收集事实，指出文档、代码与运行状态之间的差异，再提出变更。经评审和验证后的解决办法，应该回到正式脚本与当前说明中。[会话收尾](/posts/session-closeout/)负责核对这次发生了什么、哪些经验值得留下，runbook 则为下一次操作提供入口。这样，一次排障才会成为下一次可复用的能力。

截至 2026 年 10 月，这项工作已经落地了模板、结构检查和部分服务的当前状态整理，生成的服务目录也开始明确区分当前、规划与历史状态。全仓库的历史拆分、冲突清理和退役文件治理仍有待办。这些剩余工作提醒我：runbook 的可靠性需要随着系统一起维护。

对一个人管理几十个服务而言，我希望逐渐形成的工作方式是：日常操作复用已有流程，新问题留下可审查的变化，每次执行都带回范围明确的证据。人仍然负责理解依赖、确定约束和处理例外，但可以把已经明确的步骤交给工具重复完成。

我判断一份 runbook 是否有用，会想象几周后的自己打开一个全新的 AI 会话。我们能否迅速找到当前状态，理解为什么这样部署，选择受支持的操作，并在结束时确认系统确实符合预期？这些问题能得到清楚回答，我才愿意把下一次同类任务交出去。
