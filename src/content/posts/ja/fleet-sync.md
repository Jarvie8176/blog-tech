**Fleet Sync は、この Homelab のために自作した運用リポジトリの自動同期サービスです。** Fleet は、自宅のサーバー、ワークステーション、クラウド上のノードなど、まとめて管理するマシン群を指します。Sync は、それらが共通の管理された配布元から継続的に更新を取得することです。このプロジェクトでは、fleet-sync が Git 内の運用スクリプト、ツールのソースコード、設定ファイルを各ノードの所定の作業コピーに同期し、リビジョンと同期状態を報告します。

これは、運用ツールチェーンのソースファイルを継続的に配布する基盤です。実際にツールを使えるようにするには、各ノードでのインストール、依存関係の準備、設定適用も必要です。本稿では、この全体の要件から Fleet Sync の役割を考えます。

一台のマシンで運用スクリプトを書いても、作業の一部が終わったにすぎません。Homelab 全体で使い続けるには、ほかのノードもそのスクリプトと依存ツールを持ち、適切なユーザーと実行環境で動かせる必要があります。

台数が増えると、小さな違いが繰り返しの手間になります。Linux サーバーには展開用のコマンドがなく、Mac のコマンドは対話シェルからしか見えず、ARM ノードには別のバイナリが必要で、更新を逃したマシンは古いスクリプトを使い続ける。保守のたびに環境を確認し、足りない部分を手作業で補うことになります。

解決したい問題は、**運用に必要なツールチェーンを、それを必要とするノードへ自動的に届け、使える状態を維持するにはどうするか**、ということです。

具体的には、管理された配布元が更新されたら、登録済みのノードが自分に適した内容を取得し、必要なインストールや適用を行い、結果を報告する。一時的にオフラインだったノードは、復帰後に更新へ追従する。運用者は、どのノードが使える状態で、どこが未完了で、どの段階で失敗したかを確認できることが目標です。

これは Git リポジトリの同期より広い問題です。既存の fleet-sync は、まずリポジトリ配布とリビジョンの可視化を担い、CLI のインストール、環境への組み込み、その後の apply は周辺の仕組みが担当しています。

本稿は、[Runbook を介した運用協働](/ja/posts/runbook/)の続きです。作業手順が明確になったあと、それを実行するための環境をどう各ノードへ届けるかを扱います。

## 何を配布するのかを定める

ここでいうツールチェーンは、運用作業に必要なツール、スクリプト、設定の集合です。それぞれ更新方法が異なります。

| 対象                     | このプロジェクトでの例                           | ノードで必要な処理                                              |
| ------------------------ | ------------------------------------------------ | --------------------------------------------------------------- |
| 自作ツールとスクリプト   | 運用スクリプト、検査プログラム、just recipes     | 対象のリビジョンを取得し、一定の場所に置く                      |
| 外部の CLI               | just、btop、procs、op、sops、age                 | OS と CPU に合う成果物をインストールし、実行可能か確認する      |
| ランタイムと基本依存関係 | Bash、Python、Git、curl、tar、unzip              | 依存するスクリプトの実行前に準備する                            |
| 設定とコマンドの入口     | PATH、シェル設定、ツール設定、SSH アクセスモデル | 適切なユーザーまたはシステムの場所へ配置し、必要なら apply する |

リポジトリ内の `tools/cli-tools/install.sh` は、複数の CLI のインストールと PATH 設定をまとめています。別の preflight は基本依存関係の一部を確認します。運用リポジトリの同期は fleet-sync の担当です。これらが組み合わさって、利用者がいう「ノードにツールを入れる」に近づきます。

したがって「リポジトリが更新された」が示すのは、ソースファイルが届いたことです。必要な CLI は未インストールかもしれず、設定はまだ適用されておらず、サービスのプロセスは古いコードで動いているかもしれません。

## 異なるノードで必要な能力をそろえる

Homelab のノードは同じ種類のマシンとは限りません。この環境には Linux、macOS、Windows があり、CPU も x86_64 と ARM64 が混在しています。稼働時間、ネットワーク条件、実行ユーザーも異なります。

こうした違いが、配布システムで表現すべき目標を決めます。

まずプラットフォームです。同じツールでも OS や CPU によって別のリリース成果物が必要です。既存の just インストーラーは `uname` を使い、Linux または macOS、x86_64 または aarch64 の成果物を選びます。ネイティブ Windows には別のインストール対応が必要です。

次に実行主体です。あるユーザーの `~/.local/bin` にインストールしても、そのユーザーのディレクトリにツールがあることしか示しません。対話シェル、非対話 SSH コマンド、システムサービスでは、PATH、HOME、利用できる認証情報が異なることがあります。検証は、実際の作業を行うユーザーで実施する必要があります。

ノードの役割もあります。操作や障害調査に使うワークステーションと、単一のサービスを担うエッジノードでは、必要なツール群が違うかもしれません。各ノードが担当作業に必要な能力を持ち、バージョン要件を明示するのが妥当な目標です。全ノードのインストール一覧やファイルパスが完全に同一である必要はありません。

配布目標には少なくとも、対象ノードとユーザー、必要なツール群、プラットフォームごとのインストール方法、期待するバージョンまたは互換条件、検証方法が必要です。現状の実装が扱うのはその一部であり、残りが今後のツールチェーン管理の課題です。

## 初回導入と日常更新では経路が異なる

新しく参加するノードには、Git も非公開リポジトリの認証情報もない場合があります。運用リポジトリを clone してから、その中のインストーラーを実行する方式では、導入時の依存関係で行き詰まります。

既存の CLI 配布スクリプトでは、リポジトリを持つ制御側が `tools/cli-tools/` をまとめ、既存の SSH 接続を通じて対象の一時ディレクトリへ送り、そこでインストーラーを実行します。対象ノードには、事前の homelab-ops clone や非公開リポジトリの読み取り認証情報は不要です。ただし、その後にインストーラーがツールをダウンロードするためのネットワーク接続は必要です。

日常更新は、その次の段階です。基本的な実行環境があるノードへ、リポジトリの変更に応じて新しいスクリプト、検査項目、設定を継続的に届けます。毎回運用者が SSH 配布を始める方式では、長期保守が再び手作業のチェックリストになります。

そこで fleet-sync が、登録済みノードの所定の運用リポジトリを継続的に維持し、同期状態を見えるようにします。

## Fleet Sync でソースと参照先を統一する

初版の導入前は、同じ運用リポジトリがユーザーの作業ディレクトリ、デプロイツールの内部ディレクトリ、一時 clone に散らばっていました。手動で pull するものも、cron で更新するものもありました。Runbook の実行前にファイルを探し、そのコピーが期待した版か確認する必要がありました。

fleet-sync は Linux と macOS で `/opt/homelab-ops` を維持し、`$HOMELAB_OPS` を共通の入口にします。運用者と自動処理は、この管理されたコピーからスクリプトや文書を読みます。開発は別の clone や worktree で行い、自動更新との干渉を避けます。

初版は Go の hub/spoke 構成です。各ノードの agent が hub へ WebSocket 接続を開始します。hub が配布元の更新を検知して通知すると、ノードは GitHub から直接 fetch し、`origin/main` に更新します。hub は接続状態と commit も集約し、監視へ渡します。

agent が外向きに接続するため、NAT 配下のノードでも hub から各マシンへの着信経路は不要です。一方、ノードから GitHub への直接接続には依存します。hub は Git の内容を配信するサーバーではありません。webhook を逃した場合に備え、hub は 60 秒ごとに reconcile を行います。これは検査間隔であり、完了時間はネットワークとノードの状態に左右されます。

各ノードが共有するのは同期プロトコルと Git のリビジョン識別子です。agent のビルド、サービス管理、ローカルパスにはプラットフォームごとの差が残ります。

リポジトリは同じ commit にそろっていても、どのスクリプトを実行し、どの外部成果物をインストールするかはローカル側の対応で決まります。Git 同期が成功しても、Linux のシェルインストーラーが Windows 用に変わるわけではありません。

この例では、同期中に配布元が commit B のままであるとし、定期 heartbeat を省略しています。二つの取得処理は独立しており、図の上下関係が Linux、Mac の順での実行を要求するものではありません。全マシンの同時完了を待つトランザクション上のバリアもありません。

実際の動作には、次の三点が関わります。

- **通知内の版を強制せず、最新の main に追従する。** hub が B を指定しても、agent は自分が fetch した `origin/main` に reset します。配布元がすでに C へ進んでいれば、そのまま C を報告する場合があります。hub は後続の reconcile で目標を更新します。
- **オフラインのノードは再登録後に追従する。** agent はバックオフしながら再接続し、ローカルの commit を報告します。hub は遅れているノードへ同期指示を送ります。復旧には hub と Git 配布元の両方への接続が必要です。初版には、hub の停止中も独立して取得を続けるノード側タイマーはありません。
- **失敗をノード単位で把握する。** 一台の fetch 失敗で、完了したほかのノードを戻すことはありません。そのノードは後続の reconcile でも遅れとして検出されます。同じリポジトリへの重複同期では、ローカルロックで作業ツリーの並行書き込みを避けます。

ただし、最新のインストールスクリプトが届いても、再実行や全 CLI の更新は自動では行われません。既存の just インストーラーは、通常、実行ファイルがすでにあればスキップし、初回インストール時に上流の最新リリースを解決します。不足ツールの導入はできますが、指定バージョンへの継続的な収束は実装していません。版の管理には、選択、更新、検証の規則が別途必要です。

## リポジトリ同期から pull と apply へ

ssh-manifest や dotfiles が対象になるにつれ、配布は複数リポジトリへ広がりました。取得後に設定適用、コマンドの参照先更新、サービスの reload が必要な場合もあります。

後継の fleet-dist は、通知、取得、apply の三段階に分けます。

GitHub push は署名検証を行う bridge を経て ntfy メッセージになります。通知を受けたノードは自身の manifest を読み、設定されたリポジトリを取得し、対応する hook を実行します。通知内の SHA は変更のヒントで、実際の取得はその時点の `origin/main` に従います。遅れて届いた通知が、古い commit への巻き戻しを要求することはありません。

ノードは設定済みの全リポジトリを定期的にも取得します。現在の systemd timer は 15 分間隔で、最大 60 秒のランダム遅延を加えます。通知サービスの障害やメッセージの取り逃しがあっても、Git とローカル実行環境が復旧すれば、後続の定期実行で追従する機会があります。

**この図は後継の fleet-dist の実装を示しており、移行は継続中です。** 登録した各ノードは、自身の manifest に従って独立に実行します。リポジトリ、パス、hooks はノードごとに異なって構いません。図は通常のリポジトリ更新を展開し、ロック待ちのタイムアウト、初回 clone の失敗などの早期終了と、認証に関わるリポジトリ用の別ディレクトリ切り替え経路を省略しています。

図に明示しておきたい実装上の境界があります。現在の `pull-repo.sh` は fetch に失敗しても hook のループへ進みます。その場合、hook が処理するのは保持された古い内容で、fetch と apply の結果は別々に記録されます。したがって `apply_ok=1` だけでは、今回リポジトリが更新されたと判断できません。新しく取得した内容に対してだけ実行すべき hook には、追加の条件が必要です。共通フレームワークがその保証を提供しているわけではありません。

図 2a の hub reconcile と違い、図 4a の timer は各ノードで動きます。bridge や ntfy が停止しても、ノード自身で取得を始められます。監視はノードが生成した結果を読み、全体の同期状態を旧 hub が集約する構成には依存しません。

ツールチェーン配布の観点では、apply は「ファイルが届いた」と「環境が使える」を結ぶ場所です。将来、hook でコマンドのリンク更新、設定適用、インストーラー呼び出しを行うことが考えられます。ただし、共通 hook があることは、それらの組み込みが完了したことを意味しません。バイナリ更新、システム設定変更、サービス再起動には、それぞれ権限、再実行時の動作、失敗処理の取り決めが必要です。

通常の運用スクリプトと、SSH アクセスに影響する設定では、書き込み権限も分けるべきです。配布サービスには作業に必要な限定的権限を与え、認証情報は別の仕組みから供給します。ツールファイルを読めることと、アクセス制御を変更したり全認証情報を使えたりすることは別です。

## Ansible を作り直しているのでは？

両者の機能は実際に重なります。Ansible はすでに [Git モジュール](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/git_module.html)で作業コピーを管理でき、playbook でソフトウェアの導入、設定生成、サービス管理もできます。「運用ツールを自動的にノードへ届ける」は、もともと構成管理ツールで扱える問題です。Fleet Sync が、それらには扱えない新しい種類の問題を作ったわけではありません。

現時点で意味のある違いは、**どの状態の照合と調整に責任を持つか**です。

| 問い                 | 現在の Fleet Sync / fleet-dist の範囲                                 | 構成管理で担当できること                                                 |
| -------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 何をノードへ届けるか | 所定の作業コピー、manifest で選んだリポジトリと hooks                 | inventory、変数、タスクでノードの役割と必要な構成を表す                  |
| 何を完了とするか     | 初版は接続と commit、後継は fetch、checkout、apply の結果も記録       | 管理対象のパッケージ、ファイル、ユーザー、サービスの状態を確認・調整する |
| 再実行をどう扱うか   | Git 更新には目標があるが、hook を安全に繰り返せるかはスクリプトの責任 | 冪等な操作に対応したモジュールを使う。独自コマンドの再実行は別途設計する |

例えば、ノードが commit B に追従したあと、`just` が誤って削除されたとします。初版の Fleet Sync は、「このユーザーが指定版の just を実行できる」を目標状態に含めていないため、リポジトリの版は一致と報告できます。導入元、版、検査方法を適切な Ansible タスクに記述すれば、次回実行時にその差分を検出して修復できます。ただし、修復には実行の起動が必要です。playbook を書くだけで継続的な制御ループが動くわけではありません。多くの Ansible モジュールは目標状態を検査しますが、すべてのモジュールや任意のシェルコマンドが自動的に冪等になるわけでもありません。[Playbook と冪等性の説明](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_intro.html#desired-state-and-idempotency)

**pull 方式も Fleet Sync 独自の利点ではありません。** Ansible の [`ansible-pull`](https://docs.ansible.com/projects/ansible/latest/cli/ansible-pull.html) は、ノードがバージョン管理リポジトリから playbook を取得し、ローカルで実行する方式です。定期実行や外部ロックと組み合わせられます。NAT 配下にあること、時々オフラインになること、Git に定義を置きたいことだけでは、自作配布器を選ぶ理由にはなりません。pull 方式を使う場合も、対象ノードに実行環境とタスクの対応が必要です。

このプロジェクトが同期層から始めた背景は具体的です。運用スクリプトと Runbook はすでに Git にあり、最初に問題になったのはコピーの散在、入口の不統一、どのマシンが遅れているか不明なことでした。所定の作業コピー、更新通知、版の報告を接続すれば、既存のスクリプトをそのまま活用できます。それは当時の工程の一部を解決しましたが、自作方式の方が Ansible より軽く、信頼でき、安いという証拠ではありません。hub、agent、各 OS のサービス、再試行、監視にも保守が必要です。

apply の拡大に伴い、この境界は変わります。hooks が広くソフトウェアの版、ユーザー権限、設定テンプレート、依存順序、サービス再起動を管理し、冪等性、ドリフト修復、失敗からの復旧も担うなら、すでに構成管理の役割を果たしています。その段階で汎用的な規則をシェルに増やし続けるのは、成熟したツールの機能を再実装することになります。まず、その部分を移すことを検討すべきです。

有用な通知や状態表示は残し、ノード構成を Ansible などの実行器へ任せ、各作業ツリーの更新者は一つにする組み合わせが考えられます。`ansible-pull` でリポジトリ取得ごと置き換える選択肢もあります。いずれも今後の案で、現行システムへの組み込みは未実施です。Fleet Sync を残すかは、プロジェクト固有の仕事がどれだけ残るかと保守コストで判断するべきで、すでに書いたからという理由では決まりません。

## 日常同期に canary がない理由

本稿の日常更新経路には、自動 canary はありません。各ノードが `origin/main` に追従し、「一部で候補版を使い、評価を通過してから残りへ広げる」という展開ゲートを持たないためです。Canary に必要なのは、限定した範囲での実利用、結果評価、そして評価に基づく展開継続の判断です。通知の到着順、timer のランダム遅延、スクリプトの一台ずつの実行だけでは、自動的に canary にはなりません。[Canary リリースの定義と条件](https://sre.google/workbook/canarying-releases/)

これは現在の実装範囲によるものです。最初の問題は、作業コピーの散在、版の不明確さ、更新漏れだったため、仕組みは「main に追いつく」ことを中心に作られました。Canary には、候補リビジョン、ノード群、観察条件、停止、昇格といったリリース状態も必要ですが、現行プロトコルにはありません。一台に先に通知するだけでも不十分です。ほかのノードは次回同期で新しい main を取得し、候補ノード自身も B から C に進む可能性があります。

人が読むだけの文書や、まだ呼び出していないスクリプトなら、到着と有効化の間に通常もう一段階あります。そのため同期層を先に実装できましたが、「ツールチェーンには段階展開が不要」とは言えません。定期ジョブの次回呼び出し、設定を適用する hook、モデルを動的に読む認証プログラムは、すぐ新しい内容を使う場合があります。**Canary がない代償は、検証完了前に同じ誤りが全登録ノードへ広がり得ることです。** commit の一致やプロセスの正常性だけでは作業の受け入れ確認にならず、Git を戻しても、インストール、設定書き込み、ほかの副作用は自動的に取り消せません。

日常の内容配布と、配布器自体の移行は別です。fleet-dist の移行設計では、選んだノードの隔離ディレクトリで旧方式と比較するか、そのノードの旧 agent を停止してから新 agent だけに作業ツリーを更新させます。そのうえで更新、オフラインからの復帰、timer による補完を検証します。新旧 agent に同じディレクトリを同時更新させてはいけません。これは**配布方式の切り替え**を試すもので、その後の全 commit に自動 canary を提供するものではありません。移行計画自体も、受け入れ確認の完了を示す証拠ではありません。

配布物が利用中のアクセス権を変えるなら、候補内容の取得と有効化を分け、有効化に試行、確認、展開の条件を設けるべきです。ssh-manifest は、この境界を具体的に示します。

## 検証の目標は、予定した作業ができること

ツールチェーン配布の完了は、対象ノードで行う作業から逆算して判断します。

| 検査する層   | 確認する問い                                                 |
| ------------ | ------------------------------------------------------------ |
| 出所         | ファイルやインストール成果物の配布元と、期待する版は何か     |
| 到着         | ノードは今回の内容を取得できたか                             |
| インストール | バイナリはプラットフォームに適合し、依存関係はそろっているか |
| 入口         | 対象ユーザーとサービスがコマンドを見つけ、実行できるか       |
| 適用         | 設定、リンク、必要な reload は完了したか                     |
| 継続状態     | 最後の検証はいつで、どの対象ノードが未完了か                 |

既存の fleet-dist は、fetch、checkout の一致、apply の結果、実行時刻を別々に記録し、ローカル textfile から監視へ渡します。リポジトリと hook の状態は把握できますが、ツールチェーン全体の版と実作業の検証には、対応する検査が必要です。

CLI の verify は版を一覧にし、不足を `MISSING` と表示するため、確認に役立ちます。ただし主に報告の仕組みであり、終了コードが成功でも全ツールが要件を満たすとは限りません。インストーラー全体が完了しても、オフラインでスキップしたノードや不足依存関係を見落とせません。

fleet-sync 自体にも、これに直結する障害がありました。CI は成功し、イメージの digest は変わり、health も正常なのに、中身は古いバイナリでした。新コード固有の文字列との照合で誤りが見つかり、同じソースを別の builder でビルドすると正しい結果が得られましたが、根本原因は最終確定していません。リポジトリ同期、インストール成果物、実行中の版を別々に確認する必要があり、一つの「正常」信号では全体を覆えないという例です。

意味のある受け入れ確認は、今後保守を行う実際のユーザーで、実際の非対話環境を使い、ツールの版を確かめ、副作用のない検査コマンドを実行することです。常駐サービスなら、現在のプロセスが期待した版で動いているかも確認します。

## 現在の実装はどこまで進んだか

最初の問題に戻ると、既存の能力は三層に整理できます。

第一層は初回導入と不足分の追加です。CLI スクリプトは SSH でインストール処理を配布し、一部ツールをプラットフォームに合わせ、到達性と版を報告できます。基本環境への依存は残り、一部の不足は修正せず報告するだけで、統一したバージョン収束方針もありません。

第二層は運用ソースファイルの継続配布です。旧 fleet-sync は実際に配備・運用され、所定の作業コピーと同期状態の可視化を提供しています。これが現時点で最も明確な担当範囲です。

第三層は取得後の適用と継続的な検証です。fleet-dist の中核 agent、bridge、監視のコードは提供済みですが、2026 年 10 月 26 日時点で整理した記録では、全 fleet の移行は未完了です。ツールの版を継続管理する機能も、今後の組み込み対象です。

今後はツールチェーンそのものに沿って、役割ごとの必要ツール、版要件の表現、インストールと apply の再実行、オフラインからの追従、対象ユーザーでの利用可能性検証を整える必要があります。複雑な依存関係やシステム状態の管理に発展するなら、すべてを shell hook に追加する前に、構成管理ツールの採用を再検討すべきです。

完了の基準は、次の実際の保守にあります。運用者や自動処理が登録済みノードへ来たとき、期待したツールでそのまま作業できること。できなければ、何が不足し、どこが遅れ、どの段階に対応が必要かを明示できることです。

## 次回：ssh-manifest の LAN と edge への配備戦略

ssh-manifest は SSH の identity、許可するアクセス関係、公鍵を記述します。通常のファイルとして配布することと、SSH 認証が随時それを読むようにすることは、異なる変更です。後者を誤ると、保守の入口と、その変更を修復する入口を同時に失う可能性があります。そのため既存の認証切り替え設計にも、Linux と macOS の検証を含む独立した canary 段階があります。前述のリポジトリ同期の試行とは、確認する目標が異なります。

次回は、同じアクセスモデルを LAN ノードと遠隔の edge ノードへ配備するとき、復旧条件の違いをどう考えるかを扱います。ここで edge は遠隔のエッジノードを意味します。重要なのは、IP アドレスの属するネットワークだけでなく、接続と救援の条件です。

| 配備環境         | 戦略を決める前に確認する条件                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| LAN ノード       | 本当に現地で操作できるか。ローカルコンソールや独立した管理経路があるか。LAN 内にあるだけでは復旧可能とは限らない                          |
| 遠隔 edge ノード | 主 SSH 経路を失っても、帯域外コンソール、独立管理経路、ノード側ロールバックが使えるか。変更対象と同じ認証やネットワークに依存していないか |
| 共通             | 候補版と有効化範囲を明示し、新しい SSH セッションで対象ユーザーと必要経路を確認する。確認に失敗したら展開を広げない                       |

復旧しやすいノードは試行候補になりますが、LAN 内の Linux 一台では、遠隔経路や macOS の違いを検証できません。既存の接続が生きていても、次のログインが成功するとは限りません。続く記事では、候補内容の有効化、環境ごとの試行ノードの選び方、展開を広げる判断、接続を失った際の復旧を考えます。具体策にはノードの復旧能力とプラットフォーム差を反映する必要があり、LAN と edge というラベルだけでは展開順序は決まりません。
