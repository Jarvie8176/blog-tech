[「Homelab の管理」](/ja/posts/managing-homelab-with-ai/)では、この環境が家の自動化からファイル、写真、メディア、個人の情報管理へと広がった経緯を書きました。サービスが増えると、日々の保守で扱う関係も増えます。写真アプリはストレージに依存し、メディアサービスは正しいファイルを参照し、監視は問題を検出し、通知サービスは対応が必要なことを人に伝えます。

2026 年 10 月 26 日時点で、Glance に表示されたサービス一覧には 64 項目ありました。内訳は稼働環境への導入済みが 56、計画中が 3、廃止済みが 3、別の仕組みに置き換え済みが 2 です。この数にはアプリ、基盤、管理用コンポーネント、開発環境が含まれます。「導入済み」は一覧上のライフサイクル状態であり、実際に正常かどうかは別途確認が必要です。

日常的に使うサービスもあれば、それらを管理するためのサービスもあります。

| 用途             | Glance にある代表的なサービス           | 保守で確認すること                                     |
| ---------------- | --------------------------------------- | ------------------------------------------------------ |
| 家の自動化       | Home Assistant、Zigbee2MQTT             | デバイス通信、自動化ルール、実行結果                   |
| ファイルと写真   | Samba、Syncthing、Immich                | データの場所、読み書きの権限、同期、復旧               |
| メディアと読書   | Jellyfin、Music Assistant、Calibre-Web  | メディアのパス、ライブラリ、クライアントからのアクセス |
| 個人の情報と事務 | Linkwarden、Memos、Vikunja、Firefly III | 保存データ、アカウント、アプリの更新                   |
| 監視と通知       | Prometheus、Grafana、Uptime Kuma、ntfy  | チェック範囲、アラート条件、通知の到達                 |
| AI とタスク実行  | Hermes、LiteLLM、Cronicle               | 呼び出し口、権限、依存関係、タスクの結果               |

この表は用途ごとにサービスをまとめ、最後の列に保守上の関心事を並べたものです。「数十のサービスを管理する」という話は、具体的な問いに分解できます。何がそのサービスをデプロイするのか、データはどこにあるのか、旧ホストは廃止済みなのか、更新後はどのエンドポイントを確認するのか、前回の移行で残ったスクリプトはまだ使えるのか。一つずつなら難しくなくても、積み重なると普通の保守が過去を掘り起こす作業になります。

AI はコードを読み、ログを調べ、設定を編集し、コマンドを実行できます。そこで次の問いが生まれます。AI がシステムを直接操作するとき、自分はどうすればその理解を保てるでしょうか。同じ仕事を別のセッションに渡すとき、検証済みの手順をどう再利用すればよいでしょうか。「完了しました」と言われた後、何を根拠に結果を確認すればよいでしょうか。

私が目指す運用では、人がシステムを理解でき、AI が仕事を引き受けられ、既知の操作を繰り返せて、その結果を独立して検証できる必要があります。これらをつなぐ中心的な仕組みが Runbook です。この記事では、日常の操作をどう整理し、別の AI セッションに同じ仕事を渡しても明確な実行根拠を持てるようにするかを考えます。

一般に Runbook は、特定の結果を得るための運用手順を指します。簡単なチェックリストから始め、ツール、権限、エラー処理、エスカレーション先などを追加できます。[AWS の Runbook の説明](https://docs.aws.amazon.com/wellarchitected/latest/framework/ops_ready_to_support_use_runbooks.html)も、この考え方を基本にしています。私の Homelab では、サービスの Runbook が現在の説明、デプロイ設定、実行スクリプト、検証方法をつなぎ、人と AI が同じ入口から作業を始められるようにしています。

現在、比較的整っているのは、現状の共有、設定とデータの境界の明確化、そして一部のデプロイ制約です。サービスごとの操作、受け入れ確認、復旧手順はまだそろっていません。以下では Calibre-Web の既存の Runbook と実際のコードを示し、そのうえで残る実行要件を考えます。

## 現在の状態と履歴を分ける

まず必要なのは、今日のシステムが実際にどうなっているかを知ることです。

サービスの移行やデプロイ方法の変更を重ねると、文書は追記され続けがちです。最初はインストール手順だったものに、新しいホストの設定が加わり、その後、障害時の一時的な修復コマンドが追加されます。書いた時点ではどれも正しかったとしても、一つの操作入口に共存すると、実行できそうな手順が複数見えてしまいます。

2026 年 10 月の Runbook 整理では、この問題に取り組みました。互いに矛盾する現在の状態、廃止されたのにディレクトリに残る実行ファイル、デプロイ手順に混ざった移行記録などです。引き継ぐ人にも AI にも、どの情報が今も有効かを判断してから作業を始めるという負担が生じます。

そこで、現在の入口と詳しい履歴を分け始めました。現在の README では、まずサービスの管理主体、データと設定の場所、制約を明らかにします。操作、検証、復旧の手順は、サービスごとに引き続き補う必要があります。詳しい移行過程、失敗した試行、古い構成は `history.md` に移し、それを根拠にデプロイしないことを明示します。

サービスのディレクトリは、例えば次のように整理できます。

```text
runbooks/example/
├── README.md          現在の状態、制約、操作入口、検証方法
├── history.md         移行と障害の経緯。履歴であることを明示
├── deploy.sh          スクリプト化が必要な場合の実行入口
├── verify.sh          自動チェックに適した検証の入口
├── compose.yaml       現在も使っているデプロイ設定
└── recovery.md        サポートする復旧手順がある場合にだけ用意
```

これは責務の分け方の例です。ファイルは各サービスの実際の必要に合わせます。デプロイコントローラーが管理するサービスに、同じことをする手動デプロイ手順を追加する必要はありません。サポートする復旧方法がないのに、ディレクトリをそろえるためだけに空の復旧文書を置く必要もありません。

## 人と AI がサービスを操作する経路

人、AI、サービスを一緒に描くと、文書が操作にどう関わるかが見えてきます。人はリポジトリやエディターで Runbook を読み、AI はタスクに応じて同じ現在の説明を読み、そこで指定された操作入口を選びます。

_図 1：人と AI は共有 Runbook から実行入口を見つけます。破線は文書からの参照、実線は読み取り、呼び出し、結果の受け渡しです。利用できる接続方法を示したもので、全サービスが procedure として登録済みという意味ではありません。_

直接操作には、よく使う入口が二つあります。人もエージェントも、端末から独立したスクリプトを呼び出せます。登録済みの procedure は、ローカルの procedure CLI や MCP からも呼び出せます。ここでの MCP はエージェントとツールをつなぐプロトコルです。まず `list_procedures` で引数、適用範囲、SOP を確認し、次に `run_procedure` で実行します。二つの procedure の入口は、操作の選択と呼び出し時のチェックを担う同じ dispatcher を使います。

入口ごとのチェック範囲は区別する必要があります。スクリプトを直接実行する場合は、スクリプト自身の前提条件チェックと実行主体の権限に依存します。dispatcher を通る登録済み操作には、さらに引数、スコープ、gate のチェックが適用されます。文書は人と AI がルールを理解する助けになりますが、条件を満たさない操作を実際に止められるかは、各入口の実装次第です。

Runbook からサービスへ到達する方法も一つではありません。操作スクリプトは SSH、CLI、サービス API で対象を照会・変更できます。設定を基にデプロイするサービスでは、PR で設定を更新し、チェックと権限に基づくマージを経て、doco-cd などのコントローラーが設定を取得して適用します。例えば、現在の Caddy の通常のルーティング変更は後者の経路を使い、その後に対象ドメインが実際に返すアプリを確認します。Runbook が使う経路を指定することで、同じサービスを保守する入口同士の矛盾を減らします。

## Calibre-Web の Runbook の具体例

[Calibre](https://calibre-ebook.com/about) は、無料で使えるオープンソースの電子書籍管理ソフトウェアです。書名、著者、表紙などを整理し、電子書籍の形式を変換し、読書端末に本を転送できます。[Calibre-Web](https://github.com/janeczku/calibre-web) は Calibre のライブラリデータベースを使う独立した Web アプリで、ブラウザーから本を探し、読み、ダウンロードできます。ここで保守するのは Calibre-Web で、書誌情報と実際の電子書籍ファイルの両方を守る必要があります。

既存の `runbooks/calibre-web/README.md` は「current snapshot」というタイトルです。節は `Snapshot`、`Deployment invariants`、`Historical summary`、`Authority and pointers` の四つです。以下は現在の状態とデプロイ制約の原文抜粋で、ホスト、アドレス、ホスト側のパスなどの項目を省いています。操作の節は追加していません。確認したのは、2026 年 10 月 26 日時点のリポジトリのスナップショット `1d5db4f7ef9a` です。

```markdown
# Calibre-Web — current snapshot

> Current state only. Detailed migration and repair history:
> [`history.md`](history.md).

## Snapshot

| Field            | Current state                                                                  |
| ---------------- | ------------------------------------------------------------------------------ |
| Status           | Deployed; doco-cd managed                                                      |
| Library mode     | Native split library: `/library` metadata + `/storage` payloads                |
| Uploads          | Globally enabled in Calibre-Web `app.db`; not reconciled by Compose            |
| Observed library | 8 EPUB files / 19,928,132 bytes on 2026-10-23; operational data, not Git state |

## Deployment invariants

- `calibre-library-init` creates the checksum-pinned empty `metadata.db` only
  when the file is absent or empty.
- Book files and mutable SQLite databases are runtime data. Git records their
  locations and initialization rules, not their contents.
```

この入口から、すでに具体的なことが分かります。サービスは doco-cd の管理下にあり、メタデータは `/library`、本のファイルは `/storage` に分かれています。アップロード設定はアプリのデータベースに保存され、Compose では調整されません。Git が記録するのはデータの場所と初期化ルールで、ライブラリの内容ではありません。README の後半では、移行の詳細を `history.md` に案内し、設定、デプロイ登録、サービス一覧、ルーティング、認証情報の参照先について正とする情報源を示しています。

README から `docker-compose.tp.yml` をたどると、制約の一部を実装したコードも読めます。以下は `calibre-library-init` の実際の `command` フィールドで、表示用にインデントだけを調整しています。`$$` は Compose でドル記号をコンテナのシェルへ渡すための書き方です。同じサービスの環境変数とマウントに依存するため、単独のシェルスクリプトとして実行するものではありません。

```yaml
command:
  - sh
  - -euc
  - |
    target=/library/metadata.db
    chown 1000:1000 /library /storage
    chmod 2775 /library /storage
    if [ -s "$$target" ]; then
      chown 1000:1000 "$$target"
      chmod 664 "$$target"
      echo "existing Calibre metadata.db retained"
      exit 0
    fi
    tmp=$$(mktemp /library/.metadata.db.XXXXXX)
    trap 'rm -f "$$tmp"' EXIT
    wget -qO "$$tmp" "$$CALIBRE_METADATA_URL"
    echo "$$CALIBRE_METADATA_SHA256  $$tmp" | sha256sum -c -
    chown 1000:1000 "$$tmp"
    chmod 664 "$$tmp"
    mv "$$tmp" "$$target"
    trap - EXIT
    echo "initialized empty Calibre library"
```

ここでは具体的な動作がすでに定まっています。`metadata.db` が空でなければ権限を調整して内容を残し、ファイルが存在しないか空なら、固定した配布元から空のデータベースを取得し、SHA-256 を検証してから配置します。取得 URL は上流のコミットに固定され、チェックサムも Compose に保存されています。人も AI も文書から同じ実装をたどって確認でき、初期化コマンドを毎回生成する必要はありません。

ただし、保証の範囲は限られます。`-s` が調べるのはファイルが空でないことだけで、元のライブラリかどうか、本のファイルを読めるかどうかは検証しません。後続の `calibre-config-init` はライブラリ UUID を照会し、アプリ DB の構造をチェックして、パスと管理アカウントを設定します。それでも、ユーザーが元の本を開けることまでは確認できません。空の DB を作る処理は初期化であり、失われたライブラリの復元にはなりません。また、設定初期化サービスと主サービスのアプリイメージは、どちらも `latest` のままです。初期化用サンプルを固定していても、アプリ全体のバージョンを固定したことにはなりません。

ここで AI に「元のライブラリを維持して Calibre-Web を更新して」と依頼しても、この README だけでは手順どおりに実行するには足りません。更新前チェック、更新順序、ライブラリの受け入れ条件、呼び出せる更新確認スクリプト、サポートする復旧手順は記載されていません。人やエージェントは設定の場所とデータの境界を把握できますが、実行状態を調べ、バージョンと復旧の根拠を確認し、操作と受け入れ確認をレビュー可能な手順にする必要があります。そこは今後の仕事として残っています。

この実例が示しているのは、現在のコンテキストを共有し、初期化ルールの一部を実装する価値です。一連の更新を別のセッションから再実行し、独立して検証できることまでは示していません。既存の Runbook は、正しいシステム、設定、データを見つける段階を明確にしています。その先の操作手順は、まだ補う必要があります。

## 実行を繰り返し確認できる形にする

コンテキストの入口が明確になったら、次は実行を制約します。

デプロイのたびに AI が自然言語からコマンドを組み立てるなら、同じタスクでも、その場で決めることが多く残ります。どのディレクトリを先に作るか、どのユーザーを使うか、最新コードを取得するか、エラー後も続行するかなどです。繰り返せる操作は、少しずつバージョン管理されたスクリプトやデプロイコントローラーへ移します。Runbook は前提、影響、検証方法を説明し、AI は適用できる入口を見つけて既存の実装を呼びます。

プロジェクトのコード分離規約では、新規または変更する Runbook の実行コードを独立したファイルに置くことを求めています。人が実装をレビューでき、ツールが構文と動作をチェックでき、別の処理からも直接呼べます。繰り返す仕事で以前の判断を残し、次のセッションが実装を作り直す必要を減らせます。

これは[「PR review が多すぎる！」](/ja/posts/pr-review-too-many/)で書いた分担にもつながります。人は目標、制約、受け入れ条件を理解し、AI はコード調査、実装、チェックを担えます。Runbook が要件の安定した入口になり、スクリプトが具体的な動作を繰り返し確認できる形にします。

ただし、スクリプトができても最初の一歩にすぎません。

私が確認したあるデプロイスクリプトには、ツール依存と `.env` のチェックがあり、シェルの厳格モードも有効でした。しかし、ソース更新には `pull --ff-only || true` を使い、更新に失敗しても続行できました。最後も主にコンテナの状態とログを表示するだけでした。取得失敗後の続行は、古いコードのままデプロイすることを意味し得ます。ログの表示は観測材料を提供しますが、アプリの機能が正常であることまでは示しません。

こうした細部があるため、「決定的な実行」が何を意味するかを具体化する必要があります。私の目標は、入力、バージョン、前提状態が明確な既知の操作を、確認可能なルールに従わせることです。引数が欠けていれば止まり、対象が違えば拒否し、重要なステップに失敗したら明確な結果を返します。ネットワークや外部サービスは変化しますが、その変化への対処方法を定めておく必要があります。

再実行できること、冪等であること、復旧できることも、それぞれ別の問いです。別セッションから同じ手順を呼べるか、繰り返しても追加の副作用が生じないか、途中で失敗した後に続行または取り消しができるか。ファイルを `deploy.sh` と名付けたり、「冪等」とコメントしたりしても、これらの確認の代わりにはなりません。

実行層で扱えるルールは、実際にその層で強制する必要があります。例えば、対象ホストや実行ユーザーの一致、必須引数の存在、一度だけ行う初期化での既存データの検出です。重要な制約はスクリプト、権限、デプロイ方針で実施し、AI が読む説明はルールの理由を伝えます。

認証情報も、この分担の一部です。Runbook には必要な認証情報の参照先と許可された操作を書き、実際の値は許可されたツールが必要なプロセスへ渡します。ここでは[「envctl の設計と境界」](/ja/posts/envctl-design/)の通常経路に沿い、説明や実行記録へ秘密の値を複写しないようにします。出力フィルターと実行権限は別途実装する必要があり、その境界は[「秘密が漏れたらどうするか」](/ja/posts/secrets-and-credentials/)で扱っています。

異なる AI ツールも、できるだけ同じ実装を呼ぶようにします。このプロジェクトでは、呼び出せる操作を procedure、定まった操作説明を SOP と呼びます。これらは特定の AI ツールから独立した基盤に置き、操作カタログから必要に応じて発見し、共通の入口で呼び出します。各ツールの adapter は接続を担当し、デプロイ処理は一か所に保ちます。エージェントの入口を変えても、同じ操作コードをレビューできます。

AI が担う仕事は依然として多くあります。現状を読み、差異を調べ、既存の手順が適用できるか判断し、新しい問題には修正を提案します。一方、検証済みの定常操作は、できるだけ明示された入口から行います。人は新しい変更や例外に注意を向けられます。

## 一つの操作を実行して受け入れを判断するまで

サービスごとの操作と受け入れ確認を整える際に、満たしたい要件を次の図にまとめました。Calibre-Web の現在の README は、この全体をまだカバーしていません。実行者は人でも AI エージェントでも構いません。「適用・実行できる」とは、手順がタスクに合い、現状が前提を満たし、既存の許可と実際の権限が足りていることを含みます。

条件を満たしていなければ、該当する変更を止めて観測結果を残します。その後、引数を補い、状態の差を調べ、または手順の修正を提案し、解決してから再確認します。最初の失敗を、自動的に権限を広げる理由にはできません。二つの実行経路は、最後にどちらもサービスの結果を確認する必要があります。スクリプトの正常終了、PR のマージ、コントローラーの完了報告は、それぞれ流れの一部を証明するだけです。

受け入れ確認に失敗したら、実行者は既存の許可範囲で調査します。復旧が必要な場合は、現在もサポートされ、状況に適用できる手順だけを使います。実行記録には、使ったバージョン、対象、観測時刻、結果、未確認の範囲を残します。この図は毎回の操作に求めたい要件を示しており、各サービスの既存の入口がどこまで満たすかは、個別に確認する必要があります。

## 証拠に基づいて完了を確認する

見落としやすいのが、タスクの完了をどう証明するかです。

Portainer の廃止記録には、分かりやすい例があります。旧サービスのドメインのルートパスは HTTP 200 を返し、一見「正常」でした。しかし実際の応答はリバースプロキシのワイルドカード経由のディレクトリページで、対象アプリの `/api/status` は 404 を返していました。リクエストはページに到達しましたが、期待したアプリには到達していませんでした。

Runbook に「200 が返ることを確認」としか書いていなければ、人も AI も誤った結論を出せます。より有効な確認には、どのアプリの応答か、バージョンや内容は期待どおりか、認証は正しく動くか、重要なデータ経路を使えるか、といった点が必要です。確認の深さはタスクによりますが、成功条件は実行前に明記しておくべきです。

同様に、コンテナが稼働中であることはプロセス状態の一部を示すだけです。設定の Git へのマージはソースファイルの変更を示し、デプロイコントローラーの成功報告も、すべてのアプリ機能を自動的に保証するものではありません。証拠には、それぞれ証明できる範囲があります。

AI の実行報告には、四つの問いに答えてほしいと考えています。どのバージョンの手順を使い、どの対象を操作し、何を観測し、何を未検証のまま残したのか。人は端末出力をすべて読み直したり、「完了」の一言を受け入れ基準にしたりせず、証拠をたどって結論を確認できます。

Calibre-Web の既存の README に残る観測は、もっと限定的です。2026 年 10 月 23 日時点で EPUB が 8 ファイル、合計 19,928,132 バイトあり、それが Git の状態ではなく実行環境のデータだと明記されています。日付付きの比較材料にはなりますが、ファイル数と合計サイズだけでは、すべての本を開けることも、その後の更新が受け入れ条件を満たしたことも証明できません。現在の README は、この観測を一連の更新の検証記録にはしていません。

次に必要なのは、実行イメージ、アプリへのアクセス、書誌情報、ファイルの読み取り結果を、同じ操作とバージョンに結び付けることです。既存のファイル統計から、それらの結論を推測することはできません。ここまで整えば、次の AI セッションは「正常」の意味を考え直さずに、明示された受け入れ条件を再利用できます。

## 履歴と復旧手順を区別する

復旧手順にも同じ明確さが必要です。

古いデプロイスクリプトが以前動いたことだけでは、今日の環境に適しているとは言えません。ホスト、データ形式、権限、依存関係が変わっているかもしれません。そのため Runbook の規約では、履歴と復旧を分けています。履歴は過去に何が起きたかを説明し、サポートする復旧手順には、開始条件、権限、前提、検証方法、終了条件を書きます。

廃止済みで、現在の復旧にも使わないと確認できた実行ファイルは、コミットや PR への参照を残して現在のディレクトリから削除できます。追跡可能性を保ちつつ、誤用を減らせます。ただし、リポジトリのファイル削除とホストに残るものの片付けは別の仕事です。Portainer の記録でも、旧コントロールプレーンは置き換え済みだが、停止中のコンテナにはデータが残り、全ホストを対象にした廃止確認はまだ終わっていないと区別しています。

## Runbook を継続して保守する

こうした取り決めは、継続して保守する必要があります。サービス変更時にコードだけを直し、入口を更新しなければ、次の操作は古い情報から始まります。変更のたびに、実行処理は変わったか、現在の説明は正しいか、検証条件の更新は必要か、旧経路は履歴なのかサポートする復旧方法なのかを考えます。

機械的に判断できる部分は、テンプレート、ひな形生成、CI に任せています。現在の構造チェックは、新しい契約への準拠を宣言した README に必要な節があるかを調べます。履歴ファイルの警告と現在の入口へ戻るリンク、未置換のテンプレート変数、関連文書の相対リンクも確認します。

このチェックは構造上の抜けを減らしますが、ホストへログインして構成を照合したり、ある復旧方法が今日も有効かを判断したりはしません。スクリプトのテストにも範囲の定義が必要です。プロジェクトの基準では、クリーンな環境で再現でき、実行後の状態を確認でき、十分短い時間で終わる動作には自動テストを用意します。本番への書き込みや再現できない操作には、手動検証の方法とその理由を記録します。

既存の手順で扱えない問題に AI が出会ったときには、調査と修正も可能にする必要があります。まず事実を集め、文書、コード、実行状態の差を示して、変更を提案できます。レビューと検証を経た解決方法は、正式なスクリプトと現在の説明へ戻します。[セッションの締めくくり](/ja/posts/session-closeout/)は今回何が起き、何を残すべきかを確認し、Runbook は次回の操作入口になります。こうして一度の障害調査が、次回に再利用できる能力になります。

2026 年 10 月時点で、テンプレート、構造チェック、一部サービスの現在状態の整理は実装済みです。生成されるサービスカタログでも、現在、計画中、履歴の状態を明確に分け始めています。一方、リポジトリ全体での履歴分離、矛盾の解消、廃止ファイルの整理はまだ残っています。Runbook の信頼性も、システムと一緒に保守し続ける必要があります。

一人で数十のサービスを管理するうえで、私が少しずつ作りたい働き方は、日常の操作では既存の手順を使い、新しい問題ではレビュー可能な変更を残し、実行のたびに範囲の明確な証拠を持ち帰ることです。人は依存関係を理解し、制約を決め、例外を扱いながら、明確になった手順をツールに繰り返し任せられます。

Runbook が役立つかを判断するとき、数週間後の自分が新しい AI セッションを開く場面を想像します。現在の状態をすぐ見つけ、この構成の理由を理解し、サポートされた操作を選び、最後にシステムが期待どおりか確認できるでしょうか。これらに明確に答えられるなら、次の同種の仕事を任せようと思えます。
