_認証情報は読まれ、コピーされ、伝播し得るものとして設計します。露出を減らし、失効と復旧の範囲や負担を管理できるようにします。_

2026 年 6 月、`docker inspect` の環境出力から配置コントローラーの共有 GitHub PAT が会話へ入りました。更新では他の設定の上書き、変数名の誤り、成功の誤判定も起きました。読み取り、認証情報の共有、変更の検証という三つの問題です。

本記事は事故と対策の取捨を扱います。選定、コンポーネント、目標フローは[次回の envctl の設計と境界](/ja/posts/envctl-design/)へ移します。

## すべての認証情報が露出する前提で設計する

秘密保存における zero trust は、すべての認証情報が露出すると仮定し、「値は vault に留まり続ける」という約束に依存しない設計前提です。暗号化は重要ですが、使う際には読める瞬間が生まれます。会話、ログ、設定のコピー、知識への保存も伝播を広げます。

一緒に考えるのは、**露出機会、権限と寿命、伝播範囲、更新コスト**です。探索的な読み取りを全面禁止すると調査能力が落ち、通常確認のたびに全認証情報を更新すると中断と変更リスクが増えます。通常確認では値への接触を減らし、特権例外には範囲を設け、失効と更新の対象を把握する必要があります。

共有 PAT はこの負担を増やします。一つの失効が複数ノードを止めるためです。利用先一覧に加え、ノードやサービスごとの分離、リポジトリ制限、読み取り専用権限が影響を狭めます。単一リポジトリの独立 deploy key、HTTPS の fine-grained PAT、長期的な複数リポジトリ連携の GitHub App では、鍵管理、ユーザーへの紐付け、短期 token 発行の負担が異なります。[GitHub の認証方式](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys)

2026 年 10 月 26 日時点の更新経路は共有 PAT が中心で、ノード別への分離は完了していません。一つのノードの認証情報を失効させても他のノードが取得できることを確認する必要があります。

## 起こりやすい意図しない露出を先に減らす

完全な隔離には時間がかかります。その前にも安価な保護を加えられます。以下は次に実装して検証する方針であり、配備済みの保証ではありません。

**実行前の阻止。** agent のツール入口で、制限のない `docker inspect`、`env`、`printenv`、`.env` の読み取り、`envctl get/export` を拒否し、限定した確認へ誘導します。複合コマンド、スクリプト、別名、他 API で回避できるため、誤操作を減らす対策です。今回と同種の操作が実行前に止まるか合成秘密で検証する価値があります。強制的な隔離でないことは、省略する理由にはなりません。

**環境変数の秘密を減らす。** Compose の `secrets:` はサービスごとにファイルを許可し、`/run/secrets/...` へ渡せます。アプリが直接ファイルを読むなら、値はコンテナの環境に入らず、通常の inspect の環境フィールドにも含まれません。`_FILE` はアプリ側の慣例で、使用バージョンの対応確認が必要です。ファイルを再び環境へ読み込んで起動すれば露出経路が戻ります。[Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

doco-cd は、token の直接設定と排他的な `GIT_ACCESS_TOKEN_FILE` を文書化しています。移行では実行版、元の環境値の除去、実際の取得、inspect に合成値が含まれないことを確認します。既存の配備定義では他の秘密にファイルを使う一方、Git token は環境変数のままです。本記事の変更は配備の移行を行いません。[doco-cd Git 設定](https://doco.cd/latest/Git-Settings/)

通常の Compose のファイル型 secret はファイルのマウントであり、ホストの元ファイルを自動暗号化しません。ローカル平文 bootstrap の権限とライフサイクルは残り、ホスト root や Docker 管理者も読めます。意図しない転記を減らす対策で、単独の隔離にはなりません。[Compose secrets リファレンス](https://docs.docker.com/reference/compose-file/secrets/)

**返却内容の制限。** よく使う procedure はローカルで必要フィールドを選び、状態、件数、エラー分類を返します。想定外の出力は管理された実行側に留め、stdout、stderr、例外、成果物にも検出とマスキングを加えます。任意の符号化や分割値を検出する保証はありませんが、漏れを減らせます。モデルに届いた後の処理では露出を取り消せません。

## 探索的な調査には権限拡大の経路が要る

AI の調査には、想定外のログ、設定、状態を見る価値があります。すべての故障を procedure で先回りできません。独立アカウントと厳格な返却規約は探索を狭め、待ち時間、入口の整備、人の判断を増やします。その負担を明示的に引き受ける必要があります。

通常は必要フィールドだけの入口を使い、不足時は権限を持つ人がローカルで調べて秘密を除いた結果を渡すか、今回の限定チェックを追加します。agent の読み取り拡大が本当に必要な場合に、明示的に承認した一時的な権限拡大を使う設計を考えています。

承認前に対象、操作、期限、読める認証情報、出力先、終了後の更新対象を示します。実行側で権限を付与し、期限で回収し、入口コードは agent から変更できないようにします。可能な限りフィールド制限も維持します。広い shell や Docker 権限で未接触を証明できないなら、許可範囲内で読める認証情報を潜在的な露出対象として再発行、切り替え、失効、検証を計画します。負担が大きければ人が調査を続ける選択もあります。

通常の rootful Docker Engine の `docker` グループは root 相当です。shell の終了や権限の復元はコピー済み token を失効させません。権限拡大と一緒に後処理と中断の予算も承認し、実際に高権限の秘密が露出した際は切り替えの都合で失効を遅らせません。[Docker の権限](https://docs.docker.com/engine/install/linux-postinstall/)

## 知識への保存も伝播経路になる

PAT が会話に入った露出は確定しています。closeout、journal、`agent-manifest`、知識候補、検索索引へも入ったかについては、**派生経路全体の確認結果がまだありません**。一つの記録のマスキングや token の失効から、全コピーの安全や内容の消去は推定できません。

ここに [Yaaa の原則](/ja/posts/yaaa/)を適用します。派生内容は実際の出所の最高機密度以上を継承し、要約、書き換え、埋め込みで自動的に下がりません。[Session closeout](/ja/posts/session-closeout/)は、まず可視範囲の会話とツール出力に秘密があったか確認します。検出時や疑いを排除できない場合は記録と派生内容を高機密として隔離し、通常保存、追加のクラウド処理、長期知識への昇格を止めます。確認範囲も記録し、スキャン通過を不在の証明にしません。

原記録、収尾要約、journal、候補、agent-manifest、索引、同期コピー、バックアップを確認します。当時のクラウド製品、アカウント方針、削除手段も対象です。ローカル削除では提供者側の削除を証明できません。信頼できるローカル環境で調べ、古い秘密を別のクラウド検出器や issue へ再送しません。

出所と派生先の確認、制限、削除や期限待ち、未知の範囲を、秘密なしの処置記録に残します。独立したマスキングレビュー後、必要な方法と事実だけを昇格させます。歴史的 PAT の伝播確認、自動機密度付与、昇格阻止は完了済みではありません。

## 認証情報の更新も事故を起こす

同年 6 月の SSH 更新では、同種の鍵に共通する接頭辞を旧鍵の識別子にして五台をロックアウトしました。復旧時にも版の切り替え失敗後に旧コードを動かして再発しました。PAT 更新と共通するのは、対象の誤認、実行版の未確認、不確かな成功判定です。

正確な利用先と対象、確認したスクリプト版、dry-run、保護された書き込み前バックアップが必要です。一つの利用先から試し、独立した復旧経路を残し、新値の業務操作と他設定の保持を検証して、発行側の意味に従い旧アクセスの失効を確認します。成功の証拠がなければ失敗か未検証にします。失効済みの旧値は復元手段にできません。

現行 PAT スクリプトには一部修正がありますが、統一検証は未完了で、成功ログ未確認でも正常終了し得る経路が残ります。暗号文、age 身元、SOPS データ鍵の更新も業務 token を失効させません。一度に切り替える利用先を減らし、再実行可能で失敗時に旧値を壊さない更新にすることで負担を下げます。

## ツールの交付順序とリスクの優先度は異なった

6 月の事故後、10 月に完成したのは既存 dotenv 編集とバックアップを独立した envctl/bakctl に整理する作業でした。これは本番権限を変えずに合成データで読み書きと復元を検証できますが、臨時調査の読み取りは直していません。実際の順序は上記のリスク優先度と一致せず、公開を事故対策完了の根拠にはできません。

本番の検証完了日は未確定です。提案する次の検証条件は、今後広い agent 調査権限を使う前に実行前阻止、ファイル型 token、返却制限、知識伝播の処置を確認し、一時権限の期限回収と更新を演習することです。完全隔離、ノード別分離、統一した更新 procedure は別途必要で、それまでは限定チェックや人の調査を残します。

進捗は、露出経路を減らせたか、一回の露出で何を更新するか、伝播を追跡できるか、復旧を検証できるかで判断します。[次回](/ja/posts/envctl-design/)では、その中で envctl が担う限定的な役割を説明します。
