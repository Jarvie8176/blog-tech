_運用を AI に任せると、認証情報の保存、プロセスへの受け渡し、出力への露出、失効と更新、そして復旧の確認にも、明確な責任分担が必要になります。_

[前回](/ja/posts/pr-review-too-many/)は、実装が希少でなくなったとき、人の判断、機械の実行、エンジニアリング上の検証、プロジェクトの意思決定の責任をどう再配分するかを考えました。認証情報は、その問いを具体的にします。AI はサービスの配置や認証エラーの調査を手伝えますが、その過程で環境を操作できる token に触れる可能性があります。

今回の事故では、調査出力が秘密を会話に持ち込み、共有認証情報が失効の影響を広げ、更新スクリプトが設定を壊しました。暗号化と安全な取り込みは日常操作を改善します。再発を防ぐには、臨時調査の読み取りと出力を制御し、認証情報の更新を検証可能な変更にする必要があります。

## 調査が複数の利用先の更新に広がった例

2026 年 6 月の調査で、`docker inspect` の環境変数出力から、配置コントローラーの共有 GitHub PAT が会話記録へ入りました。personal access token は、設定された権限の範囲で GitHub にアクセスできます。複数のノードで同じ PAT を使えば、失効の影響も共有します。

続く更新作業では、ローテーションスクリプト自体が障害を起こしました。ほかの設定も含むファイルを上書きし、一部ノードでは token の変数名を間違え、想定した数種類のエラーが出なかったことから成功と判定していました。それぞれを修正して復旧し、後にスクリプトの修正もマージされました。

この経験は、診断出力に秘密を出さないこと、共有する利用先を調べること、ほかの設定を壊さないこと、新しい値が実際に働くと確かめることを、一つの作業につなげました。ローテーションもシステムの状態を変えるため、設計と受け入れ確認が必要です。

これは過去の露出と復旧の事例です。認証情報が会話記録へ入った時点で対処が必要ですが、第三者による悪用には別の証拠が必要です。また、当時の復旧から、現在すべての追加対策が完了したとは判断できません。

## 調査で読めるものと返せるものを制御する

事故は臨時の読み取り経路で起きました。取り込み、暗号化、`exec` が正しくても、次の `docker inspect`、`env`、`cat .env`、`envctl get` が値をコンテキストへ送る可能性は残ります。後述の五段階は計画的な操作を改善しますが、この事故を防げた証拠にはなりません。

対策は三つの場所に分けて考えます。

- **調査の入口**：よく使う確認を procedure にし、許可した対象と操作だけを受け取り、必要なフィールドをローカルで選びます。コンテナの実行状態と再起動回数なら、真偽値と数値だけを返せます。環境、ラベル、ログ、エラー全文は既定で返さず、想定外の出力は保留して管理された入口で扱います。
- **ツールの返却**：stdout、stderr、例外、成果物が agent のチャネルに入る前に、許可したフィールドから結果を構成し、秘密検出やマスキングを重ねます。検出だけで任意の形式、符号化、分割された値を見つける保証はありません。モデルに届いた後の除去では露出を取り消せません。
- **実行権限**：隔離するなら、Docker 管理権限、任意の sudo、業務用復号鍵、認証情報ファイルへのアクセスを持たない独立アカウントを使い、制限された入口に操作を依頼します。そのコード、設定、許可プログラムも当該アカウントから変更できない必要があります。

通常の rootful Docker Engine について、Docker は `docker` グループが root 相当の権限を与えると明記しています。一つのコマンドを禁止したり token をファイルに移したりしても、daemon 管理者による秘密の読み取りは防げません。[Docker の権限](https://docs.docker.com/engine/install/linux-postinstall/)

モデルが必要とするのは、サービス、認証情報の参照、許可された操作、検証結果です。値は信頼できる実行側から業務プロセスへ渡します。1Password も、同じユーザーのプロセスは互いの環境へアクセスできると想定するよう説明しています。[環境への注入](https://www.1password.dev/cli/secrets-environment-variables)

この環境では、調査入口、チャネルのフィルタ、独立した権限境界の一貫した検証は未完了です。秘密を再び出力できる経路が残っており、汎用取り込みツールの整備より先に対処する必要があります。

## 共有認証情報が影響範囲を広げる

共有 PAT の失効には複数ノードの同時切り替えが伴います。利用先一覧は更新箇所を見つける助けになりますが、認証情報の権限と影響を小さくはしません。現行の更新経路は共有 PAT を前提としており、ノード別への分離が完了したとはいえません。

単一リポジトリを取得する利用先なら、ノードとリポジトリごとに独立した読み取り専用 deploy key を検討できます。HTTPS なら対象リポジトリと必要な権限に限定した fine-grained token、複数リポジトリを扱う継続的な連携なら GitHub App の短命な installation token も候補です。コントローラが対応する認証方式と実際の取得確認で判断します。deploy key は既定で読み取り専用ですが自動失効せず、fine-grained PAT は発行ユーザーに紐付き、App は発行と更新の保守を増やします。[GitHub deploy key と App](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys) · [Fine-grained PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

受け入れ条件は、一つのノードの認証情報を失効させても他のノードが取得を続けられることです。認証情報の数が増えても、一度の露出や失効の影響は小さくできます。ただし、すべての秘密を読める特権アカウントがあれば完全な隔離にはなりません。

コントローラの平文 bootstrap 設定も残っています。アクセスするアカウント、利用先、更新責任を管理する例外です。token ファイルは環境の転記による露出を減らせますが、ホスト root や Docker 管理者は引き続き読めるため、この例外が解決済みとは扱えません。

## この認証情報スタックの課題と選定

最初の問題は、値の散在でした。ノード設定に一つ、スクリプトの環境に一つ、別の利用先には古い値が残る。更新時に、どこを直すべきか分かりにくくなります。

すでに使っていた 1Password を認証情報の権威ある記録として維持し、利用先に必要な形へ値を投影する構成にしました。投影は、用途に合わせた派生コピーです。元を変更した後も、コピーの更新と、サービスが新しい値を使うことの確認が必要です。1Password のフィールド編集は、サービス側での token 発行や失効を代行しません。

設定を Git と PR に入れたいという要件もあります。SOPS は ENV や YAML などの暗号化設定を管理し、age はその公開鍵暗号のバックエンドの一つです。recipient は復号を許す受信者の設定で、対応する秘密鍵をノードや操作者が持ちます。既存のファイルと Git の運用に適合する一方、鍵、受信者、復旧経路の管理が必要です。変数名や一部のメタデータは見えることがあります。[SOPS 文書](https://getsops.io/docs/) · [age](https://github.com/FiloSottile/age)

各経路には適用条件があります。ノードの平文 `.env` は既存プログラムへ接続しやすい一方、コピーと更新責任が分散します。`op run` は実行時に 1Password から取得でき、その依存を受け入れられる操作に使えます。保存済みの値を使う常駐タスクや一部の復旧作業では、毎回のオンライン取得への依存を減らしたいため、ローカルの暗号化 carrier を残します。

| 要件                                | 採用する構成      | 引き続き必要な作業                             |
| ----------------------------------- | ----------------- | ---------------------------------------------- |
| 認証情報の記録を集中管理            | 1Password         | 権限、期限、利用先、サービス側の発行状態の管理 |
| 暗号化設定をバージョン管理          | SOPS + age        | recipient、秘密鍵、復旧、過去のコピーの管理    |
| ローカル carrier の編集・保存・注入 | envctl + bakctl   | 互換性と読み書き、復元、出力の確認             |
| 配置用のサービス設定を生成          | envsync + doco-cd | carrier の更新、交付、配置、実際の使用の確認   |

この暗号化設定のコピーを carrier、利用先へ渡す媒体と呼んでいます。`envsync` は 1Password からサービスごとの SOPS carrier を生成し、doco-cd が配置時に復号して Compose の変数補間に使います。この段階は交付済みファイルを使うため、1Password のリアルタイム読み取りへの依存を減らせます。Git、イメージ、ネットワークなどの依存は別途管理します。carrier は古くなることもあるため、元の更新、生成、配置、業務上の検証を段階ごとに確認します。

配置コントローラー自身の起動認証には bootstrap の問題もあります。後続の配置入力を取得する前に、Git へアクセスできなければなりません。現行の経路には、別途生成してファイル権限を制限した、ホストローカルの平文設定が残っています。この例外も管理対象です。

### 複雑さを四つの問いで検討する

この設計はコピーに出所の関係を与えますが、数を自動的に減らしません。同じ認証情報が 1Password、サービス用 SOPS carrier、ローカル envctl ファイル、bootstrap 設定に存在し得ます。すべてのサービスが四層を必要とするわけではありません。[前回の四つの問い](/ja/posts/pr-review-too-many/)で各層を残す理由を確認します。

1. **実際に起きた何を解決するか。** 1Password は記録の集約、SOPS は Git での設定管理、ローカル carrier は vault への即時アクセスに依存しない実行、bootstrap は最初の取得を担います。調査時の読み取りと共有権限は直接解決しません。
2. **簡単な方法で足りるか。** 即時アクセスを許容するなら `op run`、既存 SOPS ファイルを使う実行だけなら `sops exec-env` を使えます。ローカル編集が不要なら envctl のコピーは省けます。統一のためだけにコピーを追加しません。
3. **保守は何が増えるか。** 派生コピーごとに出所の参照、利用先、生成または配備バージョン、更新時刻、権限、更新する入口の責任者が必要です。秘密のハッシュを公開の証明にせず、バージョンと実際の認証操作を確認します。出所の変更だけでは実行中プロセスは更新されません。
4. **削除すると何を失うか。** ローカル保存をなくすと即時アクセスへの依存が戻ります。envctl をなくすと編集とスナップショットの約束を失いますが、SOPS の注入は残ります。サービス carrier をなくすと配備の受け渡しが変わります。必要な利用先だけがコピーを持つべきです。

現在ローカル carrier を残すのは可用性と保守負担の取引です。全コピーの一覧と陳腐化確認は統一されておらず、出所が明確でも更新が完結したとはいえません。利用先ごとに重複を減らし、更新失敗、未配備、旧値の継続使用を見える状態にする必要があります。

## envctl がコンポーネントをつなぐ方法

`envctl` は、この Homelab 用の dotenv ツールとして始まりました。現在は独立した公開リポジトリ [Jarvie8176/envctl](https://github.com/Jarvie8176/envctl)と [v0.1.0 リリース](https://github.com/Jarvie8176/envctl/releases/tag/v0.1.0)があります。編集、SOPS 呼び出し、バックアップ、プロセス実行をつなぎ、ファイル保存用の `bakctl` と対で配布します。1Password 接続とノード配布は外側のツールが担当し、既存環境の公開版への移行も個別に確認します。

配布物はリポジトリの[固定バージョンのインストール手順](https://github.com/Jarvie8176/envctl#install-a-fixed-release)から取得し、[Releases](https://github.com/Jarvie8176/envctl/releases) でバージョン、成果物、チェックサムを確認します。本記事は v0.1.0 の動作を扱い、後続版とインストール方法は公開リポジトリで確認します。

既存環境では、[接続と移行の規約](https://github.com/Jarvie8176/envctl/blob/main/docs/integrations.md)に沿って別のインストール先で検証してから利用先を切り替えます。envctl と bakctl は同じリリースにそろえ、実際の実行ファイルを確認します。ソースの checkout を更新しても、別ノードへコピーした実行ファイルは更新されません。

![認証情報スタックと envctl の論理構成：1Password と envsync がサービス用 carrier を提供し、envctl が設定、編集、保存、SOPS、bakctl、プロセス実行をつなぐ](/images/secrets/components-ja.png)

_論理的な責任分担です。envctl の該当実装は現在一つのスクリプトにあり、独立したモジュールやサービスへの分割済みを表していません。_

| 論理コンポーネント      | 担当すること                                                     |
| ----------------------- | ---------------------------------------------------------------- |
| CLI と設定              | コマンド、対象ファイル、SOPS 実行ファイル、鍵設定の選択          |
| Document                | キーと値の検索・変更、他の行の保持、同じ値の再書き込みの処理     |
| Storage と SOPS adapter | 読み取り、暗号化、復号、置換。平文は子プロセスのパイプで受け渡す |
| Backup adapter          | bakctl による保存、履歴表示、ファイル復元                        |
| Runner と Output        | プロセスへの変数注入、またはコマンドに応じたキー名・値の出力     |

プロセスへの注入は envctl 独自の機能ではありません。SOPS は復号結果を子プロセスの環境へ渡す `exec-env` と、ファイルを使うプログラム向けの `exec-file` を備えています。復号して一度実行するだけなら、まず標準機能を検討します。envctl の主な違いは編集にあり、key ごとの stdin 入力、他の行の保持、候補暗号文の復号検査、排他とアトミックな置換、対になるバックアップと復元の約束を提供します。既存 dotenv 操作の共通入口であり、実行時の隔離を追加するものではありません。[SOPS のプロセス実行](https://getsops.io/docs/usage/advanced/#passing-secrets-to-other-processes)

現在の既定対象は `~/cc/.env` で、ファイル名が `.enc` で終わる場合だけ自動的に暗号化経路を使います。例では `service.env.enc` を明示します。配置用 carrier は別の命名を使うことがあり、SOPS と doco-cd が消費します。名前の途中に `enc` があるだけで、envctl が復号すると判断してはいけません。

`exec` は親の環境を継承し、選んだファイルの変数をすべて注入します。用途ごとに carrier を分ければ、一回の業務操作へ渡す内容を減らせますが、コマンド別の変数許可リストはまだありません。`get` と `export` は値を、`list` はキー名を出力します。秘密を使う作業では、通常は業務プロセスへ直接消費させ、先にモデルへ値を戻さない形にします。

暗号化書き込みの一時ファイルには暗号文が入り、暗号化対象の bakctl スナップショットも暗号文です。これにより、このツール経路が明示的に作る平文コピーを減らせます。子プロセス、ログ、ほかのプログラムの出力は、それぞれ制御が必要です。

これらは人向けツールの既定値を引き継いでおり、agent 向けとして保守的ではありません。v0.1.0 の復号検査、ロック、アトミックな置換は**書き込みの完全性**を守ります。今回必要なのは**読み取りと出力の制約**です。

agent モードを設けるなら、暗号化ファイルの明示を必須にし、`get`/`export` を拒否し、`exec` は宣言した変数だけを注入する設計が考えられます。親環境も選別し、古い秘密の混入を防ぐ必要があります。実行可能な操作と返却フィールドも制限します。任意のプログラムへ渡す変数を減らすだけでは、値の出力や別の秘密へのアクセスを防げません。**これは未実装の案で、v0.1.0 に agent モードはありません。** 実装しても、強制には独立権限と管理された実行側が必要です。

## 空の項目から認証情報を使った実行まで

架空の `demo-service` で、固定していきたい手順を説明します。項目作成、参照の読み取り、envctl の stdin 入力と `exec` は既存の能力です。取り込み前の検査、失敗時の保護、出力の選別は、制御された入口にまとめ、合成データで一貫した受け入れ確認を行う必要があります。

![五段階の手順：agent が基礎環境と空の項目を作り、人が 1Password に入力し、ローカルツールが検査して暗号化した後、envctl が業務コマンドを実行する](/images/secrets/use-case-ja.png)

_目標とする手順です。値を扱うのはローカルツールで、モデルには参照と結果を返します。この通常経路だけでは、同じ権限を持つ agent を隔離できません。_

### Agent が基礎環境を準備する

許可されたノードに `op`、SOPS、age ツールと対になる envctl/bakctl を用意し、実際の実行パスとバージョンを確認します。そのノードで age identity を生成または再利用し、recipient とファイル権限を設定して、合成値で暗号化と復号を確認します。

1Password への初回アクセスにも認証が必要です。サービスアカウントなどの初期アクセス用認証情報は、許可された制御面で準備し、秘密鍵や token を検査出力へ戻しません。`age-keygen` は鍵の identity を作るためのツールです。envctl は暗号化読み書きに SOPS を呼び、SOPS が age バックエンドを使います。

### Agent が項目の stub を作る

Agent は指定 vault に空の項目を作り、サービス名、用途、利用先、ユーザーが埋めるフィールドを記録します。秘密フィールドは空のままにし、人には項目リンクと入力説明を返します。1Password CLI のカテゴリーテンプレートと項目作成コマンド で、この準備ができます。[項目作成の説明](https://www.1password.dev/cli/reference/management-commands/item)

例えば `credential` フィールドを使うと決め、参照を `op://demo-vault/demo-service/credential` とします。実在する項目を指さない例です。stub の存在は準備の完了だけを示し、入力済みや使用可能という意味にはなりません。

### Human が 1Password に入力する

ユーザーはサービス側で適切な権限の認証情報を取得し、1Password へ直接入力します。用途、権限範囲、有効期限を確認し、会話では「入力済み」とだけ知らせます。より広いアクセスや別の token が必要なら、人が取捨選択する地点として扱います。

### Agent がローカル検査と暗号化取り込みを起動する

呼び出しの引数には、参照、対象キー、carrier のパスだけを含めます。例えば参照先を `DEMO_API_TOKEN` に対応付けます。制御された取り込みプロセスが値を読み、読み取り成功、フィールドの存在、非空、合意した形式への適合を確認した後、stdin 経由で envctl に渡して `service.env.enc` へ保存します。値を引数、shell 展開、ツール結果へ入れる必要はありません。

失敗時の順序が重要です。`op read` を直接 `envctl set` へつなぐと、上流が失敗しても下流が空入力を書き込む場合があります。`pipefail` はパイプラインの失敗を報告しますが、発生済みの書き込みは取り消せません。読み取りと検査が成功してから、書き込みを呼び出します。公開 v0.1.0 は、候補の暗号文を再復号して一致を確認した後、対象を原子的に置き換えます。この保護と上流の非空検査は別々の段階を担当し、互いの代わりにはなりません。[公開版のセキュリティモデル](https://github.com/Jarvie8176/envctl/blob/v0.1.0/docs/security-model.md)

このラッパーではコマンドトレースも無効にし、キー、状態、必要なエラー分類だけを返します。生の応答、例外、秘密値のハッシュは戻しません。同じ値の再取り込みで無意味な更新も発生させません。

### Agent が envctl 経由で業務コマンドを実行する

呼び出しは次の形です。`service_check.py` は別途用意する業務確認スクリプトを表します。

```bash
envctl --file ./service.env.enc exec -- python3 service_check.py
```

スクリプトはプロセス内で `DEMO_API_TOKEN` を読み、認証付きリクエストを組み立て、合意した状態フィールドだけを返します。その値を `curl` の認証引数へ展開したり、リクエスト全体のログを有効にしたりすれば、別の出口から再び露出します。

機械的な受け入れ確認には、テスト専用の識別できる文字列、合成 canary を使えます。正常時、読み取り失敗、空フィールド、誤った鍵、業務失敗のそれぞれで、stdout、stderr、引数、成果物にその値が出ないかを調べます。失敗後も元の carrier が変わらないことを確認します。これは指定経路の検査であり、完全な隔離には別途権限境界が必要です。

## 露出した対象と範囲を確認する

まず出力とコピーの拡大を抑え、露出した対象、権限、時刻、コピーを持つ可能性のある場所を確認します。秘密の種類ごとに対処が異なります。

| 露出したもの            | 必要な対応                                                                             |
| ----------------------- | -------------------------------------------------------------------------------------- |
| 業務 token やパスワード | 発行サービスで失効・再発行・変更し、利用先を更新して古いアクセスの無効化を確認する     |
| age の復号用秘密鍵      | 復号可能な carrier と過去のコピーを調べ、identity を交換し、中の業務認証情報も評価する |
| SOPS のファイルデータ鍵 | 対象ファイルを特定し、データ鍵とアクセス設定を更新して、中の秘密を評価する             |
| 出力済みの私的内容      | アクセス、保持、削除の範囲を扱う。認証情報の更新では取得済みの内容を回収できない       |

SOPS の `updatekeys` は recipient を調整し、`rotate` はファイルのデータ鍵を更新します。サービスの token は失効しません。侵害された identity を除外し、データ鍵を更新してから、新しい業務認証情報を保存します。古い暗号文や取得済みの平文は回収できません。[SOPS の鍵管理](https://getsops.io/docs/usage/key-management/)

Git に露出した場合も、最新版から文字列を削除するだけでは失効しません。先にサービス側のアクセスへ対処し、内容と拡散範囲に応じて、履歴、clone、キャッシュ、ほかのコピーの整理を進めます。[GitHub の機密データ削除](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

## 認証情報の更新を管理された変更にする

2026 年 6 月の SSH 鍵更新にも似た問題がありました。スクリプトは同種の公開鍵に共通する接頭辞を旧鍵の識別子として使い、五台をロックアウトしました。復旧時にはバージョン切り替えの失敗後に古いスクリプトを実行し、再発しました。PAT 更新の変数名違い、設定上書き、成功の誤判定にも、対象の誤認、実行バージョンの未確認、不確かな成功条件という共通点があります。一つの照合式を直すだけでは次の事故を防げません。

現行 PAT スクリプトには他設定の保持、対象選択、成功ログの確認が加わっています。ただし、統一された dry-run、書き込み前バックアップ、旧アクセス失効の自動確認はありません。成功ログが未確認でも再確認を促すだけで終了状態が成功になり得る経路も残ります。汎用手順と後続の強化は未完了で、更新全体が管理済みとはいえません。

定着させたい最小限の流れは次の通りです。

1. **計画と dry-run**：認証情報、利用先、正確な対象 key、権限、変更差分、実行スクリプトのバージョンを列挙します。複数 key、同種の key、空入力、誤対象を合成設定で確認し、計画に秘密を含めません。
2. **復旧経路の保持**：書く前に保護されたバックアップを取り、復元を確認します。一つの利用先から試し、本更新で失われない管理用の認証手段を残します。指定バージョンの取得や切り替えに失敗したら停止します。
3. **更新と設定確認**：管理されたプロセス内で新値を読み、正確な対象だけを変更し、失敗時は旧値を保持します。他のフィールドが変わっていないことも確認し、バックアップも秘密として扱います。
4. **新値と利用先の検証**：利用先が読んだ版を確認してから、実際の取得、ログイン、業務操作を行います。エラーのないログ、コンテナの健康、書き込み成功では代替できません。成功の証拠がなければ失敗か明示的な未検証状態を返します。
5. **旧値の失効と検証**：発行側で失効させ、同じ対象への旧アクセスが無効になったか確認します。ネットワーク障害、誤対象、権限拒否を区別し、セッション、派生 token、キャッシュもサービスの意味に従って調べます。agent へは秘密を除いた結果だけを返します。
6. **記録を保持**：バージョン、対象、利用先の結果、失効状態、復元条件、未完了項目を残します。失効済みの旧認証情報は復元手段にならず、別の復旧用の認証手段か再発行能力が必要です。

順序は緊急性で変わります。悪用中や高権限の露出なら、まずアクセスを制限して中断を受け入れます。新旧の共存を制御できる場合に限り、期限内で新値を確認してから旧値を失効させます。滑らかな切り替えのために必要な失効を遅らせるべきではありません。

## 現在の実装と優先順位

2026 年 10 月 26 日時点で、envctl/bakctl、サービス carrier、更新スクリプトの一部修正は提供されています。公開 v0.1.0 の書き込み保護には合成データでの暗号化経路テストがあります。ただし、臨時調査が漏らさないこと、共有 PAT の分離、すべての旧アクセスの失効、完全な更新 procedure の検証完了は示していません。

優先するのは調査入口、ツールの返却、権限境界です。続いて認証情報の分離と管理された更新を確認し、五段階の取り込みを完成させます。agent モードとコピーの陳腐化確認も個別の実装と検証が必要です。ツールの版は [envctl リポジトリ](https://github.com/Jarvie8176/envctl)で管理し、ノードへの採用と実際の業務結果は別々に確認します。

[セッションの締めくくり](/ja/posts/session-closeout/)では、塞いだ露出経路、切り替えた利用先、失効した旧アクセス、まだ開いている入口を残します。新しいツールが動くことに加え、この事実で事故原因に対処できたかを判断する必要があります。
