_認証情報は読まれ、コピーされ、伝播し得るものとして設計します。露出を減らし、失効と復旧の範囲や負担を管理できるようにします。_

2026 年 6 月、`docker inspect` の環境出力から配置コントローラーの共有 GitHub 個人アクセストークン（PAT）が会話へ入りました。更新では他の設定の上書き、変数名の誤り、成功の誤判定も起きました。読み取り、認証情報の共有、変更の検証という三つの問題です。

露出後、当時すでに認証情報を更新しました。旧 PAT の GitHub 側での失効を示す記録は十分に残っておらず、この部分の処置記録を補う必要があります。

この経験から、AI 調査の柔軟さを残しながら、露出後の負担をどう管理するかを考え直しました。ツールの選定と構成は[次回](/ja/posts/envctl-design/)で扱います。

## 最初に一つの PAT を共有した理由

各ノードは同じ配置コントローラーを動かし、HTTPS で同じ非公開の配置リポジトリを取得していました。旧コントロールプレーンから doco-cd への移行では、bootstrap 設定に既存の Git PAT を引き継ぎ、後続ノードもその認証情報を再利用しました。取得先と用途が同じなので、手元の token で各インスタンスを動かせました。

ノードごとの発行、保存、配布、設定の対応付けが減り、初期の管理項目を少なくできました。一方で、節約したのは接続時の作業です。個別に失効させる境界がないため、一度の露出、期限切れ、権限変更でまとめて切り替える必要が生まれました。同じリポジトリを使っても認証情報まで共有する必要はなく、配備が安定した段階で、この先送りした更新コストを見直す余地がありました。

## すべての認証情報が露出する前提で設計する

zero trust の前提から、すべての認証情報が露出すると仮定して考えたいと思います。暗号化は重要ですが、使う際には読める瞬間が生まれます。会話、ログ、設定のコピー、知識への保存も伝播を広げます。

一緒に考えるのは、**露出機会、権限と寿命、伝播範囲、更新コスト**です。探索的な読み取りを全面禁止すると調査能力が落ち、通常確認のたびに全認証情報を更新すると中断と変更リスクが増えます。通常確認では値への接触を減らし、特権例外には範囲を設け、失効と更新の対象を把握する必要があります。

PAT の共有は更新負担を増やし、ノードやサービスごとの分離は失効の影響を狭めます。同時に、寿命の短縮を優先して検討したいと思います。GitHub App の installation token は発行から一時間で期限切れになり、リポジトリと権限も限定できるため、必要時に読み取り権限を取得するコントローラーに合います。[GitHub App token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)

分離は影響する利用先を、短い寿命は露出後に使える時間を減らします。会話、索引、バックアップの期限切れコピーはその token で直接アクセスできなくなりますが、取得済みデータの処理は残ります。App 秘密鍵の保護、更新、発行失敗への対応も必要です。一時間 token を固定 PAT と同様に設定へ置けば、別の停止原因になります。

現在は共有 PAT の経路が残っています。短期発行と利用先別の割り当てを合わせて比較し、個別失効と期限切れ後の更新を試したいと考えています。

## 秘密を読む権限を実行側に残す

暗号化とコマンド阻止は誤操作を減らし、権限分離は agent が読める範囲を決めます。同じユーザーで age 秘密鍵を読めれば envctl を経由せず SOPS を使えます。Docker 管理権限でもコンテナ内の秘密を読めます。

agent は独立アカウントにし、業務の復号鍵、vault 読み取り認証情報、Docker socket、任意 sudo を持たせず、管理された実行側に許可された業務操作を依頼したいと考えています。認証用の鍵と認証情報、入口コードと許可プログラムは実行側が管理します。この共通の隔離はまだなく、exec、阻止、マスキングは主に意図しない露出を減らす役割です。

## 起こりやすい意図しない露出を先に減らす

完全な隔離には時間がかかります。まず誤操作が起こりやすい場所に保護を加える予定です。

**実行前の阻止。** まず制限のない `docker inspect`、`env`、`printenv`、`.env` 読み取り、`envctl get/export` を止め、合成秘密で確認します。同じ値は `docker compose config` の補間結果、`docker exec … env`、`/proc/<pid>/environ`、起動ログにも出ます。ブラックリストは同等の経路を見落としやすい方式です。[Compose 設定の出力](https://docs.docker.com/reference/cli/docker/compose/config/)

拒否時は秘密が会話へ入るおそれを説明し、許可された調査入口を示し、同じ値を別のコマンドで読もうとせず、不足時は権限拡大を申請するよう伝えます。そうしないと agent が別の書き方で読み続けかねません。長期的には、操作、対象、返却フィールドの許可リストを独立した実行側で適用する方が合います。

**環境変数の秘密を減らす。** Compose の `secrets:` はサービスごとにファイルを許可し、`/run/secrets/...` へ渡せます。アプリが直接ファイルを読むなら、値はコンテナの環境に入らず、通常の inspect の環境フィールドにも含まれません。`_FILE` はアプリ側の慣例で、使用バージョンの対応確認が必要です。ファイルを再び環境へ読み込んで起動すれば露出経路が戻ります。[Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

doco-cd は、token の直接設定と排他的な `GIT_ACCESS_TOKEN_FILE` を文書化しています。移行では実行版、元の環境値の除去、実際の取得、inspect に合成値が含まれないことを確認します。既存の配備定義では他の秘密にファイルを使う一方、Git token は環境変数のままです。[doco-cd Git 設定](https://doco.cd/latest/Git-Settings/)

通常の Compose のファイル型 secret はファイルのマウントであり、ホストの元ファイルを自動暗号化しません。ローカル平文 bootstrap の権限とライフサイクルは残り、ホスト root や Docker 管理者も読めます。ファイル化で転記の機会を減らし、アクセス権限は別途管理します。[Compose secrets リファレンス](https://docs.docker.com/reference/compose-file/secrets/)

**既知の形式から検出する。** GitHub PAT の `ghp_`、`github_pat_` は安価な正規表現検査に使え、平文全体がモデルへ届く前に阻止や置換を行えます。エラーも分類だけを返します。符号化、切り詰め、出力片をまたぐ分割は別途扱い、有効性も形式だけでは分かりません。まず既知の平文漏れから対処します。[GitHub token の形式](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#githubs-token-formats)

**返却内容の制限。** よく使う procedure はローカルで必要フィールドを選び、状態、件数、エラー分類を返します。想定外の出力は管理された実行側に留め、stdout、stderr、例外、成果物にも検出とマスキングを加えます。検出で漏れを拾い、フィールド選択でチャネルへ入る内容を減らします。どちらもモデルへ届く前に行います。

## 探索的な調査には権限拡大の経路が要る

AI の調査には、想定外のログ、設定、状態を見る価値があります。すべての故障を procedure で先回りできません。独立アカウントと厳格な返却規約は探索を狭め、待ち時間、入口の整備、人の判断を増やします。その負担を明示的に引き受ける必要があります。

通常は必要フィールドだけの入口を使い、不足時は権限を持つ人がローカルで調べて秘密を除いた結果を渡すか、今回の限定チェックを追加します。agent の読み取り拡大が本当に必要な場合に、明示的に承認した一時的な権限拡大を使う設計を考えています。

承認前に対象、操作、期限、読める認証情報、出力先、終了後の更新対象を示します。実行側で権限を付与し、期限で回収し、入口コードは agent から変更できないようにします。可能な限りフィールド制限も維持します。広い shell や Docker 権限で未接触を証明できないなら、許可範囲内で読める認証情報を潜在的な露出対象として再発行、切り替え、失効、検証を計画します。負担が大きければ人が調査を続ける選択もあります。

通常の rootful Docker Engine の `docker` グループは root 相当です。shell の終了や権限の復元はコピー済み token を失効させません。権限拡大と一緒に後処理と中断の予算も承認し、実際に高権限の秘密が露出した際は切り替えの都合で失効を遅らせません。[Docker の権限](https://docs.docker.com/engine/install/linux-postinstall/)

## 知識への保存も伝播経路になる

PAT は会話に入り、closeout、journal、`agent-manifest`、知識候補、検索索引へ伝わる可能性もありました。その追跡はまだ補えていません。失効はアクセス権を処理し、伝播の確認では残った内容を探す必要があります。

ここに [Yaaa の原則](/ja/posts/yaaa/)を適用します。派生内容は実際の出所の最高機密度以上を継承し、要約、書き換え、埋め込みで自動的に下がりません。[Session closeout](/ja/posts/session-closeout/)は、まず可視範囲の会話とツール出力に秘密があったか確認します。検出時や疑いを排除できない場合は記録と派生内容を高機密として隔離し、通常保存、追加のクラウド処理、長期知識への昇格を止めます。確認範囲も記録し、漏れの追跡につなげます。

原記録、収尾要約、journal、候補、agent-manifest、索引、同期コピー、バックアップを確認します。当時のクラウド製品、アカウント方針、削除手段も対象です。ローカル削除では提供者側の削除を証明できません。信頼できるローカル環境で調べ、古い秘密を別のクラウド検出器や issue へ再送しません。

出所と派生先の確認、制限、削除や期限待ち、未知の範囲を、秘密なしの処置記録に残します。独立したマスキングレビュー後、必要な方法と事実だけを昇格させます。次は過去の PAT の伝播を確認し、機密度の付与と昇格制限を実際の締めくくりに接続します。

## 認証情報の更新も事故を起こす

同年 6 月の SSH 更新では、同種の鍵に共通する接頭辞を旧鍵の識別子にして五台をロックアウトしました。復旧時にも版の切り替え失敗後に旧コードを動かして再発しました。PAT 更新と共通するのは、対象の誤認、実行版の未確認、不確かな成功判定です。

正確な利用先と対象、確認したスクリプト版、dry-run、保護された書き込み前バックアップが必要です。一つの利用先から試し、独立した復旧経路を残し、新値の業務操作と他設定の保持を検証して、発行側の意味に従い旧アクセスの失効を確認します。成功の証拠がなければ失敗か未検証にします。失効済みの旧値は復元手段にできません。

現行 PAT スクリプトには一部修正がありますが、統一検証は未完了で、成功ログ未確認でも正常終了し得る経路が残ります。暗号文、age 身元、SOPS データ鍵の更新も業務 token を失効させません。一度に切り替える利用先を減らし、再実行可能で失敗時に旧値を壊さない更新にすることで負担を下げます。

## 更新後の日常的な使い方を改善する

token の更新は、漏えいが起きた当時に完了しています。その後に改善したいのは、日常的な認証情報の使い方です。agent がタスクのたびに保存場所を探し、値を読み出し、コマンドに組み込むなら、秘密が会話に入り込む可能性のある操作を何度も通ることになります。

10 月に envctl/bakctl を整理して公開したのは、既存の dotenv 編集・バックアップツールを再利用できる入口にするためでした。`envctl exec` なら、認証情報のファイルと業務コマンドを指定し、値の子プロセスへの注入をツールに任せられます。agent は先に平文を取り出さずにタスクを進められます。自ら保存場所を探し、値を読み、受け渡す操作を減らすことが、このツールの目的です。

この経路を、前述の出力フィルタリング、権限分離、短期認証情報と組み合わせ、秘密に触れる機会、アクセスできる範囲、露出する期間をそれぞれ減らしていきたいと考えています。重視したいのは、よく使う調査経路で露出を減らし、一回の事故で更新する対象を少なくし、コピーを追ってサービスを復旧できることです。[次回](/ja/posts/envctl-design/)ではローカルツールの設計を説明します。
