AI との対話が終わり、コードもマージされ、説明も十分に見えても、大事な経験は何十往復もの会話やツール出力に散らばったままかもしれません。数週間後に別のツールで続きを始めると、採用した案、実際に行った検査、残作業をもう一度探すことになります。

この整理を **session closeout、セッションの締めくくり**と呼んでいます。一回の仕事の事実を確認し、結果、根拠、残作業を持続的な場所へ残し、長く使える知識の候補を選びます。[Yaaa の導入記事](/ja/posts/yaaa/)では、モデルやツールを交換できる設計を紹介しました。ここでは、交換した後も仕事を続けられるようにします。

## 一度の公開にも、複数の「完了」がある

このブログの構築でも例がありました。記事はマージされ、CI と自動公開も成功し、3 言語の本文は読めました。しかし本番確認では、削除したはずのページが 200 を返しました。配信元には残っておらず、公開ドメインが古いキャッシュを返していたのです。後に[ゲートウェイと公開方法の修正](https://github.com/Jarvie8176/blog-tech/pull/13)につながりました。

その時点で、記事の修正、マージ、デプロイにはそれぞれ成功の根拠がありました。一方、削除 URL の外部から見える動作には問題が残っていました。締めくくりの記録では両方を残し、調査を具体的なタスクへ引き継ぐ必要があります。セッション全体を一つの「完了」にまとめると、この違いが消えます。

完了条件は、そのときの依頼にもよります。レビュー用の原稿が依頼なら、レビュー可能な PR の提出で満たせる場合があります。マージして公開する依頼なら、未承認の PR は残作業です。業務上の課題を残して引き継ぎを整えることはできますが、資料の準備だけで受け手が引き継いだとは言えません。

## 五つの手順で結果を残す

現在は 5 段階の SOP を再利用しています。SOP は固定した作業手順書で、異なる AI ツールでも同じ内容に従います。

1. **何が起きたかを確認する。** 関係する PR、タスク、検証結果を読み直し、参照できた会話の範囲を示します。圧縮要約しかなければ、その不足も残します。
2. **タスクの進捗を更新する。** 関連 issue と上位プロジェクトの本文が正しいか確認し、コメントには今回の増分を記します。完了条件を満たしてから閉じます。
3. **成果物の行き先を決める。** スクリプト、設定、失敗記録、検証方法を、リポジトリへ残すか、作業記録として保持するか、規則に従って片付けるか判断します。
4. **残作業を引き継ぐ。** 現在の状態、根拠の入口、試した方法、制約、最初の一歩、完了条件を記します。既存のタスクに収まれば、新しい引き継ぎ issue は不要です。
5. **再利用できる方法を探す。** まず既存の SOP や procedure の修正を考え、繰り返す需要がある場合に新しい手順を切り出します。

各段階には成果物、または該当しない理由が必要です。更新した issue 本文、作業記録、スクリプトの PR、自足した引き継ぎ資料などが該当します。独立した journal ファイルや新しい PR が必要かは、実際の材料と利用者の依頼によります。

## 根拠が結論を支えられるようにする

既存の締めくくり記録を評価した際は、92 件のコメントを調べ、目的に沿って選んだ 10 組の事例を詳しく読みました。コメント数は独立したセッション数ではなく、成功率の計算にも使えません。本番の仕事を再実行した評価でもありません。価値があったのは、根拠の読み違いを見つけることです。

たとえば、元の比較レポートを失い、利用者から報告された数値しか残っていない場合、コードの hash を保存していても数値の独立検証にはなりません。既知の未修正問題があれば、CI がすべて成功しても全体の受け入れ完了にはできません。ファイル hash の一致、利用者による短時間の抜き取り確認、全体のシナリオ検証は、それぞれ別の問いに答えます。

重要な結論では、少なくとも三つを確認したいと考えています。

| 確認すること           | 残す情報                                                        |
| ---------------------- | --------------------------------------------------------------- |
| 誰が何を観測したか     | プログラムの直接観測、利用者の報告、別 agent の伝聞、または推論 |
| 根拠は今も参照できるか | 閲覧可能、権限不足、紛失、当時未収集の区別                      |
| どの範囲と時点を覆うか | 観測時刻、対象、成功・省略の件数、過去の結果か現在の状態か      |

権限不足を紛失と記録したり、前回成功したから現在も正常と扱ったりはできません。プログラムは項目、参照先、内容のダイジェスト、矛盾した主張を検査できます。データベースの完全な復元や機器の利用体験には、対応する分野の検証方法が必要です。

## 作業記録から長く使える知識へ

締めくくりは、まず一回の仕事の文脈を残します。長期知識にするには、また役立つか、根拠は何か、どの条件で成立するか、誰が保守するかを選びます。個人システムでは、保守者は通常利用者本人です。agent は候補を提案し、保守者が採用、修正、取り消しを判断します。

![対話から知識へ：事実を確認して作業を締めくくり、記録と引き継ぎを残す。再利用する経験はレビューを経て記憶・SOP・テストへ入り、次の仕事で適用条件を確認する](/images/closeout/lifecycle-ja.png)

_作業記録には未完了事項も残せます。長期知識への採用には別途レビューが必要です。図は目標の流れであり、自動的な知識採用が稼働していることを示しません。_

| 材料                                         | 適した行き先                                 |
| -------------------------------------------- | -------------------------------------------- |
| 今回の問題に関する経緯、失敗、訂正           | 作業記録と管理されたアーカイブ               |
| 根拠と範囲が明確で、今後の判断に影響する事実 | 長期記憶の候補                               |
| 安定した検査順序や操作方法                   | SOP。決定的な手順は procedure の候補にもなる |
| 再現できる失敗や誤った判断                   | テスト、反例、障害事例                       |
| 残作業                                       | 既存タスク、または自足した引き継ぎ資料       |

ブログのキャッシュ問題から残すべき方法には条件があります。削除を許すサイトをゲートウェイ経由で公開する場合は、削除した元の URL と、公開ページが示すコミットを確認することです。この方法は[公開コード、文書、回帰チェック](https://github.com/Jarvie8176/blog-tech/pull/13/files)に入りました。方法を成果物へ残した例として追跡できますが、別のツールが独立して引き継げた効果までは証明していません。

小さな知識カードなら、**結論、根拠、適用範囲、成立しなくなる条件、保守場所、次回の利用入口**だけでも役立ちます。結論が成り立たなくなれば、修正や取り消しができるようにします。要約、匿名化した文章、検索インデックスにも私的情報が残り得るため、元の会話と長期知識のアクセス、保持、削除は分けて管理します。

### 知識へ昇格させる前に秘密を確認する

[認証情報の露出の振り返り](/ja/posts/secrets-and-credentials/)から、締めくくりに確認を加えます。可視の会話、ツール出力、保存成果物に秘密がないか先に調べます。検出時や疑いを排除できない場合は、原記録と要約、journal、知識候補、agent-manifest、索引を高機密として制限し、通常保存、追加のクラウド処理、知識への昇格を止めます。範囲と不明点を記録し、スキャン通過を不在の証明にしません。

派生内容は出所の最高機密度を継承し、独立したマスキングレビュー後に必要な事実と方法だけを昇格させます。秘密を含まない伝播と処置の記録を残し、同期コピー、バックアップ、提供者の保存方針も確認します。これは手順上の要件で、ツール横断の自動検出、機密度付与、阻止は実装と検証が必要です。

## ツールをまたいで使う実装

締めくくりを三つに分けています。共有 SOP は作業内容を定めます。実行中の agent は参照できる材料を整理し、事実を確認して変更を提案します。プログラムは決定的に検査できる部分を担います。Codex と Claude Code の入口が異なっても、締めくくりの意味と根拠の要件を共有します。

一回の締めくくりが複数の元セッションを覆うことも、後から引き継ぎを補うこともあります。入力では元セッション、今回の締めくくり実行、修訂関係を分けます。同じ入力の再実行で書き込みを重複させず、新しい発見や引き継ぎは増分として残す必要があります。

実行機構は、根拠と計画をまとめ、許可された範囲で書き込み、結果を読み直す設計です。会話の要約は入力の一つです。モデルが「完了」と書いたことだけで完了状態を発行せず、報告の検証のために本番障害を勝手に再現することも避けます。

### まず説明できる状態表を作る

現在のオフライン試作が示すのは、セッションごとの **closeout state** と **staleness** です。前者は明示的な締めくくり記録の有無と最新の活動を覆うかを、後者は最後に保存された活動からの経過時間を表します。

以下は試作が受け取る実験用の記録で、公開済みの汎用 schema ではありません。

```json
{
  "provider": "codex",
  "session_id": "resumed-after-closeout",
  "state": "closed",
  "covers_through": "2026-10-24T20:00:00Z"
}
```

試作はホスト、ツール、元の session ID で識別し、`covers_through` と最新の活動時刻を比較します。記録が `closed` でも、その後に活動があれば `needs_closeout` を表示します。明示的な記録がなければ `unknown` とし、長く使われていないことから終了済みとは推測しません。

時刻を固定して 6 件の合成セッションを入力した CLI の実出力です。`local` はサンプルで使う既定のホスト名です。

```text
SESSION                                  CLOSEOUT        STALENESS
local/claude/open-old                    open            2d 0h · stale
local/claude/legacy-no-closeout-record   unknown         1d 2h · stale
local/claude/closing                     closing         2h 0m · fresh
local/codex/closed-recent                closed          30m · fresh
local/codex/resumed-after-closeout       needs_closeout  5m · fresh
local/codex/archived-source-unavailable  unknown         unknown
```

締めくくりの状態と未活動時間は独立です。再開直後でも締めくくり直しが必要になり、締めくくり済みのまま長く使われないこともあります。元データを読めない、時刻が不正、末尾の記録が不完全な場合は不明値を残します。試作は時刻と記録を信頼する表示器であり、締めくくり内容の十分さや業務の完了を証明するものではありません。

## 現在できることと、次に検証すること

2026 年 10 月 25 日時点で、5 段階の SOP には手動で使った記録があり、過去事例の評価も完了しています。記録の量と、採用された再利用可能な成果物の量を分けて集計すると、次のとおりです。

| 集計対象                     | 確認した件数           | 数え方                                                                                      |
| ---------------------------- | ---------------------- | ------------------------------------------------------------------------------------------- |
| 議論の記録                   | 92 件のコメント        | 締めくくり、引き継ぎ、追記、修正を含み、独立した 92 セッションではありません                |
| 詳細な確認                   | 10 組の事例、7 件の PR | 記録、成果物、PR の状態を目的抽出で確認しており、全履歴の悉皆調査ではありません             |
| マージ済みの再利用可能な方法 | 少なくとも 3 組の事例  | 操作・受け入れ手順書 4 件（新規 3 件、改訂 1 件）と、実装・合成テスト・CI を含む検証器 1 組 |
| 未マージの方法に関する成果物 | 2 組の事例             | 手順書、検査スクリプト、テストは PR にありますが、採用済みには数えません                    |

マージ済みの 3 組は、検証手順と分野別の受け入れ手順、段階ごとの復旧確認、復旧手順と読み取り専用検証器を残しています。数えるのは再利用可能な方法の成果物で、journal、索引、参照リンクは別件として加算しません。同じ事例に複数のファイルがあっても、事例数は 1 組です。この 5 組は今回、方法を含む PR まで明確に追跡できた事例であり、残りの事例に蓄積がないと判定したわけではありません。「少なくとも 3 組」は確認できた下限で、10 や 92 を分母にした成功率ではありません。マージ済みであることも、その後の独立した再利用を証明しません。

読み取り専用の試作は CLI 表、JSON、静的 HTML を出力できます。本稿のために再実行した 11 項目のテストはすべて成功し、入力は合成セッションと元形式に合わせた合成記録です。このテスト数は、上記の過去記録や採用された成果物の件数とは別に集計しています。

完全な自動締めくくりは未完了です。実際の作業から記録を自動発行する接続、実履歴の走査、常駐画面、長期知識の自動採用経路はありません。共通の実行機構とマージ許可の制約には方向性が定まりましたが、実装と一通りの検証は残ります。締めくくりの依頼自体がマージやデプロイを許可するわけでもありません。

次は範囲を限った実データで状態と根拠の網羅性を確認し、オフライン検査器によって誤った結論や引き継ぎ不足が減るか比較します。元の会話に参加していない新しいセッションが、残されたタスク、SOP、根拠だけで引き継ぐ検証も必要です。時間、token、引き継ぎ成功率の信頼できる基準値はまだなく、削減率は示しません。

次に同じ問題に出会ったとき、agent が使える方法とその根拠を見つけ、再検証が必要な条件を理解できることを目指しています。Session closeout はその入口を残し、知識が役立つかは次の利用で確かめます。

## 付録：コピーして使える締めくくり prompt

締めくくりの呼び出し用草案を、汎用テンプレートに整理しました。最初の 3 項目を置き換えてから、現在の agent に渡します。継続的なルールはプロジェクトの SOP で管理します。

```text
プロジェクトとリポジトリ：[対象と関連タスクの入口]
締めくくり SOP：[現行 SOP のパスまたはリンク]
書き込み範囲：[更新可能なタスク、記録先、リポジトリ。既存の明示的な許可を引き継ぐ]

この session の締めくくりを実行してください。まず SOP を読み、使える procedure の引数、範囲、実行条件を確認してください。
既存の許可を再利用し、条件を満たさない操作は停止して記録してください。制約は迂回しません。
実行入口がなければ、同じ SOP でレビュー可能な結果を準備し、未実行の操作を列挙してください。

次の 5 段階を実施してください。
1. 振り返りと記録：見える会話の範囲、圧縮された要約、欠けた文脈を明記します。
   issue、PR、commit、検証根拠を確認し、直接観察、伝聞、推論、不明を区別します。
   目標、行動、判断と理由、結果、訂正、残作業を保存します。生の会話や機密資料は既存の保管ルールに従います。
   会話、ツール出力、成果物の秘密を先に確認し、対象範囲を記録します。通過しても不在の証明にはしません。
   検出または疑いが残る場合は原記録と派生内容を高機密に制限し、通常保存、クラウド再処理、知識昇格を止めます。
   秘密の値を転記せず伝播と処置を記録し、独立したマスキングレビュー後に必要な事実と方法だけを昇格させます。
2. タスクの更新：関連 issue と上位プロジェクトの本文で、現状、受け入れ条件、残作業を確認します。
   今回の進捗だけを追記し、根拠が受け入れ条件を満たす場合のみ閉じます。他者の無関係な変更は保持します。
3. 成果物と知見の扱い：正本に保存済み、再利用知識として採用、今回限りの保管、保留を判断し、理由と所属先を示します。
   検証方法、実行順序、失敗した方法、環境の注意点も含め、検証と機密情報の除去後に適切な場所へ提出します。
   知識として採用しないことは、削除してよいという意味ではありません。
4. 残作業の引き継ぎ：既存タスクを再利用し、適切な引き継ぎ先がない場合のみ新設します。
   現状と時刻、採用済み判断、コードと根拠の入口、失敗した方法、阻害要因、次の行動、受け入れ条件、許可範囲を保存します。
   この会話に依存しない引き継ぎ prompt を用意し、全体の文脈を継続して読める場所へ保存します。
   不要なら理由を示します。明示的な依頼なしに次の session を作成したり、メッセージを送ったりしません。
5. 方法の再利用：既存 skill、SOP、procedure を調べてから、必要な追加・改訂を提案します。
   内容の採用、入口の導入、プログラムの呼び出し可否、ツール間の検証状況を別々に報告します。

上記の範囲と既存の許可内でのみ変更を公開します。既定ではレビュー可能な結果を渡し、
このテンプレート自体はマージやデプロイの追加許可を与えません。
書き込み結果を読み戻します。既存の許可でマージする場合は、PR 状態、マージ SHA、対象ブランチの内容を確認します。
根拠を保存してから、それに依存する最終状態を更新します。再開時は実施済み操作を調べ、重複作成や投稿を避けます。

最後に、記録と PR のリンク、実際に更新したタスク、知識の採否と保存先、残作業と阻害要因、
実行済み・未実行の範囲、次の session 用 prompt または引き継ぎ不要の理由を示します。
読み戻して確認できた操作だけを完了と報告し、未マージ、未デプロイ、未検証、不明の状態を保持します。
```

その呼び出しで締めくくり記録を自動マージしたい場合は、次の許可を別途追加できます。対象は記録のみです。新しい方法や実装を含む PR には、それらの変更に対する許可とレビューのルールを適用します。

```text
今回の追加許可：journal／締めくくり記録の独立した PR を作成し、リポジトリの実行条件、CI、必要なレビューを満たした後に自動マージしてください。
対象は今回の締めくくり記録のみで、新しい操作規範、ADR、コード、スクリプト、fixture、設定、資産一覧、既存の業務 PR は含みません。
実際のリポジトリ、PR、head に対応させて差分全体を確認し、ブランチ保護は迂回しません。
マージ後に PR 状態、マージ SHA、対象ブランチの内容を読み戻します。待機列への追加や要求の成功をマージ完了とは報告しません。
```
