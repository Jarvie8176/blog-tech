設定を見れば、あるサービスが今日どこで動いているかは分かります。しかし、数か月前になぜそこへ配置したのかまでは、読み取れないことがあります。

当時はメモリ、ネットワーク、権限に制約があったのかもしれません。単に最も低コストな暫定案を選んだ可能性もあります。環境が変われば、以前の判断の前提も変わります。理由がチャットやコミット履歴にしか残っていなければ、次の保守作業でまた調べ直す必要があります。引き継ぐのは将来の自分かもしれませんし、当初の議論に参加していない AI エージェントかもしれません。

私は運用リポジトリに、現在どの案を採用しているかと、なぜそこへ至ったかの両方を残したいと考えています。Git はファイルの変更を保存し、runbook は操作方法を説明します。ADR は重要な決定の背景、選択、代償を、後からたどれる記録にします。

[第 09 回 Fleet Sync（中国語）](/posts/fleet-sync/)では、設定の配布を扱いました。初期の方式では hub が spoke への配布を調整し、後継方式では各ノードが Git から内容を取得し、通知を受けて適用します。本稿ではその決定を例に、ADR 自体の仕組みを説明します。記録をどう構成するか、提案をライフサイクルへどう載せるか、新しい決定が古い決定をどう置き換えるか、どの保守作業をツールに任せられるかが中心です。

## ADR と MADR がそれぞれ担うこと

ADR は Architecture Decision Record、アーキテクチャ上の決定を残す記録です。一つの重要な決定について、その時点の背景、選択、状態、それによって生じる結果を説明します。サービスの配置先、データの保存方法、認証・認可の境界、設定の配布方針などが対象になります。

Michael Nygard は ADR の紹介で、決定が変わった後も古い記録を残し、後継の決定に置き換えられたことを示すよう述べています。後の保守担当者が過去を理解し、どの結論が現在は適用されないかを見分けるためです。[Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

MADR は Markdown Architectural Decision Records の略です。ADR 用の構造化された Markdown テンプレートを提供し、問題の背景、検討した選択肢、決定結果、トレードオフを整理しやすくします。上流プロジェクトには完全版と簡略版があり、必要に応じて選べます。[MADR 公式ドキュメント](https://adr.github.io/madr/)

ADR は決定に関する情報を保存する実践であり、MADR はその情報を文書にまとめる助けになります。採番方法、置き換え関係の分岐を認めるか、新しい記録をいつ作るか、CI で何を検証するかは、プロジェクト側でさらに定める必要があります。

運用リポジトリでは、それぞれの記録が答える問いも異なります。

| 記録・成果物                 | 主に答える問い                             |
| ---------------------------- | ------------------------------------------ |
| ADR                          | なぜこの案を選び、どの代償を受け入れたのか |
| Runbook                      | 実行、検証、復旧の手順は何か               |
| 設定と inventory             | どの設定とリソース関係を宣言しているか     |
| 実行時の確認とデプロイの証拠 | 今マシンで何が動き、期待どおりか           |

ADR が必要かを考えるとき、私は「将来この選択を変える際に、当初の制約や代償を知る必要があるか」と問います。サービス境界、データモデル、権限、長期的な依存関係は、通常は記録する価値があります。一時的なトラブル調査は issue に残し、具体的な操作手順は runbook で維持できます。

## homelab-ops が MADR Light の変種を採用する理由

homelab-ops は ADR-0026 で、自分たちのテンプレートを MADR Light と呼んでいます。Context、Decision、Consequences、Rejected alternatives を残し、問題の規模に応じて詳しさを調整します。配布アーキテクチャの変更には詳細な比較が必要ですが、小さなインターフェース上の取り決めなら数段落で足りる場合もあります。

軽量なテンプレートを選ぶのは、記録の負担を決定の規模に見合うものにするためです。短い記録でも、背景、選択、その結果、他の案を採らなかった理由は説明する必要があります。結論だけでは、新しい制約が生じたときに元の決定がまだ適用できるかを判断できません。

テンプレートに加えて、決定の変化を扱う規則も必要です。初期のリポジトリでは、古い ADR に Amendment を追記していました。ADR-0026 はその問題を記録しています。写真パイプラインの ADR では、本文と複数の修正が矛盾するようになっていました。読者は元の決定と後から加えられた修正を組み合わせ、従うべき内容を再構成しなければなりませんでした。

そこで、この変種にはいくつかの規則を加えています。受け入れ済みの決定本文を実質的に変えるときは新しい ADR を作ること、全面的な置き換えは線形のチェーンにすること、部分的な置き換えでは対象範囲を明記すること、採番・索引・関係の維持はツールに任せることです。これは homelab-ops の設計上の選択であり、MADR がすべてのプロジェクトに求める規則ではありません（ADR-0026）。

## homelab-ops の ADR の構造

homelab-ops の ADR は `decisions/` 配下の Markdown ファイルです。識別情報と状態、決定の本文、ナビゲーションと参考資料の三つで構成されます。

ADR-0049 は以前の hub-spoke 配布方式を、ADR-0059 は git-pull と通知を契機に適用する後継方式を記録しています。後者のファイル名は `adr-0059-fleet-sync-gitpull-ntfy.md` です。0059 は通し番号で、後半が主題を示します。ファイルの先頭には二つの `---` で囲まれた YAML メタデータがあり、front matter と呼ばれます。

```yaml
---
id: '0059'
uuid: 73fa7bc9
title: Fleet distribution — git-pull + ntfy-triggered apply-agent
date: 2026-07-03
status: accepted
original-adr: '0049'
original-adr-uuid: da2bdab9
supersedes: '0049'
supersedes-uuid: da2bdab9
---
```

`id` は日常の参照に使います。`uuid` は本プロジェクトで使う 8 桁の 16 進数の安定した別名で、草稿に正式な番号が付いても変わりません。`title` と `date` は主題と記録日を示し、`status` は決定のライフサイクル上の状態を表します。識別用のフィールドは同じ記録を見つけるために、状態フィールドはその記録をどう扱うかを判断するために使います。

この記録には `original-adr: "0049"` と `supersedes: "0049"` の両方があります。ADR-0049 が直接の前任であり、この変遷の起点でもあるためです。今後 ADR-0059 を新しい決定が置き換えるなら、新記録の直接の前任は 0059 になりますが、チェーンの起点は 0049 のままです。対応する `-uuid` フィールドは、関連する記録の安定した識別情報を照合するために使います。

本文では、フィールドだけでは表せない判断を説明します。軽量な骨組みは、次の四つに重点を置きます。

| 本文の節              | 書く内容                           | 読者が理解できるべきこと                   |
| --------------------- | ---------------------------------- | ------------------------------------------ |
| Context               | 問題、制約、決定を促した新しい事実 | なぜ今決める必要があり、どの制約があったか |
| Decision              | 選択、適用範囲、主要な規則         | 何を決め、何がまだ未決定か                 |
| Consequences          | 利点、コスト、受け入れた制限       | 選択から何が生じ、何を負担するか           |
| Rejected alternatives | 検討した案と採用しなかった理由     | 他の実現可能な案が今は適さない理由         |

見出しを機械的にそろえる必要はありません。ADR-0059 は代替案を `Alternatives` にまとめ、設定モデル、健全性の可視化、移行の節も加えています。これらは決定の適用条件と実装上の制約を説明します。継続的に更新する日常の操作手順は、リンク先の runbook に任せます。

ナビゲーション情報は、履歴と現在の入口を結びます。ADR-0049 の front matter と冒頭の注記は ADR-0059 を指し、歴史的な本文には当時その案を受け入れた理由が残ります。末尾の issue、設計文書、関連 ADR からは、議論と実装をさらにたどれます。

この二つの記録の英語全文は、同じ公開 Gist にあります。[ADR-0049](https://gist.github.com/cyber-ayi/bee0dc359a661352ced8152f52f76fee#file-adr-0049-fleet-sync-hub-spoke-distribution-md) と [ADR-0059](https://gist.github.com/cyber-ayi/bee0dc359a661352ced8152f52f76fee#file-adr-0059-fleet-sync-gitpull-ntfy-md) を対照できます。

## 提案から受け入れ済みの決定へ

ADR のライフサイクルは、決定をどう扱うかを表します。`proposed` は提案、`accepted` は受け入れ済みの決定、`rejected` は採用されなかった提案です。受け入れ済みの決定は、後から廃止されたり、新しい決定に置き換えられたりします。

ADR を受け入れるとは、その選択と代償を認めることです。レビューでは、問題が実在するか、制約が十分に整理されているか、代替案を妥当に比較しているか、結果をどう検証するかを判断します。ファイルの完成、CI の通過、番号の取得だけで、この判断が完了するわけではありません。この状態図が表すのはプロセス上の意味です。リポジトリのフィールドが実際の決定を適時に反映できるかは、後述する維持の仕組みにも依存します。

`rejected` と `deprecated` は異なる履歴を残します。前者は受け入れ済みの案にならず、後者は一度有効になった後で適用されなくなったものです。`superseded` はさらに後継の記録を示し、次にどこを読むべきかを伝えます。この違いを残すことで、履歴を知らずに同じ案を何度も提案することを防げます。

ADR-0042 は実際の rejected の例です。監視の表示基盤の最終形として Perses を採用する提案でしたが、冒頭には 2026 年 6 月 30 日に却下され、一度も accepted になっていないと記録されています。その後の方針は ADR-0051 が引き継ぎます。ここに残るのは採用されなかった選択肢であり、かつて確定していた案が後に失効した履歴ではありません。

### pending は採番待ちを表す

`pending` が表すのは別の事柄です。番号の割り当てがまだ終わっていません。`id: pending` や `adr-pending-<uuid>-<slug>.md` というファイル名に現れ、`status` の決定状態ではありません。

採番と決定状態を分けることで、並行して草稿を作れます。複数の著者やエージェントが安定した UUID 別名をそれぞれ生成でき、同じ「次の番号」を取り合う必要がありません。通し番号は、マージ後の共通ワークフローが割り当てます。議論中は UUID と草稿のパスで記録を識別します。

| 番号フィールド | 決定状態   | 意味                                                                                        |
| -------------- | ---------- | ------------------------------------------------------------------------------------------- |
| `id: pending`  | `proposed` | 未採番で、決定はまだ議論中                                                                  |
| `id: pending`  | `accepted` | 決定は受け入れ済みで、採番完了を待っている                                                  |
| `id: 0071`     | `proposed` | 採番済みだが、状態フィールドは提案のまま。後述する Music Assistant のチェーン末尾が該当する |
| `id: 0059`     | `accepted` | 採番済みで決定も受け入れ済み。デプロイの進捗は別途検証が必要                                |

新しい主題の草稿では `original-adr: pending` も使い、自分自身がチェーンの起点になることを表します。採番時にはこのフィールドも `id` とともに更新します。既存の ADR を置き換える草稿なら、`original-adr` は元の起点をそのまま引き継ぎ、新記録自身の `id` だけが割り当てを待ちます。どちらの場合も、`uuid` と `original-adr-uuid` はそれぞれの安定した識別情報を保持します。

pending ファイルは一時的に main ブランチへ存在できます。草稿 PR のマージで採番ワークフローが起動し、さらに採番 PR を作ります。後者がマージされて初めて、正式なファイル名と番号が main に入ります。採番待ちは、決定待ちや提案の却下を意味しません。二つの PR の具体的な流れは後で説明します。

デプロイの進捗は、さらに独立した三つ目の問題です。第 09 回では、新しい配布方式の中核実装は存在するものの、fleet 全体の移行は未完了という段階を扱いました。ADR が accepted でも、実装の完了はタスク、デプロイ記録、受け入れ確認の証拠から判断する必要があります。[Fleet Sync の実装範囲（中国語）](/posts/fleet-sync/)

## 置き換え関係で意思決定の履歴を残す

決定が変わっても、古い記録には価値があります。ADR-0049 は hub-spoke を選んだ背景と代償を、ADR-0059 は判断し直す契機になった事実と新しいトレードオフを残します。置き換え関係で両者を結ぶと、読者は後継を見つけるとともに、なぜ最初から後の案を選ばなかったかも理解できます。

homelab-ops では、全面的な置き換えを線形にします。新しい ADR の `supersedes` が指せる直接の前任は一つだけで、対象は main 上で `accepted` である必要があります。同じ前任から置き換えを分岐させることもできません。そのため、履歴のチェーンが最終的にどこへ至るかを、ツールが一意に答えられます。

| フィールド            | 意味                                  |
| --------------------- | ------------------------------------- |
| `supersedes`          | 現在の ADR が直接置き換える前任       |
| `original-adr`        | チェーンの最初の ADR                  |
| `superseded-by`       | 古い ADR が現在指しているチェーン末尾 |
| `superseded-by-chain` | 途中の置き換え関係をたどるための記録  |

チェーンが延びると、古い ADR の `superseded-by` は新しい末尾を指し、`superseded-by-chain` は途中の経路を残します。同じ記録から、後継の終点を探すことも、変遷を調べることもできます。

古い決定を残すことは、ファイルの全バイトを固定することではありません。過去の決定本文を保持しつつ、置き換え状態、ナビゲーション用の参照、引用、所定の形式の注記は維持できます。歴史的な理由と現在のナビゲーションには、それぞれの役割があります。

### 実例 Music Assistant の三世代の ADR

Music Assistant には、ADR-0009 → ADR-0028 → ADR-0071 という実際の三世代のチェーンがあります。以下の関係と状態は、2026 年 10 月 26 日に確認した記録に基づきます。

ADR-0009 は、a1989 の macOS コンテナ環境にサービスを置き、その制限を受け入れました。ADR-0028 はその後、ポートのバインド互換性を整理し、古い Amendment のネットワーク変更を独立した記録へ取り出しました。ADR-0071 では再生バックエンドとネットワーク要件が変わり、Linux ホスト tp-server、host ネットワーク、Soloist バックエンドを選ぶ内容になっています。

現在のファイルの関係はすでに 0071 まで延びています。0009 と 0028 はどちらも `superseded by ADR-0071` と記され、直接 0071 を指します。しかし 0071 の front matter はまだ `status: proposed` です。図もこの実際の値を残しています。

実線は古い記録から新しい記録へ向かい、記録された置き換えの順序を表します。破線は古い記録からチェーン末尾へ直接移る入口です。実際の `supersedes` フィールドは逆向きに、直接の前任を指します。三つのファイルの値は次のとおりです。

| ADR  | original-adr | supersedes | superseded-by | superseded-by-chain |
| ---- | ------------ | ---------- | ------------- | ------------------- |
| 0009 | 0009         | なし       | 0071          | [0028, 0071]        |
| 0028 | 0009         | 0009       | 0071          | [0071]              |
| 0071 | 0009         | 0028       | なし          | なし                |

0028 と 0071 はそれぞれ直接の前任を持ち、三つともチェーンの起点は 0009 のままです。0009 からは `superseded-by: 0071` で末尾へ直接移れますし、`[0028, 0071]` で途中の変化も確認できます。起点、直接の前任、末尾は異なる役割を担います。

この例には、初期の規則から移行した痕跡も残ります。0028 の本文が変えるのはネットワークの行と対応する結果だけで、他の決定は 0009 を引き継ぎますが、メタデータは全面的な置き換えになっています。古い Amendment を整理して作られたためです。現在同じ範囲の変更をするなら、次節の部分的な置き換えを使うべきです。

0071 の proposed という値は、ライフサイクル維持の現実的な問題も示します。作成 PR #2308 と採番 PR #2311 は、どちらもマージ済みです。移行 epic #2306 に実装記録があり、incident #2297 には、復旧・再設定したインスタンスで 10 月 6 日に Spotify の再生音を確認した記録があります。実作業は進んでいても、状態フィールドは同期されていません。読み取りツールはこの差を見つけられますが、修正には決定の根拠へ戻る必要があります。proposed だけを見て移行が始まっていないとは判断できません。

クエリ結果も、この不一致をそのまま返します。`chain-of 0009` は `0009,0028,0071`、`terminal-of 0009` は `0071` を返します。一方、`status-of 0071` は `proposed` を返し、`is-active 0071` の終了コードは `1` です。チェーン末尾にあることと、accepted であることは独立した結果です。

### 部分的な置き換えで変更しない範囲を残す

元の決定の一部だけを変える際、ADR 全体を失効扱いにすると、まだ有効な内容まで無効にしてしまいます。ADR-0056 が変更するのは、ADR-0034 の workstream の定義と関連する制約であり、他の分類は引き続き有効です。そのため独立した ADR を作り、古い記録の該当箇所に範囲の注記を加えます。古い記録は accepted のままで、全面的な置き換えを示す `supersedes` は空欄にします。

この方法は全面的な置き換えチェーンを単純に保つ一方、部分的な関係を本文の中に残します。今後の改善として、「この部分は今どの ADR が定義するか」を答える、検索可能な範囲索引が考えられます。以下はまだ実装していない設計案です。

新しい ADR に、対象 ADR の安定した UUID、上書きする範囲の識別子、新しい決定の節の位置を構造化して記録します。その関係から、古い記録の案内とクエリ索引を生成します。範囲の識別子は変わりやすい行番号ではなく、決定項目に対応させます。0056 なら、workstream の定義、正本となる資料の入口、CI invariant #3 を別々に登録し、変更の全範囲をカバーする必要があります。

0034 を照会したときには、範囲ごとの読み取り先を返すのが望ましい形です。

| 照会する範囲                                  | 参照すべき決定 | 残すべき説明                                              |
| --------------------------------------------- | -------------- | --------------------------------------------------------- |
| workstream の定義                             | ADR-0056       | stack をまたぐ反復実行可能なパイプラインまたは SOP に変更 |
| workstream の正本資料の入口と CI invariant #3 | ADR-0056       | workflow 文書を参照し、対応するファイルの存在を検証       |
| app、stack、host など他の分類                 | ADR-0034       | 今回の部分的な置き換えの対象外                            |

クエリは、全面的な置き換えチェーン、部分的な上書きの一覧、記録の状態、本文の位置を返す必要があります。受け入れ済みの上書きは有効な結果へ含め、proposed は未確定の変更として分けます。同じ範囲に複数の有効な決定があり、優先関係を確定できない場合は、日付や番号で一つを選ばず、競合を報告します。後継自体が置き換えられる際には、元の上書き範囲を引き継ぐかも明示する必要があります。

CI では、対象と範囲が存在するか、関係が循環していないか、上書きが競合していないか、生成物が宣言と一致するかを検証できます。範囲自体が正しいかは、引き続きレビューが必要です。まず 0034／0056 の組で設計を検証し、その後に他の記録を移行できます。未登録の部分的な関係には明示的な案内を出し、元の注記へリンクします。上書きが重なって組み合わせて読むのが難しくなったら、有効な決定を新しい完全な ADR にまとめ、レビュー後に全体を置き換えます。

## ADR の仕組みをどう自動化するか

記録と関係は継続して維持する必要があります。homelab-ops は Markdown に決定を保存し、スクリプトで採番とナビゲーションを維持し、CI で明確な制約を検証します。README とチェーン索引は ADR から生成し、手作業の一覧を別々に管理する負担を減らします。

### 草稿の生成と番号の割り当て

`adr-new.py` は 8 桁の 16 進数 UUID を生成し、既存のチェーン索引と照合して衝突を確認します。新しい主題には、本文の骨組みと自分自身を指す起点の仮値を用意します。置き換え用の草稿は元の起点を引き継ぎ、直接の前任を記入し、前任の本文をコピーして節ごとに修正できるようにします。フィールドの漏れを減らし、元の決定との差も確認しやすくします。

```bash
python3 tools/adr-new.py example-topic
python3 tools/adr-new.py --supersedes NNNN replacement-topic
```

2 行目の `NNNN` は置き換える実際の ADR 番号です。生成器はまずローカル索引から対象の状態を確認します。草稿の作成後に main が変わる可能性があるため、PR 検証でもマージ基準に照らして再確認します。

pending ファイルが `main` に入ると、`adr-assign.yml` が採番を直列に実行します。各ファイルが最初に追加された時刻で並べ、現在の最大番号の次から順に割り当てます。同じ時刻ならファイル名で並べ、順序を再現可能にします。

採番ツールはファイル名を変更し、`id` と新しい主題の起点の仮値を置き換え、タイトルを更新し、リポジトリ内の pending パスと `ADR-<uuid>` 参照を書き換えます。安定した UUID と決定状態は保持します。番号を取得しても、proposed が自動的に accepted になることはありません。

### 置き換えチェーンと参照の自動維持

新しい記録に `supersedes` があれば、`adr-supersede.py` が前任とその祖先の状態、末尾の ID と UUID、履歴の経路、冒頭の案内を更新します。最初の置き換え日は保持し、チェーン更新日は更新し、起点は変えません。これにより古い ADR は履歴の経路を残しつつ、新しい末尾を直接指せます。

続いて `adr-supersede-sweep.py` が、指定範囲の runbook、文書、ADR 参照を走査し、古い参照の隣に後継番号を含む HTML コメントを加えます。元のリンクを残し、著者やソースを読むエージェントに適用可否の確認を促します。通常このコメントは描画後の本文には表示されません。また、スクリプトが参照を削除すべきか書き換えるべきかまで判断したことにもなりません。

最後に `adr-chain-gen.py` が front matter から `.terminal-map.json` を再構築し、起点、メンバー、終点を計算して分岐と循環を検証します。`adr-readme-gen.py` はその結果から閲覧用の索引を更新します。派生ファイルは照会・閲覧の入口を提供し、決定内容そのものは ADR に残ります。

### 二つの PR で一度の採番を完了する

採番ワークフローは作業ブランチで変換を行い、`adr-verify.sh --no-pending` を実行します。未採番ファイルと関連する検証エラーが残っていないことを確認して、自動 PR を作ります。この PR がマージされて初めて、正式な番号が main に入ります。

自動変換は PR の diff として残り、レビューと CI の入口も維持します。ワークフローは自動マージの有効化を試み、利用できなければ手動マージを待ちます。直列実行は割り当て時の競合を減らしますが、PR の生成とマージは別の段階であり、PR 検証で結果を確認する必要があります。pending ファイルがなければ採番ジョブは終了します。検証に失敗すると採番 PR は作らず、修正後に再実行できます。

### CI の各層が検証する制約

PR ワークフローは検証を `adr-corpus` にまとめます。通常の PR 検証は pending ファイルを許可し、採番ワークフロー末尾の `--no-pending` は採番がすべて完了していることを求めます。同じ検証器が、段階ごとに異なるモードで正当な状態を確認します。

| 検証の層       | 機械的に確認する内容                                                                          | 防ぎたい問題                                             |
| -------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| ファイルと採番 | 新規ファイルは pending 名を使い、番号、UUID、必須フィールド、状態値が規則に従う               | 手動での番号の取り合い、識別情報の重複、フィールドの欠落 |
| 関係と基準     | 前任がマージ基準で accepted、既存の起点は不変、チェーンに分岐や循環がない                     | 失効した前任からの別分岐、チェーンの起点の書き換え       |
| 本文の変更     | 保護対象の本文を基準と比較し、新しい Amendment 節を禁止、所定の関係注記と参照の書き換えを許可 | 記録済みの決定と理由を同じ場所で変更すること             |
| 派生ファイル   | チェーン索引と README を再生成して Git diff を比較                                            | 本文と索引の不一致、生成結果の手動変更                   |

関係と本文の検証には、PR の実効的なマージ基準が必要です。今回の変更と、すでに main にある変更を区別するためです。派生ファイルは再生成後の Git diff で確認し、差が残れば、著者が ADR と一致する生成結果をコミットします。

`adr-corpus` はすべての PR で実行します。ADR と無関係の変更は素早く通過し、パスフィルターでワークフロー全体を省略しません。必須チェックが必ず結果を返すようにし、無関係な PR が現れないチェックを待ち続けることを防ぎます。

### 状態が proposed のままになる理由

自動採番と決定の受け入れは別です。現在のワークフローは `supersedes` があると置き換えチェーンを維持し、新記録が accepted であることを追加条件にしていません。R1 が確認するのは基準上の前任の状態です。そのため、番号とチェーンは更新されても、新記録は proposed のままになり得ます。Music Assistant がその例です。

別のケースとして、PR がまだマージされていない場合があります。2026 年 10 月 26 日時点で、ブラウザー移行 PR #2353 は未マージでした。Helium ADR は `id: pending` と `status: proposed` の両方を持ち、D1–D7 の個別の判断は運用者の確認待ちでした。方向性は議論されていても、具体的な取捨選択と main 上の記録がまだ収束していません。

したがって proposed を見たら、三つを区別する必要があります。決定自体が確認待ちなのか、accepted への更新がマージ待ちなのか、関連 PR はマージ済みでも状態フィールドが更新されていないのかです。proposed と書かれた草稿をマージしても、自動的に accepted にはなりません。

状態フィールドが実際の決定からずれる問題は、issue #2231 で追跡されています。当時のスナップショットには proposed が 14 件あり、その複数に本番での実行の証拠がありました。再レビューでは後継の状態検証の欠落を確認し、まず過去の決定を照合してから機械的な検証を加える方針が示されました。本稿の確認時点でも issue は未解決で、該当するライフサイクルの確認を待っていました。

修正には順序が必要です。レビュー時点で「後継が proposed のままではならない」という制約を加えると、0032、0033、0046 などの既存記録が違反になります。すぐ有効にすれば、過去のデータが検証を妨げます。決定の証拠に従って状態を修正し、その後で検証と回帰ケースを加え、proposed のプロセス上の意味を明文化すべきです。本番で稼働していることは照合の手がかりですが、一括で accepted にする根拠にはできません。

ここで、[第 05 回「PR レビューが多すぎる！」](/ja/posts/pr-review-too-many/)で述べた分担に戻ります。エージェントは証拠を整理し、状態の差を見つけ、修正とテストを準備できます。人が確認するのは、まだ決まっていない範囲と代償です。確認後は、受け入れの根拠、状態変更、それを含む PR を一緒に追跡し、main と決定が一致するまで進めます。同じ判断を繰り返す負担を減らし、読むたびに同じ質問をし直すことも避けられます。

## 人とエージェントが決定を正しく読むために

文書が増えるほど、読む経路が重要になります。検索結果は古い runbook、過去の ADR、セッション記録から来るかもしれません。キーワードが一致しても、現在適用できるとは限りません。

homelab-ops は `.terminal-map.json` を生成し、必要な情報を照会するツールを提供します。今回の設定配布の変更なら、リポジトリのルートで次を実行できます。

```bash
python3 tools/adr-chain-query.py terminal-of 0049
python3 tools/adr-chain-query.py status-of 0059
python3 tools/adr-chain-query.py is-active 0059
```

最初のコマンドはチェーン末尾を探し、二つ目は記録の状態を読み、三つ目は状態が `accepted` かを終了コードで示します。小さな照会により、エージェントはまず位置を特定し、その後で必要な本文だけを読めます。索引全体と過去の全記録をコンテキストに入れる必要はありません。

それでも、チェーン末尾はどこか、記録は accepted とされているか、実システムへ反映されたかという三つの問いは分ける必要があります。README の Active グループには proposed も含まれるため、分類だけで受け入れ済みとは判断できません。部分的な置き換えは現在、範囲の注記で表現しています。将来の範囲索引は、その読み取り先も一緒に返すべきです。

人とエージェントに共通する読み方は、候補の ADR を探し、後継と部分的な上書きを特定し、状態と決定の根拠を確認し、runbook と稼働の証拠を組み合わせて次の行動を判断することです。フィールドと証拠が食い違ったら、対応する追跡タスクへ差を戻して一度修正を進めます。毎回のタスクで推測し直す必要はありません。

## 維持できる最小限の仕組みから始める

個人プロジェクトは、小さな取り決めから始められます。重要な決定には背景、選択、代償、採用しなかった案を書き、状態を明記します。決定が変わるときは古い記録を残して後継へリンクします。これだけでも、将来理由を探し直すコストを減らせます。

並行した草稿で番号の衝突が起き始めたら自動採番を加えます。古い参照が繰り返し読者を誤らせるなら、置き換えの警告と索引を加えます。規則が何度も破られるなら、明確な制約を CI に組み込みます。

自動化を一段加えるたびに、ツールの保守と PR も増えます。投資する価値があるのは、衝突、漏れ、誤読を繰り返し起こしている工程です。記録の粒度、部分変更の範囲、選択肢を比較し直す必要があるかは、引き続き実際の問題に即して判断します。

私がこの仕組みに残したいのは、後から使い続けられる判断の根拠です。現在の決定から理由をたどり、過去の決定から後継を探し、状態のずれを見つけたら修正先へ進めることです。本文がトレードオフを保存し、関係フィールドが履歴をつなぎ、ツールが反復可能な部分を維持します。後の保守担当者は既存の選択を理解し、それを変える根拠も持てるようになります。
