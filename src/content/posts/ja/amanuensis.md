[Amanuensis](https://portfolio.fnpg.me/projects/amanuensis/) は、[Yaaa](/ja/posts/yaaa/) の中で情報収集、トリアージ、通知を担当するサブシステムです。さまざまな入力を記録に整え、注目すべき情報を判断し、対象者、機密度、通知のタイミングに従って届けます。最初のアプリケーションである digest は、流れ続けるメールを、少数の有用な通知とダイジェストにまとめます。

情報を受け取ってから、今何に注目すべきかを理解するまでには作業が残ります。メール、購読、メモ、タスクの各ツールには、それぞれ確認すべき受信箱があります。各項目を要約しても、画面の切り替えや割り込みまで減るとは限りません。

本文では全体像、コンポーネント構成、情報統合の順に説明します。**メール収集、トリアージ、digest 配信には稼働記録があります。タスクやメモなどの完全な接続、異なる情報源にまたがるイベント統合は、個別の実装と受け入れ確認が必要です。** 図は責務とインターフェースを示しており、すべての情報源が接続済みという意味ではありません。イベントの例は完全な架空のものです。

## 一通のメールが通る処理

地域イベントを購読しているとします。メールでは開催日が土曜日へ変更されましたが、公開ニュースレターには古い日付が残っています。新着の取得、出所と時刻の保持、重要性の判断、通知時刻の選択、配信失敗後の処理は、それぞれ異なる仕事です。

二つの資料が同じイベントを指すと判断するには、実体の対応付け、時間の比較、証拠の矛盾処理も必要です。同じデータベースに保存した段階では、収集上の統合までしか終わっていません。

Amanuensis は主経路を **gather / judge / deliver、つまり収集・判断・配信**に分けます。各段階が入力、結果、状態を持ち、利用するアプリケーションが接続します。

矢印はデータの依存関係です。digest はストアの照会、変換、独立したスケジュールによって接続します。一つのプロセス内で三つの kit を順番に実行する必要はありません。収集と判断を定期実行し、配信はダイジェストの時間帯まで待てます。後段が一時的に利用できなくても、上流の記録は保持できます。

## 三つの kit の構成

プラットフォームは、個別にインストールとテストができる Python package で構成されます。

```text
packages/
  ingest-kit/    # 適応、正規化、カーソル、同一情報源内の重複抑制、保存
  triage-kit/    # 判断入力、ポリシー、モデル経路、構造化された判断
  push-kit/      # チャネル選択、配信検査、キュー、配信台帳
```

triage-kit は ingest-kit を import せず、push-kit も前の二つを import しません。アプリケーションが収集記録を判断入力へ変換し、有効な判断を元の記録と関連付けて配信入力を作ります。アダプター、推論先、チャネル実装を個別に変更できる一方、フィールドの変換と契約の互換性はアプリケーションが維持します。

| コンポーネント          | 入力と出力                               | 管理する状態                           |
| ----------------------- | ---------------------------------------- | -------------------------------------- |
| `ingest-kit`            | 情報源アダプター → 正規化 Item           | カーソル、ハッシュ、記録、実行監査     |
| `triage-kit`            | 入力 + ポリシー → structured verdict     | 判断、モデル版、再試行、例外           |
| `push-kit`              | 配信入力 + チャネル一覧 → 配信または保持 | キュー、試行、拒否、明示的な反応の状態 |
| digest アプリケーション | 照会、変換、関連付け、スケジュール       | 配備設定、非公開ポリシー、接続         |

### ingest-kit：出所の違いを保持して形を揃える

アダプターが情報源のプロトコルを扱います。基本記録は `source_id`、`external_id`、タイトル、著者、時刻、本文、必要なメタデータを持ちます。元の識別子を残すことで、後段から `(source_id, external_id)` で同じ項目を参照できます。

再開位置を表すカーソルもアダプターが管理します。エンジンは opaque cursor を保存して返すだけで、増加する整数とは仮定しません。メールの UID、同期 token、時刻を共通の保存インターフェースで扱えます。ただし、新たな情報源にはアダプターの実装、権限確認、更新や削除など固有の意味の処理が必要です。

現在の内容ハッシュは、**指定フィールドによる同一情報源内の重複抑制**です。異なる情報源が同じ出来事を示すことや、本文全体の意味的な一致までは判定しません。digest は収集と判断を分離しており、収集時にモデル呼び出しを必要としません。

### triage-kit：解釈を確認できる判断へ変える

項目ごとの一回のモデル呼び出しで、`priority`、`audience`、`summary`、`key_entities`、`action_required` を生成します。この structured verdict が後段のポリシーへの入力になります。日程変更メールは注意に値すると判断されても、対象者は個人のままかもしれません。イベント名と日付が抽出されても、別の記録と統合できた証拠にはなりません。

ポリシーのインターフェースには、重要性の基準、対象者の規則、モデル選択の拡張点があります。基本実装では設定で規則のテキストを変更できます。現在のカレンダー、在席状態、計画に応じた動的判断には、追加のコンテキスト接続と実装が必要です。拡張点の存在だけで、計画を継続的に理解しているとはいえません。

機密度は推論前に利用可能な経路を決めます。高機密の内容は信頼された local-only の経路だけに送ります。接続できなければ `deferred` とし、後で再試行します。クラウドへ切り替えません。priority の欠落や不正は `degraded`、再試行上限後は `dead` とし、正常そうな値を作りません。要求したモデルと実際に応答したモデルも区別して記録し、確認できない出所は不明のまま残します。

### push-kit：重要性を適切な割り込みへ変える

priority は `must`、`should`、`fyi`、`ambient`、`drop` の五段階で、緊急性と情報価値を示します。**実際の配信時刻は配信ポリシーが決めます。** bundled default は digest-first で、即時配信には明示的な設定が必要です。モデルが `must` を返すだけでは即時通知になりません。

ポリシーは即時配信、次のダイジェスト時間帯、静かな保持を選べます。`drop` は配信せず記録のみを残し、`ambient` は後で見返すために保持できます。操作の権限は与えません。`action_required: true` も、利用者の注意が必要かもしれないという判断です。

送信前にエンジンが独立して検査する条件は二つです。チャネルの対象者が項目の対象者と一致すること、高機密の項目が非クラウドと設定されたチャネルだけへ進むことです。ダイジェストの flush も同じ検査を通り、台帳に保存された項目の属性を使います。対象者不明は personal、機密度不明は high とします。チャネル設定の信頼性と下位層の隔離は、別途正しく保つ必要があります。

ローカル推論を終えても、要約をクラウドへ送ってよいことにはなりません。適切な非クラウドのチャネルがなければ保持して配信しません。利用可能な `--dry-run` では、外部送信や配信状態への書き込みをせずに経路と検査を予行できます。

## 仕組みと個人の規則をどこへ置くか

再利用するコードに、実際の家族、アカウント、チャネルの情報を混ぜないため、三層の policy を使います。

| 層                | 内容                                                     | 管理場所                            |
| ----------------- | -------------------------------------------------------- | ----------------------------------- |
| T0 engine         | 保存、再試行、インターフェース、モデル経路、配信検査     | プラットフォーム package            |
| T1 defaults       | 汎用の重要性基準、プロンプト、既定の経路                 | プラットフォームの bundled defaults |
| T2 private policy | 実際のメンバー、対象者分類、チャネル対応、個人の修正規則 | 利用側の非公開設定やプラグイン      |

これはコードと設定の境界です。エンジンのソースに個人の識別情報や経路を埋め込みませんが、実行時には個人データを扱います。プラグインもホストプロセスの権限で動きます。プロセス隔離やログの秘匿が自動的に得られるわけではありません。

機密ポリシーをソースから分離すると、再利用や将来の公開に必要な整理を減らせます。現時点でオープンソース公開済みであることや、実行記録を公開できることは意味しません。

### 収集の統合：一緒に照会できる記録

共通の形に整えても、元の識別子は維持します。情報源の識別子によって、二つのシステムが偶然同じ ID を使っても誤って一致させずに済みます。時刻、出所、実行記録は、どこからいつ取得したかを説明します。

架空の変更メールとニュースレターは、まだ別々の記録です。違いを消さずに、共通の照会と判断の対象にできます。

### 判断の統合：証拠とコンテキストを結ぶ

確立した経路の中心は、規則と単一項目から結果を作るトリアージです。「土曜日が新しい予定で、金曜日は古い」と結論するには、同じイベントかを確認し、公開時刻と出所の権威を比較し、矛盾を保持して根拠を説明する必要があります。

現在の計画、情報源間の関連、人による修正は有用な拡張です。エンティティのフィールド、ポリシーのインターフェース、記録の識別子は接続点になりますが、それだけでイベントのクラスタリング、矛盾解消、長期記憶が完成するわけではありません。

結合後も情報源の制約を継承する必要があります。高機密の資料を含む要約は対応する機密度を保持すべきで、短くなったことを理由に下げるべきではありません。これは今後の結合処理に対する要件であり、各変換で実装と検証が必要です。現在の項目ごとの配信検査だけでは、派生チェーン全体の制御を代替できません。

### 表示の統合：複数の到着を一度の閲覧にまとめる

意味的な統合がなくても、時間帯ごとの収集、並べ替え、まとめ配信によって割り込みを減らせます。キューと配信台帳は、取得済み、判断済み、送信済みを区別します。

同じ時間帯に入った項目が、同じ話題とは限りません。任意の自然言語による概説も、機械的に作った項目インデックスの代わりにはなりません。概説に失敗しても基本のインデックス行を配信でき、文章生成の成否が時間帯全体の可用性を決めずに済みます。

台帳は情報源、項目、チャネルで配信を関連付け、再試行の抑制や診断を支えます。ただしデータベース更新と外部送信の間には結果不明の状態が起こり得るため、チャネルに応じた照合が必要です。台帳の存在だけで、すべてのチャネルに厳密な exactly-once を保証できません。`sent`、`read`、`acked` は、それぞれ配信記録、明示的な閲覧信号、明示的な確認を示し、現実のタスク完了は証明しません。

## 修正を次の判断へつなぐ

review card では「同意」「もっと上」「もっと下」「この種類は不要」といった低負担の信号を受け取り、feedback ledger に保存します。繰り返される修正から override rules の候補を整理し、人が確認してから次のトリアージへ適用できます。モデルによる解釈と、長期的な規則の変更には別のレビュー段階があります。[作品集の技術説明](https://portfolio.fnpg.me/projects/amanuensis/technical/)

このループはトリアージの修正を扱います。カード、取得、候補生成、承認後の適用は個別に検証する必要があります。図示されたループだけでは本番接続の完了を証明できず、Yaaa 全体の SOP 学習やツール間記憶ができたことにもなりません。

## 現在の境界と次の確認

既存の記録では、2026 年 7 月にメール収集、トリアージ、digest 配信の稼働経路が成立しています。本文は 2026 年 10 月 28 日に記した仕組みの説明で、公開日が新たな稼働確認日ではありません。作品集の[ウォークスルー](https://portfolio.fnpg.me/projects/amanuensis/walkthrough/)は、実システムから採取し展示用に再構成した資料です。記録の変化を理解する助けにはなりますが、受け入れ確認の代わりにはなりません。

| 範囲                                         | 本文での扱い                                      |
| -------------------------------------------- | ------------------------------------------------- |
| 三つの kit と digest 接続                    | 実装とメール経路の稼働記録あり                    |
| メール以外の情報源                           | 拡張可能だが、個別の adapter と本番接続を確認する |
| 現在の計画を使う判断、情報源間のイベント統合 | 追加の実装と検証が必要                            |
| トリアージのフィードバック                   | 設計と展示があり、接続ごとに確認する              |
| 汎用対話、長期記憶、承認後の操作             | Yaaa 全体の統合に属し、別の完成条件を持つ         |

次に有用なのは、変更されたイベントへ戻る検証です。関連記録を見つけ、新旧の情報と矛盾を示し、通知する理由を説明して、許可された経路で届けられるか。カレンダーまで変更するなら、Yaaa の操作経路へ進み、承認と実行結果を別途確認します。
