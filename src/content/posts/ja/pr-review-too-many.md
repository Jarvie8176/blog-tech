_AI を流体のような知能と捉え、要件・制約・受け入れ条件で実装を形にする。_

Homelab の設定、スクリプト、保守を AI に任せると、変化はすぐ GitHub に現れます。確認すべき実装、判断すべき設計、処理すべきプルリクエストが一緒に増えていきます。

AI は複数の作業を同時に進められますが、結果が適切かを判断する人は必要です。すべての変更が私の逐行レビューを待つなら、コーディングで浮いた時間が、そのままレビューに移るかもしれません。保守の負担を減らしたかったのに、自分がシステム全体のレビュー待ち行列になってしまいます。

実装できる量が増えたとき、人はどこで判断し、プロジェクトはどこで立ち止まるべきなのでしょうか。

私は AI を、**流体のような知能**として捉えています。大まかな方向を示すと、探索し、足りない部分を補い、部品をつなぎ、実装の細部を埋めてくれます。私が用意するのは「金型」です。要件、設計の意図、インターフェース、破ってはいけない制約、そして完成品をどう判定するか。その型を AI に満たしてもらい、射出成形するように実装を形にして、監査や実際の使用を通じて仕上げます。

金型自体も更新が必要です。実装によって見落としていた要件が分かったり、受け入れ時の確認で設計が用途に合わないと分かったりします。成果物を磨き続けるか、型から作り直すかも、このプロセスで判断することです。AI は空白を機能、抽象化、手順で埋めるのも得意なので、型が実際の必要以上に複雑になっていないかも見なければなりません。

## 金型を実際に使える制約にする

Homelab Ops では、この金型がいくつかの場所に分かれて存在しています。

Issue は解決する問題と完了条件を示し、epic は関連作業をまとめます。設計文書はシステムの分け方を、インターフェースは部品間で情報を交換する方法を説明します。PR はレビュー対象の変更を固定し、CI は機械的に判定できる条件を確認します。運用記録と受け入れ結果は、その変更が実際に何をしたかを残します。

これらは互いに整合している必要があります。要件がチャットにしか残っていなければ、次の実装で抜け落ちるかもしれません。インターフェースについて文書とコードが違う意味を持っていれば、後続の部品も異なる理解で育っていきます。

自由に工夫できる範囲も分けます。画面の文言や配置はプロトタイプで議論できます。一方、データをどこに書いてよいか、操作がどの対象に影響してよいか、失敗からどう復旧するかには、もっと明確な境界が必要です。プログラムで確認できる制約は、プログラムに確認させます。意味の理解や取捨選択が必要な部分は、AI や人が判断します。

残したいのは、ほかの人や次のセッションも使える作業条件です。目標、入力、許される変更、受け入れ方法が分かれば、その先を進められる状態にします。

## 複数のエージェントで実装の反例を探す

実装と同じように、レビューも並行して進められます。詳しい確認に値する変更では、並行処理、リソース消費、権限とデータ公開、障害復旧、あるいはインターフェースの生成側と利用側など、異なる視点から反例を探してもらいます。

実際には、こうした視点を細かい指示にして渡す必要はありません。普段は **「PR #xxx を監査して」** と頼むだけです。監査の視点を選び、作業を分け、ソースコードを読み、発生条件を探し、再現し、指摘を集約して判断する。その知的作業をモデルに任せます。具体的であるべきなのは、返ってくる指摘と根拠です。最初の依頼は短くて構いません。

そうできると考えるのは、クラウド側の大規模モデルが、十分な量のベストプラクティス、設計パターン、失敗の経験から学んでいるからです。進歩の速さも推論能力も、私が実際に任せている作業にはすでに十分です。自分の実践で必要を満たしているので、複雑な思考をモデルに預け、トークンと電気代を知的労働と交換しています。これは現在の用途で得た結果に基づく判断であり、適切にできたかは、監査の根拠と使用時のフィードバックで確かめ続けます。

目標は、対抗的なレビューを何度も繰り返してモデルに不足を埋めてもらい、その後は実際の使用で見つかった問題を次の改善へ返すことです。人は **判断が必要な地点を理解し、要件を確認すること** に集中します。なぜ変更が必要か、どの取捨選択を受け入れるか、結果が用途に合っているかを判断します。

各エージェントの指摘は、集約し、重複を除き、結論を判断する必要があります。写真キャッシュの監査では、あるレビュー担当は同時実行による破損を否定し、別の担当は発生すると判断しました。調整役が実際に再現を試し、書き込み時にファイルが切り詰められる時間帯があると確認しました。結論を決めたのは、発生手順と観測した挙動でした。

指摘は P0 から P3 に分けて優先順位を付けられます。以下はこの記事で使うレビュー上の目安で、実際の重大度は影響範囲と発生条件から判断します。

| 区分 | 主に確認すること                                         | 対応                                                   |
| ---- | -------------------------------------------------------- | ------------------------------------------------------ |
| P0   | 復旧が難しい重大な損害や、重要な境界の突破につながるか   | 関連作業を止め、影響を抑えて修正する                   |
| P1   | 中核機能を妨げるか、重要な運用・復旧の約束を無効にするか | 該当段階を進める前に解決する                           |
| P2   | 特定条件で信頼性、互換性、保守に問題が起きるか           | 今回の受け入れ範囲に応じて修正するか、明示して追跡する |
| P3   | 読みやすさ、見せ方、局所的な保守性を改善するか           | 重要な指摘を埋もれさせず、価値に応じて予定する         |

四つの区分をすべて埋める必要はありません。指摘には根拠が必要です。再現できていない懸念は、確認事項として残せます。確定した不具合に見せる必要はありません。

修正した部分も再レビューします。一つの発生条件だけを塞いでいるかもしれず、別の問題を生むこともあります。検証ツールも間違えます。古い版を調べる、別のプレビューサーバーにつなぐ、新しいサンプルがテスト対象に入っていないといったことが、誤った結論につながります。どの版と対象を確認したか、その検証が目的の誤りを検出できるかも示す必要があります。

複数の賛同は手掛かりになります。独立した反例と実行時の根拠があれば、結論をより判断しやすくなります。こうした方法は複数の作業で使っていますが、共通の監査 SOP とツール化は引き続き整理している段階です。

## AI が増やす複雑さにも上限を設ける

AI はコードや文書を作るコストを下げる一方、システムに余分な構造が生まれやすくもします。局所的な修正が、汎用インターフェース、設定層、プラグイン、移行ツール、新しい管理手順へと広がることがあります。一つずつ用途を説明できても、組み合わせると、この Homelab が本当に必要とする範囲を超えるかもしれません。

分析の複雑さをクラウドモデルに任せても、そのすべてを恒久的なフレームワーク、設定、承認手順にする必要はありません。監査中の探索はトークンを消費して終えられますが、残した部品や手順には、その後も保守のコストがかかります。

増えた複雑さには継続的な保守が必要です。部品が増えれば、配備、更新、障害調査、復旧を考えます。設定項目が増えれば、理解し検証する挙動も増えます。承認手順が増えれば、人の注意も使います。AI が保守を手伝っても、理解、引き継ぎ、ツール交換のコストはシステムに残ります。

そのため設計をレビューするときは、次の点も確認します。

- 追加する構造は、すでに起きた問題、または近く起きる明確な根拠のある問題のどれを解決するか。
- 既存の部品と、もっと単純な実装で今回の要件を満たせないか。
- 実行時の依存、保守手順、人が理解すべき概念がどれだけ増えるか。
- この層を延期または削除すると、どんな実用上の能力を失うか。

共通の操作基盤でも、この取捨選択をしました。既存の配布手段を再利用し、ツール間の設定変換やコード生成のために、別のフレームワークを作る案は明確に退けています。必要だったのは、異なるツールから共通操作を見つけて呼び出せることです。考えられる拡張を先回りして全部作る必要はありませんでした。

複数エージェントによる監査にも範囲の管理が必要です。境界条件や精巧な実装案は、際限なく追加できます。提案は実際の影響、発生条件、今回の目標に照らして判断します。データの完全性、権限、復旧、中核的な挙動は深く確認します。局所的な命名、利用者のいない拡張点、好みだけによる実装の交換は、保守上の価値に応じて扱い、完成までの作業を無限の磨き込みにしないようにします。

現在の段階には、レビューの終了条件を設けたいと考えています。進行を妨げる問題が解決し、合意した受け入れ条件を満たし、残るリスクと後続作業の置き場所が決まっていることです。新しい重要な根拠が出れば、再び調べます。必要な細部を保ちながら、価値の小さい論点でレビューが回り続けるのを防ぎます。

金型そのものにもコストがあります。不要な依存、分岐、手動の調整を減らし、追加する複雑さには具体的な用途を持たせ、用途を失った部分は単純化したり取り除いたりできるようにしたいのです。

## 判断が必要な地点までプロジェクトを進める

目標と許可された範囲が明確なら、AI は一続きの作業を進められるはずです。現状を調べ、情報を補い、案を出し、実装、テスト、修正を行って、レビューできる結果を残す。コマンドのたびに「続けますか」と聞けば、不要な待ち時間が増えます。

人に届いてほしいのは、取捨選択が必要な問いです。次の操作でデータ公開の範囲が広がるのか、合意済みのインターフェースを変えるのか、継続的な運用費が増えるのか、既存サービスに影響する変更を実行するのか、といったことです。

そのためには tracker で作業の状態が分かる必要があります。確定した要件、実装上の細部、ほかの作業に阻まれているタスク、判断を待つ操作を区別します。後続タスクは先に作り、開始を妨げる条件を記録して、条件が満たされるまで待機させられます。

判断が必要な地点では、AI は選択に十分な材料を持ち帰るべきです。観測したこと、実行可能な選択肢、推奨、コスト、受け入れると進められる作業を示します。見つかったのが実装の不具合で、修正が元の目的と許可範囲に収まるなら、そのまま解決を続けます。

これは、私が高めたいプロジェクト推進の能力です。継続実行、承認、タスク復旧の能力はツールごとに異なるので、実際に進める範囲は、その作業で具体化する必要があります。独立してできる準備を先に済ませ、人の注意を、本当に方向転換が必要な場所へ残します。

## 要件を発見し、型から作り直すかを判断する

明確に書かれたタスクでも、誤解に基づいていることがあります。AI はその誤解も素早く実装できます。速く進むほど、早い段階で形を見せて方向を確認する価値があります。

Homelab の監視画面でも、このずれがありました。「glance」は独立したポータルを指す場合も、Grafana 内のダッシュボードを指す場合もあります。ある作業では先にポータルが変更されましたが、明確になった要件は、ほかのダッシュボードで注意が必要な項目を Grafana のアラート概観に動的に集約することでした。無関係な変更を戻し、実際の対象画面を中心に実装し直す必要がありました。

問題はコードを書く前からありました。ユーザーがどの入口を使い、何を判断したくて、どんな情報が足りず、何があれば役に立つのかを確かめる必要があります。名前が同じことや実装が簡単なことだけでは、タスクを理解したとは言えません。

使って初めて分かる問題もあります。ダイジェスト配信では、流入量が通知枠で処理できる量を上回る状態がありました。メッセージを増やせば滞留の一部は緩和できますが、読む負担も増えます。その後の設計は、通知面、完全なデータ、詳細を読む画面を分離し、要約の構成、明示すべき内容、フィードバックの対象を改めて検討しました。

これが requirements discovery、要件の発見です。ユーザーの反応、プロトタイプ、運用データで、最初のタスク記述を更新します。方向が合わなければ、要件と設計に戻り、完成した実装の一部を置き換えることも受け入れます。

## Spike と最小限の E2E で、本格的に進めるかを決める

再設計で、すぐに全体を実装する必要はありません。重要な仮定が不確かなときは、小さな実験で、その後の進路を変える問いに答えます。これが spike です。

GitHub への書き込みにセッションの出所を示す印を付ける実験では、CLI のさまざまな本文入力を正しく扱えるか、繰り返し編集しても印が重複しないか、本文を明示しないコマンドの意味を変えないかを確かめる必要がありました。

代用品を使ったテストだけでは足りませんでした。本物の CLI につなぐと、古い末尾注記を取り除く処理が、その後にある有効な本文まで消してしまう挙動が見つかりました。実際の内容を保存できるかという問題であり、印が表示されたことを喜ぶ前に解決すべき欠陥です。

そこで、進行を三つに分けて考えます。

1. **Spike**：重要な問いを固定し、最小限の実装で、成立するかしないかの根拠を探す。
2. **最小 E2E**：代表的な入力を本物の入口から実際の出力まで通し、受け取り側から読み返す。
3. **本格的な実装と運用**：結果に基づいて進路を採用、調整、または断念し、全体の実装、配備、監視、用途に即した受け入れを計画する。

実験の結論には範囲があります。API を一度呼べたことは、その経路が通る証拠にはなりますが、継続運用、更新、復旧、複数人での利用にはまだ答えていません。逆に、重要な仮定を否定する実験結果があれば、そこでプロジェクトを止める価値もあります。

まず判断に役立つ結果を得てから、金型への投資を続けるかを決めたいのです。

## 段階の間に、判断のためのゲートを置く

AI が自律的に進むには、どこで止まるべきかが必要です。Gated decision は、次の操作を明示的な判断や検証条件に結び付けます。

ゲートには異なる役割があります。設計のゲートは方向と取捨選択を決めます。インターフェースを固定するゲートは、部品間の契約が依存できるほど安定しているかを確認します。リリースのゲートは、どの変更を稼働環境へ入れるかを決めます。受け入れのゲートは、観測した結果が当初の要件を満たしたかを判断します。

人の判断と機械的な検証は組み合わせられますが、役割は異なります。CI が通るインターフェースでも、利用側に必要なフィールドを欠いているかもしれません。設計を受け入れても、それだけでノードに配備されたり、ユーザーにとって使えると確認されたりはしません。

Homelab のインターフェース固定の議論でも、テストが通り続ける一方で、対抗レビューがフィールドの意味、必須になる条件、文書のずれを見つけました。実装から実際の入出力を取り出し、生成側と利用側を照合してから、ほかの部品が依存を固定できる時点を決める必要があります。

役に立つゲートは、何を守り、どんな根拠で通過でき、誰が判断し、その後何が許されるかを示します。「承認が必要」とだけ書き、現在の版、対象、操作に結び付けなければ、参加者が別々のものを承認してしまいます。

承認ツールにも同じ確認が必要です。トークンや確認画面があるだけでは、正しい人が正しい引数を承認したことや、タスク復旧後も正しく使えることの証明にはなりません。実際にできている範囲を説明すべきで、「ゲートがある」の一言で承認経路全体を代用することはできません。

意味のある境界にゲートを置くことで、不要な中断も、必要な判断を経ない進行も減らせます。

## ソースを逐行読むより、設計と実装の意図を確認する

実装を AI の監査と自動テストが調べるなら、人は何を読むべきでしょうか。

私が集中するのは、判断が必要な地点を理解し、要件を確認したうえで、設計と実装の意図を見ることです。なぜ変更が必要か、なぜこの進路か、残す既存の挙動は何か、何が変わるか、なぜその検証で結論を支えられるかを考えます。

意図は挙動として説明する必要があります。「キャッシュを追加する」は実装手法の名前です。「同時に要求しても読み手には完全な結果だけを見せ、リソース消費には明確な上限を設ける」なら、確認対象が分かります。「再試行を追加する」も、対象となる失敗、重複書き込みの有無、停止条件、最終的な失敗の見え方を説明する必要があります。

すべての PR でソースを逐行読むことは標準にしていません。代わりに、AI に **要件 → 設計上の選択 → 実装箇所 → 観測した結果** の関係を説明してもらいます。確かめる必要があれば、その根拠からコード、テスト、稼働状態に戻れるようにします。影響の大きい変更には、追加のコードレビューや専門分野のレビューも考えられます。

私が判断しやすい PR には、次のことが書かれていてほしいと思います。

- 解決する実際の問題、選んだ案、その取捨選択を受け入れる理由。
- 増える複雑さに価値があるか、同じ要件を満たす単純な方法がないか。
- 変わる挙動、影響する対象、復旧や互換性のコスト。
- AI の監査で見つかったこと、その対応、まだ結論が出ていない判断。
- 受け入れで確認した入力と挙動、実際に使って私が確認すべきこと。

ソースコードは、引き続き実装を検証する重要な対象です。私は金型と成果物の関係に注意を向け、コードを読めるツールに実装の細部を調べてもらいます。説明が流暢でもテストが多くても、実際の挙動で確かめる必要があります。

## 受け入れとフィードバックで、次の仕上げにつなぐ

PR をマージした後も、変更が稼働環境へ届いたか、ユーザーが最終的に何を受け取ったかを確認します。

写真処理の E2E 作業では、一つの教訓が残りました。限定的な転送確認は終わり、未完了の部分も正直に記録されましたが、ユーザーが保存先を確認する前に、転送したテスト用コピーを削除してしまいました。その後の受け入れと引き継ぎに必要な対象が失われたのです。

欠けていたのは、依頼全体の終点でした。選んだデータがどの段階を通り、最終的にどこへ保存され、誰の確認がまだ必要で、いつ削除できるかを定める必要がありました。

そのため、受け入れは実際の用途から書きます。通知なら、期待するトリガーから正しい受信先の読めるメッセージまで。写真なら、合意した保存先に届き、後続ツールで使えること。サービス更新なら、新しい版が動き、既存データと機能が引き続き使えること。各段階で確認したことと、まだ不明な状態を示します。

フィードバックにも行き先が必要です。実装の誤りは回帰テストにできます。誤解が続く要件は、タスクのテンプレートや設計説明へ戻せます。用途に合わない既定の挙動は、調整できる方針に変えられます。インターフェース自体が合わなければ、設計を再び議論します。同じ問題が繰り返されるなら、注意書きを増やすだけでなく、制約や仕組みを変えます。

これが仕上げの意味です。一度ずれを直したら、次は適切な結果を得やすくする。残す価値のある経験は、[セッションのクローズアウト](/ja/posts/session-closeout/)を通じて、後続タスクが見つけられる記録、手順、検証ツールにします。

## レビューを、判断が必要な場所へ戻す

この方法でも PR はなくなりません。設計、実装、配備、その後の修正には、確認できる変更記録が必要です。

気にしているのは、問題を解決しながら保守負担まで増やしていないか、同じ低レベルの問いを自分が何度も判断していないか、判断を求められるときに材料がそろっているかです。要件が曖昧なら発見から始め、重要な仮定が未検証なら実験し、実装のずれは監査とテストで早く見つけ、新たな取捨選択が生じたら人の判断につなぎます。

人の精力は、判断が必要な地点を理解し、要件を確認することに集中させます。モデルが繰り返し対抗レビューを行って実装の不足を埋め、実際の使用が次のフィードバックを生みます。私の役割は、方向、取捨選択、結果が自分の必要に合っているかを判断することです。

AI を流体のような知能として扱うとは、作業する余地を与えながら、型が適切かを確かめ続けることです。AI は実装の細部を埋め、誤りを探し、型の再設計も手伝えます。人は目的、制約、受け入れ条件、操作の境界を理解し、成果物が用途から外れたときに介入できる必要があります。

Homelab Ops で作りたいのは、必要な形を伝え、AI に連続して進めてもらい、根拠で成果物を確認し、フィードバックを次へ返すリズムです。読むプルリクが多すぎるときは、実装を人の前へ集めるプロセス自体を設計し直す必要があるのかもしれません。
